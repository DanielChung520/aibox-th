## 1. v1 → v2 變更摘要

| 項目 | v1（前版） | v2（本版） |
|------|-----------|-----------|
| Agent 數量 | 5 個全部做 | **先做 3 個**（請購 + 比價 + 跟單） |
| Agent 4 品管 | Phase 1 最優先 | **往後放** |
| Agent 5 評鑑 | Phase 3 | **往後放** |
| SRM 底座 | 未明確定義 | **Phase 0 明確定義**，為 Agent 2 的前置依賴 |
| LINE 供應商通知 | 僅提及 | **明確定義架構**與綁定流程 |
| Ragic 寫入路徑 | 「禁止寫入」一刀切 | **分級定義**：建議 vs 自動化 vs 人工中繼 |

### 為什麼品管和評鑑往後放？

- **Agent 4 品管**：屬於採購流程的後端（到貨才發生），不影響前端請購→比價→下單→跟單的流程閉環。且品管需要與倉管現場作業流程深度整合，獨立開發也能做好。
- **Agent 5 評鑑**：需要累積足夠的採購歷史數據才有意義，至少等 Agent 1-3 上線運作一段時間後再做。

## 3. Phase 0 — SRM 供應商底座

### 3.1 為什麼要有 SRM 底座

Agent 2（比價下單）是整個系統的價值核心，但它**完全依賴供應商資料**：

```
Agent 2 的輸入依賴：
├── 合格供應商清單 → 沒有 → 不知道找誰比價
├── 各供應商歷史報價 → 沒有 → 不知道行情、無法標記異常
├── 供應商等級/評分 → 沒有 → 比價結果無權重，無法排序推薦
└── 供應商聯絡方式 → 沒有 → 下單後 Agent 3 無法通知
```

SRM 底座就是為了解決這個問題——在 Agent 開發的同時，先把供應商資料整理好。

### 3.2 SRM 底座需要的資料

全部資料來源為 **Ragic 既有表單**，SRM 底座不做新的交易系統，只做**資料映射 + 補充 + 分析**。

| 資料 | 來源 | SRM 做的事 | 優先級 |
|------|------|-----------|:------:|
| 供應商基本資料 | Ragic「廠商資料設定」表 | 映射為 SRM 供應商主檔，補充 LINE ID 欄位 | P0 |
| 歷史採購單價 | Ragic「採購憑單」表 | 萃取出「物料 × 供應商 × 日期 × 單價」的歷史報價庫 | P0 |
| 供應商等級 | 暫無→由 SRM 手動設定 | A/B/C 三級，初期人工指定，後續由 Agent 5 自動算 | P1 |
| 供應商 LINE ID | 暫無→需建立綁定流程 | 讓供應商掃 QR Code 綁定 LINE → 後續通知用 | P0 |

### 3.3 SRM 底座頁面（遵循 CRM 模式）

```
src/pages/eea-srm/
├── SrmLayout.tsx           ← 共用外殼（複製 EeaCrmLayout 模式）
├── SupplierListPage.tsx    ← 供應商列表（搜尋 + 表格 + 等級標籤）
├── SupplierDetailPage.tsx  ← 供應商詳情（基本資料 + 歷史交易 + 評分）
├── PriceHistoryPage.tsx    ← 歷史報價庫（物料 × 供應商 × 價格趨勢）
├── LineBindingPage.tsx     ← LINE 綁定管理（QR Code 產出 + 綁定狀態）
└── DashboardPage.tsx       ← SRM 儀表板（供應商統計 + 預警摘要）

路由: /app/eea-srm/{page}
API: srmApi（與 crmApi 平行，放在 src/services/api.ts）
Store: srmStore（Zustand，與 crmStore 平行）
```

### 3.4 Ragic 上需要新增/補強的欄位

建議在 Ragic 既有表單上**補充以下欄位**，不動既有流程：

| 表單 | 新增欄位 | 用途 |
|------|---------|------|
| 廠商資料設定 | `line_user_id`（文字） | 供應商 LINE 綁定後寫入 |
| 廠商資料設定 | `srm_grade`（下拉：A/B/C/E） | SRM 供應商等級 |
| 廠商資料設定 | `srm_status`（下拉：合格/觀察/暫停/黑名單） | SRM 供應商狀態 |

## 4. 三種邊界原則（不可違反）

### 4.1 Ragic 邊界

| 層級 | 定義 | 適用于 |
|:----:|------|--------|
| **T1 建議** | AI 產出文字建議，人員閱讀後自行到 Ragic 操作 | Agent 1 請購建議、Agent 2 比價分析 |
| **T2 草稿** | AI 產出結構化草稿，人員一鍵確認後透過 API 寫入 Ragic | Agent 2 採購單草稿 |
| **T3 自動** | AI 直接透過 API 寫入 Ragic（僅限非交易性資料） | Agent 3 催貨紀錄、SRM 評分卡 |

**禁止**：AI 直接修改 Ragic 的交易性資料（庫存異動、已簽核訂單、財務資料）。

### 4.2 資料邊界

```
Agent → 唯讀查詢 Ragic（透過 Data Agent）
Agent → 讀寫 ArangoDB（SRM 底座自己的資料）
Agent → 寫入 Ragic（僅 T3 層級：催貨紀錄、評分卡）
Agent → 發送 LINE（僅透過通知引擎，不直接呼叫 LINE API）
```

### 4.3 流程邊界

```
Agent 產出建議 → 人工作業確認 → 人員在 Ragic 執行交易操作
Agent 產出草稿 → 人員一鍵確認 → API 寫入 Ragic
Agent 自動執行 → 僅限非交易性、可回溯的操作
```

## 5. Agent 1 — 採購請購小秘

### 5.1 定位

> 就像一個 **採購助理** — 工單來了自動算缺哪些料、要不要買、有沒有人重複買。

### 5.2 負責 QA（5 題）

| 角色 | 問題 | AI 怎麼回答 |
|:----|------|-----------|
| 管理部主管 | 目前有幾張請購單等我簽核？有沒有急件？ | 調出待簽清單，按金額/急迫度排序 |
| 倉管人員 | 輪椅升降機目前庫存還有幾台？夠不夠下週的生產需求？ | 查庫存 + 比對下週工單需求量 |
| 倉管人員 | 新到的空壓機比較大台，建議放哪個儲位？ | 查儲位表 + 物料尺寸 → 建議適當儲位 |
| 生產人員 | 輪椅固定座缺貨，有沒有相容的替代品可以先用？ | 查替代料表 + 庫存 → 列出可用替代品 |
| 生產人員 | 我需要領一把新的電鋸，請購流程怎麼走？ | 引導填寫請購單，告知所需資訊 |

### 5.3 AI 用量：低（約 20%）

```
此 Agent 90% 是規則：
├── BOM 展開 → VLOOKUP 等級
├── 庫存比對 → 數值加減
├── 重複偵測 → 文字比對
├── 儲位建議 → 規則引擎
└── 替代料查找 → 預設替代料表查詢

只有 10% 需要 LLM：
└── 產出「建議說明」文字（如「根據過去6個月趨勢，建議多採購3個」）
```

### 5.4 流程

```
工單建立 / 手動查詢
    │
    ▼
BOM 展開 → 算出所需物料清單
    │
    ▼
比對庫存（現有量 + 在途量 - 已分配量）
    │
    ▼
缺口分析 → 有缺口？
    ├── 無 → ✅ 記錄正常，不動作
    └── 有 → 查近期有無其他人已請購同一物料
              │
              ▼
        產出請購建議（物料 + 數量 + 建議供應商 + 預估單價）
              │
              ▼
        📋 送簽核 → 人員確認後轉正式請購單
```

### 5.5 讀取的 Ragic 表單

| 表單 | 用途 |
|------|------|
| 工單表 / 生產製令單 | 得知目前正在進行的改裝案 |
| PLM-產品主檔維護（BOM） | 展開工單所需物料清單 |
| 庫存表 | 查目前庫存量 |
| 請購憑單 | 查詢已有請購（避免重複） |
| 歷史採購紀錄 | 參考上次跟誰買、多少錢 |
| 儲位表 | 建議存放位置 |

### 5.6 產出

請購建議書（文字報告），包含：
- 物料清單（料號、名稱、需求量）
- 庫存狀況（現有量、在途量、缺口）
- 建議採購量 + 建議供應商
- 預估總金額
- 優先級標記（急迫/正常/可延後）

## 6. Agent 2 — 採購比價下單小秘

### 6.1 定位

> 就像一個 **比價專員** — 自動找合格供應商報價、算誰最划算、產出採購單草稿。

### 6.2 負責 QA（5 題）

| 角色 | 問題 | AI 怎麼回答 |
|:----|------|-----------|
| 管理部主管 | 這張請購單的三家報價結果如何？你建議選哪家？ | 列出三家 TCO 排名 + AI 建議 + 價格異常標記 |
| 管理部主管 | 這張大額採購超出預算了，有沒有更經濟的替代方案？ | 查替代物料/供應商 + 價差分析 |
| 採購人員 | 這個新物料要跟哪些供應商詢價？有合格供應商清單嗎？ | 調出合格供應商名單 + 聯絡方式 + 過去報價參考 |
| 採購人員 | 這張請購單核准了，幫我產生採購憑單並帶入報價資料 | 自動填入採購單草稿 + 附報價文件 |
| 財務人員 | 這張進口的輪椅升降機有沒有關稅減免？稅額怎麼算？ | 依稅則查詢關稅 + 減免條件說明 |

### 6.3 AI 用量：中（約 30%）

```
70% 是規則：
├── 合格供應商篩選 → SQL 查詢 + 狀態過濾
├── TCO 計算 → 單價 + 運費 + 付款條件公式
├── 歷史均價比對 → 數值比較
└── 關稅計算 → 稅則對照表

30% 需要 LLM：
├── TCO 比較的「推薦說明」文案生成
├── 價格異常的「原因推測」文字
└── 替代方案的「可行性評估」說明
```

### 6.4 流程

```
請購單核准事件觸發
    │
    ▼
Step 1：查詢合格供應商
    │ 從 SRM 供應商主檔篩選「狀態=合格 + 類別匹配」
    │ 排除黑名單 / 暫停交易供應商
    ▼
Step 2：調出歷史報價
    │ 從 SRM 歷史報價庫取得各供應商對該物料/類似物料的報價
    ▼
Step 3：TCO 比較
    │ 計算總持有成本（單價 + 運費 + 付款條件換算）
    │ 比對歷史均價，標記價格偏離 > 15% 的項目
    ▼
Step 4：AI 推薦
    │ 排序：TCO 低 → 高（同級時品質分高者優先）
    │ 產出推薦說明
    ▼
Step 5：人員選擇供應商
    │ 管理部主管確認 → 選擇供應商
    ▼
Step 6：產生採購單草稿（T2）
    │ 帶入品項/數量/價格/交期，供人員確認後寫入 Ragic
```

### 6.5 讀取的 Ragic 表單

| 表單 | 用途 |
|------|------|
| 廠商資料設定 | 合格供應商清單 + 等級 + 聯絡方式 |
| 詢價單 / 詢價憑單 | 各供應商過去報價單價 |
| 請購憑單 | 輸入來源（已核准的請購需求） |
| 採購憑單 | **產出目標**（產生採購單草稿） |
| 國定假日表 | 計算預估到貨日（排除假日） |

### 6.6 依賴：SRM 底座

**Agent 2 是唯一「沒有 SRM 底座就不能運作」的 Agent。** 下方這些資料必須在 Phase 0 準備好：

- ✅ 供應商主檔完整（名稱、統一編號、類別、等級、狀態）
- ✅ 歷史報價庫已建立（至少過去 12 個月的採購單價）
- ✅ 供應商等級已至少人工指定一批

如果 Phase 0 來不及完整，Agent 2 可以先以「查詢模式」上線（只列出合格供應商清單 + 歷史價格，不做 TCO 排序推薦），待資料完整後再開啟全功能。

## 7. Agent 3 — 採購跟單小秘

### 7.1 定位

> 就像一個 **催貨專員** — 每天盯交期、快到期自動催、延遲了自動評估影響。這是三個 Agent 中最需要 AI 推理能力的。

### 7.2 負責 QA（6 題）

| 角色 | 問題 | AI 怎麼回答 |
|:----|------|-----------|
| 總經理 | 目前有沒有逾期未交的採購單？會影響哪些客戶的車輛交期？ | 逾期清單 + 關聯工單 + 客戶交期影響評估 |
| 管理部主管 | 本週有哪些採購單即將到期？倉庫備料狀況如何？ | 到期清單 + 庫存缺口分析 |
| 採購人員 | 供應商說那批輪椅固定座要延遲一週，對生產有什麼影響？ | 查關聯工單 → 受影響的車輛 → 延遲天數估算 |
| 採購人員 | 目前我手上有哪些逾期的採購單需要催供應商？ | 逾期清單（依天數排序）+ 供應商聯絡資訊 + 催貨通知草稿 |
| 生產人員 | 我這張改裝工單需要的折疊椅到了嗎？什麼時候可以領？ | 查採購進度 → 物料到貨狀態 → 預計可領時間 |
| 生產人員 | 那台福祉車的改裝還差哪些料沒到？影不影響交車日？ | 未到料清單 + 預計到貨日 + 對交車日的影響 |

### 7.3 AI 用量：高（約 40%）

```
60% 是規則：
├── 交期計算（今日 vs 到期日） → 日期加減
├── 分級邏輯（正常/將逾期/逾期/嚴重逾期） → If-Then
├── 催貨通知產生（套用範本） → 字串模板
└── 待簽/待辦清單彙整 → SQL 查詢

40% 需要 LLM：
├── 延遲影響評估（PO Delay → 影響哪些工單 → 影響哪些客戶交期）
├── 替代方案建議（換供應商？換替代料？）
└── 催貨文案的「語氣分級」調整（一般提醒 vs 正式催告）
```

### 7.4 流程

```
每日定時掃描所有未結案 PO
    │
    ▼
Step 1：交期監控
    │ 計算距交期還有幾個工作天
    │ 分級：正常(>7天) / 將逾期(3-7天) / 逾期(<3天) / 嚴重逾期(已過期)
    ▼
Step 2：分級處理
    │ 正常 → ✅ 不動作
    │ 將逾期 → ⚡ LINE 提醒採購人員
    │ 逾期 → 🚨 自動 LINE 通知供應商 + 採購人員
    │ 嚴重逾期 → 🔥 LINE 通知供應商主管 + 採購主管 + 啟動影響評估
    ▼
Step 3：影響評估（僅嚴重逾期）
    │ 查該物料用在哪張工單
    │ 查該工單對應哪個客戶、預計交車日
    │ 評估延遲天數對交車日的影響
    ▼
Step 4：產出報告
    │ 一般 → 催貨通知（含逾期天數 + 物料 + PO 編號）
    │ 嚴重 → 逾期影響報告（含受影響客戶 + 預計延遲日 + 替代建議）
```

### 7.5 分級催貨矩陣

| 等級 | 條件 | 動作 | 通知對象 | 管道 |
|:----:|------|------|---------|:----:|
| L1 | 距交期 3-7 天 | 系統內提醒 | 採購人員 | 系統通知 |
| L2 | 逾期 < 3 天 | LINE 催貨通知 | 供應商 + 採購人員 | LINE |
| L3 | 逾期 3-14 天 | LINE + Email 催告 | 供應商負責人 + 採購主管 | LINE + Email |
| L4 | 逾期 ≥ 14 天 | 影響評估報告 + 替代方案 | 管理部主管 + 總經理 | Email + 系統報告 |

### 7.6 讀取的 Ragic 表單

| 表單 | 用途 |
|------|------|
| 採購憑單 | 所有進行中的採購單、交期、供應商 |
| 生產製令單（工單） | 查物料用在哪張工單、影響哪個客戶 |
| 廠商資料設定 | 供應商聯絡資訊、LINE ID、歷史交期達成率 |
| 國定假日表 | WORKDAY 計算 |

### 7.7 產出

依觸發等級不同：
- **L1-L2**：催貨通知（LINE 訊息）
- **L3**：催告通知（LINE + Email）
- **L4**：逾期影響評估報告（含受影響客戶清單、預計延遲日、替代方案建議）

## 8. LINE 供應商通知架構

### 8.1 為什麼需要專用架構

既有 CRM 的 LINE 整合（LineAssistantPage）是面向**客戶**的。供應商通知需要：
- 不同的 LINE 帳號（或同一帳號下不同的頻道）
- 不同的訊息範本（催貨通知 vs 客戶關懷）
- 供應商 LINE ID 綁定流程（客戶是掃碼加好友，供應商也需要類似機制）

### 8.2 綁定流程

```
管理部人員在 SRM 頁面選擇供應商 → 點「綁定 LINE」
    │
    ▼
系統產生一次性綁定 QR Code（內含供應商編號）
    │
    ▼
供應商負責人用手機掃 QR Code → 加入 LINE 官方帳號
    │
    ▼
系統記錄 line_user_id → 寫入 Ragic 廠商資料設定的 line_user_id 欄位
    │
    ▼
日後 Agent 3 發出通知時 → 查該供應商的 line_user_id → 發送 LINE 訊息
```

### 8.3 訊息範本

**L2 催貨通知**：
```
{供應商名稱} 您好，

您有一筆訂單即將逾期，請儘速安排出貨：

┌──────────────────────────┐
│ 訂單編號：PO-2026-0123   │
│ 物料名稱：輪椅升降機固定座 │
│ 訂購數量：15 組          │
│ 原訂交期：2026/06/25     │
│ 目前狀態：已逾期 2 天     │
└──────────────────────────┘

請於 2026/06/28 前回覆預計出貨日期。
如已出貨請忽略此訊息。

台灣福祉 採購部
```

**L4 嚴重逾期通知**：
```
⚠️ 緊急通知 ⚠️

{供應商名稱} 您好，

訂單 PO-2026-0123 已逾期 7 天以上，
此物料已影響 {受影響車輛數} 台福祉車的改裝排程。

請於 24 小時內回覆預計出貨日期，
逾期未回覆將依合約辦理。

台灣福祉 採購部
```
