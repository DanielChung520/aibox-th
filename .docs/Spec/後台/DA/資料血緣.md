# 資料血緣（Data Lineage）— 記錄層級關聯圖譜

> 文件定位：定義「資料血緣」功能的完整流程、後端邏輯、前端組件、API 規格及已知限制。

---

## §1 概述

### 1.1 什麼是資料血緣

資料血緣是從**某一筆具體記錄**出發，沿著 schema 圖譜中定義的 FK（foreign key）關聯，**遞迴展開所有相關記錄**，形成一棵「記錄層級的關聯圖譜」。

與 schema 圖譜的區別：

| 面向 | Schema 圖譜（既有） | 資料血緣（本功能） |
|------|-------------------|-------------------|
| 節點 | 表（table） | 記錄（record row） |
| 邊 | 表間關聯定義 | 實際 FK 欄位值 |
| 觸發 | schema 管理頁 | 某一筆記錄的內頁 |
| 目的 | 理解資料結構 | 追蹤資料脈絡 |

### 1.2 兩種載入模式

| 模式 | 說明 | 適用場景 |
|------|------|----------|
| **逐步拼湊（預設）** | 只載入 root 記錄 + FK ghost 邊，點擊 ghost 才展開該邊 | 調查型場景（如退貨追因），每次只載入 <1s |
| **全部展開（選項）** | 一次性 BFS 全跑完，一次吐出完整圖譜 | 已知範圍的批次追蹤，需完整脈絡 |

### 1.3 使用者流程

```
Data Agent → Schema 管理頁
    ↓ 雙擊某張表
資料預覽 Modal（表記錄列表）
    ↓ 點擊某一列
Drawer（記錄明細）
    ↓ 點擊右上角「🔗 資料血緣」按鈕
記錄血緣圖譜 Modal
    │
    ├─ 預設：逐步拼湊模式
    │   ├─ 載入 root 記錄（實心節點）
    │   ├─ 顯示可用 FK 邊為 ghost 節點（虛線框 + 虛線邊）
    │   └─ 點擊 ghost 節點 → 展開該條 FK 邊 → 載入目標記錄
    │
    └─ 選項：全部展開（一次性 BFS）
        └─ 呼叫原本的 trace/record API
```

### 1.4 Ghost 節點視覺

| 屬性 | 值 |
|------|-----|
| 填充色 | `#94a3b8`（slate-400） |
| 填滿透明度 | 0.25 |
| 邊框 | 虛線 `[5, 4]`，`#94a3b8` |
| 標籤 | 目標表名稱 |
| 邊樣式 | 虛線 `[6, 4]`，`#cbd5e1`，半透明 |
| 邊標籤 | `{欄位名稱}={FK值}`（如「進貨單號=IN-001」） |

### 1.5 架構位置（逐步拼湊）

```
Frontend (React)
    │
    ├─ POST /api/v1/da/trace/fk-preview   ← 載入 root + FK 邊 metadata
    └─ POST /api/v1/da/trace/fk-edge      ← 展開單條 FK 邊

Rust API Gateway (:6500)
    ↓ proxy
unified_agents (:8011) → RecordTracer
    ├─ fk_preview()     ─→ _fetch_record_via_proxy + _get_relations_for_table
    └─ expand_fk_edge() ─→ _fetch_records_by_field_value + FK preview (next-level)
```

## §2 後端核心邏輯

### 2.1 RecordTracer 類別

**檔案**：`ai-services/data_agent/ragic/record_tracer.py`

#### 2.1.1 trace() — 一次性 BFS（legacy）

```
Input:
  table_key  : str   — 資料表 ID（如 "FORM_36"）
  record_id  : str   — 記錄的 Ragic row ID（如 "22"）
  account    : str   — Ragic 帳戶名稱
  depth      : int   — 最大追蹤深度（預設 3）
  max_fan_out: int   — 每條 FK 邊最大展開記錄數（預設 10）

Output: DataGraph {
  nodes: [ { table_key, table_name, ragic_id, fields, depth } ],
  edges: [ { from_ragic_id, from_table_key, to_ragic_id, to_table_key,
             via_field_id, via_field_name, relation_type } ],
  root_ragic_id, root_table_key,
  total_records, total_time_ms
}
```

#### 2.1.2 fk_preview() — FK 邊預覽（v2.0.0 新增）

```python
async def fk_preview(table_key, record_id, account) -> dict:
```

| 步驟 | 方法 | 說明 |
|------|------|------|
| 1 | `_fetch_record_via_proxy()` | 取得 root 記錄的全部欄位值 |
| 2 | `_get_relations_for_table()` | 查詢該表的所有出邊 FK 關聯 |
| 3 | `_load_fk_field_map()` | 載入 FK 欄位的 display name |
| 4 | 對每條 FK 關聯：`_get_field_value()` | 從記錄中取出 FK 欄位值 |

**輸出**：

```json
{
  "record": { "_ragicId": "22", "1023149": "IN-001", ... },
  "table_name": "進貨明細",
  "fk_edges": [
    {
      "from_field_id": "1023149",
      "from_field_name": "進貨單號",
      "from_field_value": "IN-001",
      "target_table_key": "ERP_48",
      "target_table_name": "進貨單",
      "relation_type": "many-to-one"
    }
  ]
}
```

**關鍵**：此方法**不 fetch 目標記錄**，只告訴前端「有哪些路可以走」，讓前端顯示 ghost 節點。

#### 2.1.3 expand_fk_edge() — 單條 FK 邊展開（v2.0.0 新增）

```python
async def expand_fk_edge(table_key, record_id, field_id, field_value, account, via_field_name="") -> dict:
```

| 步驟 | 方法 | 說明 |
|------|------|------|
| 1 | `_get_relations_for_table()` | 找到符合 `field_id` 的 FK 關聯 |
| 2 | `_resolve_field_id()` | 將目標表欄位名稱轉換為 field ID |
| 3 | `_fetch_records_by_field_value()` | 搜尋目標表中 FK 值吻合的記錄 |
| 4 | 對每筆目標記錄：重複步驟 1–3 | 取得該記錄的 FK preview（供下一級 ghost） |

**輸出**：

```json
{
  "nodes": [
    { "table_key": "ERP_48", "table_name": "進貨單", "ragic_id": "10", "fields": {...} }
  ],
  "fk_previews": {
    "10": [
      { "from_field_id": "1015500", "from_field_name": "供應商", "from_field_value": "SUP-001",
        "target_table_key": "VENDOR_1", "target_table_name": "供應商", "relation_type": "many-to-one" }
    ]
  },
  "relation_type": "many-to-one",
  "via_field_name": "進貨單號"
}
```

**關鍵**：`fk_previews` 讓前端可以立即顯示下一級的 ghost 節點 — 每次展開都自動包含下一層的 FK 線索。

#### 2.1.4 演算法流程對比

```
trace() 一次性 BFS：
  fetch root → 載入 FK 關聯 → BFS 全部跑完 → DataGraph

fk_preview() + expand_fk_edge() 逐步拼湊：
  fk_preview → root + FK edges metadata
    ↓ 使用者點擊 ghost
  expand_fk_edge → 目標記錄 + 下一級 FK preview
    ↓ 使用者再點擊 ghost
  expand_fk_edge → 更多記錄 + 更下一級 FK preview
    ↓ ...
```

### 2.2 關鍵方法

| 方法 | 目的 | 資料來源 |
|------|------|----------|
| `_fetch_record_via_proxy` | 取得單筆記錄的全部欄位 | Rust Proxy API (`/api/v1/da/ragic/proxy/{table_key}/data`) |
| `_get_relations_for_table` | 取得該表的所有**出邊**關聯 | ArangoDB `da_table_relation_ragic` (source_table) |
| `_load_fk_field_map` | 載入 FK 欄位的 display name | ArangoDB `da_table_relation_ragic` (description) |
| `_fetch_records_by_field_value` | 在目標表中搜尋符合 FK 值的記錄 | Rust Proxy API (page scan) |
| `_resolve_field_id` | 將欄位名稱解析為欄位 ID | ArangoDB `da_field_info_ragic` |
| `_resolve_ragic_path` | 將 table_id 解析為 Ragic tab/sheet | ArangoDB `da_table_info_ragic` |

### 2.3 為何不直連 Ragic API

RecordTracer 最初以 Python `RagicAPIClient` 直連 Ragic API 取得記錄資料，但遇到問題：

1. **`get_record()` 回傳結構不一致** — 單筆記錄 API 回傳的資料欄位數遠少於 list API
2. **快取失效** — 直接呼叫 Ragic API 繞過了 DuckDB cache

**解決方案**：改由 Rust Proxy API 統一代理所有資料查詢：

```
RecordTracer → Rust Proxy (:6500) → DuckDB Cache → Ragic API
```

Proxy 的 `ragicProxyData` 端點：
- 已實作 DuckDB cache hit/miss（位於 `./data/table_cache.duckdb`）
- 欄位格式一致（naming=EID，field_id 為 key）
- 回傳完整的 `rows[]` + `fields[]` 結構

### 2.4 FK 關聯的資料模型

#### ArangoDB `da_table_relation_ragic` 文件結構

```json
{
  "_key": "rel_CONFIGURATIONFILE2_1015500",
  "source_table": "CONFIGURATIONFILE_2",
  "source_field": "1015500",
  "target_table": "CFG7_EMPLOYEE",
  "target_field": "員工編號",
  "relation_type": "many-to-one",
  "description": "代理人編號",
  "data_source": "ragic",
  "status": "enabled"
}
```

**重要**：
- `source_field` **為 field ID**（如 `"1015500"`）— 可直接用於 proxy 資料查詢
- `target_field` **為 field name**（如 `"員工編號"`）— 需用 `_resolve_field_id()` 轉換成 ID
- `status` 可控制關聯啟用／停用

### 2.5 關聯的儲存來源

關聯資料透過以下管道建置：

1. **MD Import 自動解析** — `md_parser_relations.py` + `arango_writer.py`
   - 從 Ragic 欄位的 `linked_to` / `loaded_from` memo 解析
2. **手動種子資料** — `seed_ragic_schema.py`（已停用，由 MD Import 取代）
3. **手動維護** — 可透過 `/api/v1/da/ragic/graph/all-relations` 管理

### 4.4 關鍵邏輯

**逐步拼湊狀態管理**：

```typescript
interface GhostEdge {
  id: string;                    // `${from_record_id}_${from_field_id}`
  from_record_id: string;
  from_table_key: string;
  from_field_id: string;
  from_field_name: string;
  from_field_value: string;
  target_table_key: string;
  target_table_name: string;
  relation_type: string;
}

// Modal 內部狀態
const [loadedNodes] = useState<Map<string, Record<string, unknown>>>();  // 已載入的記錄
const [loadedEdges] = useState<Array<Record<string, unknown>>>();         // 已載入的邊
const [ghostEdges] = useState<GhostEdge[]>();                             // 待展開的 FK 邊
```

**bulidGraph() 合併邏輯**：
1. 將 `loadedNodes` 轉為 G6 實體節點 + force-graph 節點
2. 將 `ghostEdges` 去重（依 `target_table_key`）轉為 ghost 節點
3. 將 `loadedEdges` 轉為實體邊
4. 將 `ghostEdges` 轉為 ghost 邊（指向 ghost 節點）

**Ghost 點擊展開流程**：
```
1. 判斷 ghost 節點對應的 ghostEdges
2. 呼叫 dataAgentApi.fkExpandEdge({ table_key, record_id, field_id, field_value, ... })
3. 從 response.nodes 新增到 loadedNodes
4. 從 response 建立實體邊 (source → target) 新增到 loadedEdges
5. 從 response.fk_previews 建立新 ghostEdges
6. 移除已展開的 ghost edge
7. 重建 ParsedGraph → 重新 init G6
```

**顯示「資料血緣」按鈕的條件**：

```typescript
extra={
  selectedRecord && getRecordId(selectedRecord) ? (
    <Tooltip title="查看此記錄的資料血緣圖譜">
```

## §5 Rust API Gateway 路由

### 5.1 路由註冊

**檔案**：`api/src/api/da.rs`

```rust
// 一次性 BFS（legacy）
.route("/api/v1/da/trace/record", post(ragic_trace_record_proxy))

// FK 邊預覽（progressive）
.route("/api/v1/da/trace/fk-preview", post(ragic_fk_preview_proxy))

// 單條 FK 邊展開（progressive）
.route("/api/v1/da/trace/fk-edge", post(ragic_fk_edge_proxy))
```

### 5.2 Proxy Handler 模式

三個 handler 使用相同的 proxy 模式：

```rust
pub async fn ragic_fk_preview_proxy(Json(payload): Json<Value>) -> Response {
    let url = format!("{}/da/ragic/trace/fk-preview", CONFIG.ai_services.unified_agents_url);
    let Ok(client) = reqwest::Client::builder()
        .timeout(std::time::Duration::from_secs(30)).build() else {
        return StatusCode::INTERNAL_SERVER_ERROR.into_response();
    };
    match client.post(&url).json(&payload).send().await {
        Ok(resp) => { /* 透傳回應 */ }
        Err(e) => { /* 回傳 502 */ }
    }
}
```

| Handler | URL | Timeout |
|---------|-----|---------|
| `ragic_trace_record_proxy` | `/da/ragic/trace/record` | 120s |
| `ragic_fk_preview_proxy` | `/da/ragic/trace/fk-preview` | 30s |
| `ragic_fk_edge_proxy` | `/da/ragic/trace/fk-edge` | 30s |

### 5.3 服務發現

## §6 已知問題與限制

### 6.1 功能限制

| 問題 | 影響 | 原因 | 建議修正 |
|------|------|------|----------|
| **僅限 Ragic 資料源** | SAP / Parquet 資料無法追蹤 | `da_table_relation_ragic` 只存 Ragic 關聯 | 需建立 SAP 關聯資料 `da_table_relation` 及對應的 RecordTracer |
| **Proxy scan 效率** | 目標表資料量大時慢（page scan） | `_fetch_records_by_field_value` 逐頁掃描比對 | 需在 Proxy API 實作欄位值過濾（WHERE clause） |
| **無循環保護（資料層）** | 可能無限追蹤 | schema 層有 visited set，但 FK 值可能形成循環 | 增加 max_total_nodes / max_total_time 防護 |
| **FK 值無類型轉換** | 數字 vs 字串比對不一致 | `_get_field_value` 不做類型正規化 | 標準化為字串比對（已實作 `str().strip()`） |
| **Ghost 節點身分不明** | ghost 節點不知道目標記錄的 `_ragicId` | FK 值不等於 Ragic row ID | 需額外查詢或改由 cache 預存 ID |
| **目標表 field_id 快取** | 多次 resolve 浪費查詢 | `_resolve_field_id` 每次都查 ArangoDB | 新增 LRU cache（table_key → name → id） |

### 6.2 前端注意事項

| 問題 | 說明 |
|------|------|
| **資料表 rowKey** | `SchemaDataPreviewModal` 使用 `rowKey={(_record, idx) => `row_${idx}`}`，無法回溯記錄 ID |
| **Drawer 無資料時** | 若 `selectedRecord.entries()` 為空，Drawer body 顯示空白 Descriptions |
| **圖譜 Modal 無資料** | API 回傳 `total_records=0` 時顯示「尚無關聯記錄」Empty 狀態 |
| **Ghost 點擊防重** | 使用 `expandingEdges: Set<string>` 避免同一 ghost 被重複點擊 |

### 6.3 效能邊界（逐步拼湊 vs 一次 BFS）

| 模式 | 單次查詢 | 深度 3 總成本 |
|------|----------|---------------|
| **逐步拼湊** | 1 次 FK preview + N 次 FK edge（各 <1s） | 使用者控制，只展開需要的路徑 |
| **一次性 BFS** | 1 + N + N² + N³ 次 page scan | 15s+（最壞情況） |

N = 每層 FK 邊數。
