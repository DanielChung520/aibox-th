# 知識管理優化規格書 v6

## 1. 文件定位

### 1.1 文件目的

本文件定義 AIBox / 艾企系統中「知識管理」的 v6 優化方向。

v6 不再以「上傳、切塊、向量化、圖譜抽取」作為中心，而是將知識管理重新定義為：

> **一套可治理、可追溯、可授權、可組裝的知識邊界系統。**

知識管理的目的，不是把文件處理進系統；而是保證 AI 在企業場景中，永遠只在**被允許的知識邊界內**，使用**可審核的證據包**來輔助人類決策。

### 1.2 v6 與 v5 的本質差異

| 面向 | v5 | v6 |
|------|----|----|
| 核心關注 | 文件上傳與多模態處理管線 | 知識邊界治理與有界證據組裝 |
| 成功標準 | 上傳成功、向量成功、圖譜成功 | 回答有邊界、有證據、有來源、可審核 |
| 知識角色 | 被處理的文件 | 可治理的企業證據資產 |
| HybridRAG 角色 | 雙通道檢索 | 證據/記憶組裝層 |
| 圖譜角色 | 知識抽取結果 | 結構化事實網絡與邊界約束 |
| 向量角色 | 語義召回 | 候選證據召回器 |

## 2. 設計背景

### 2.1 既有系統已經做到什麼

根據現行代碼與既有規格，系統已具備以下能力：

- 知識庫建立、編輯、複製、授權與收藏（`KnowledgeBaseManagement.tsx`）
- 知識庫詳情頁三欄式檢視（文件清單 / 內容 / 圖譜側邊面板）（`KnowledgeBaseDetail.tsx`）
- Basic / Domain / Major 三層知識本體管理（`OntologyList.tsx`）
- Celery 非同步任務：文件向量化與圖譜抽取（`celery_app/tasks.py`）
- LLM 圖譜抽取與 chunk 平行處理（`kb_pipeline/graph.py`）
- HybridRAG：Query Classifier → Embedding → Qdrant → ArangoDB → Fusion（`knowledge_agent/hybrid_rag/service.py`）

### 2.2 既有系統還缺什麼

現行系統的主要短板，不在「處理能力不足」，而在「治理與證據契約不足」：

- 向量點與圖譜節點之間缺少強制性的 canonical link
- Graph 抽取依賴 free-form LLM JSON，易失真、難審核
- Graph Search 目前偏向 keyword + BM25，尚未形成真正的 path-centric evidence retrieval
- HybridRAG 有融合，但缺少明確的 evidence pack contract
- UI 有圖譜展示，但缺少 provenance 顯示（來源 chunk、原文位置、信心度、版本）
- Ontology 已存在，但對抽取、檢索、回答的規範力仍不足

因此，v6 的目標不是「再做更強的 ingestion」，而是補齊：

> **知識邊界、證據契約、來源追溯、權限控制、生命週期治理。**

## 3. v6 的核心主張

### 3.1 知識邊界 = 安全邊界

在企業 AI 中，知識不是越多越好；未被治理的知識，會成為幻覺與越權的來源。

因此 v6 的第一原則是：

> **AI 是否能使用某段知識，不由 LLM 自行判斷，而由產品層定義的知識邊界合約來決定。**

### 3.2 知識管理的最終輸出不是 Chunk，而是 Evidence Pack

v6 中，知識管理的輸出不應再停留在：

- file
- chunk
- vector point
- graph node

而應提升為：

> **Evidence Pack（證據包）**

它是可被 AI 使用、也可被人類審查的最小知識單位。

### 3.3 記憶不是累積，而是組裝

v6 採納以下觀點：

- 記憶不是 prompt 變長
- 記憶不是資料永久累積
- 記憶是依任務與邊界條件，動態組裝出來的 working set

因此，知識管理必須為未來的 HybridRAG / Memory Service 提供：

- 可治理的來源
- 可引用的證據
- 可撤回的記憶材料
- 可融合的上下文組件

---

## 4. v6 要優化的真正對象

### 4.1 不是 Upload Pipeline

Upload、分類、切塊、向量化、圖譜抽取在 v6 中仍然重要，但它們都降級為支援層。

### 4.2 是知識治理與組裝能力

v6 應優化的核心對象，是以下四件事：

1. **Knowledge Boundary Control**：AI 能使用哪些知識、不能使用哪些知識
2. **Evidence Assembly**：如何從向量、圖譜、結構與原文中組裝證據
3. **Governed Memory**：哪些知識可保留、可過期、可撤回、可重建
4. **Provenance & Auditability**：每個回答如何回到來源、版本與權限

## 6. 核心數據與治理模型

### 6.1 四種知識單位

v6 中知識管理需明確區分以下四種單位：

| 單位 | 說明 | 是否可直接供 LLM 使用 |
|------|------|----------------------|
| File | 原始文件 | ❌ |
| Chunk | 切塊後文本 | ⚠️ 僅限經過邊界與版本驗證後 |
| Graph Entity / Edge | 結構化實體與關係 | ⚠️ 僅作為結構證據，不直接視為最終答案 |
| Evidence Pack | 組裝完成、可審核的證據包 | ✅ |

### 6.2 Evidence Pack 定義

Evidence Pack 至少應包含以下欄位：

```json
{
  "evidence_id": "ev_xxx",
  "root_id": "kb_xxx",
  "file_id": "file_xxx",
  "chunk_index": 12,
  "entity_id": "kg_xxx",
  "source_type": "vector|graph|fusion|raw",
  "content": "...",
  "normalized_score": 0.87,
  "extraction_confidence": 0.91,
  "ontology_version": "v1.2.0",
  "text_span": {"start": 1200, "end": 1450},
  "usable_scope": ["knowledge_answer", "intent_support"],
  "version": "2026-04-17T23:35:16Z",
  "status": "active"
}
```

### 6.3 Governed Memory 定義

任何可被 AI 調用的記憶材料，都必須可追溯到其原始證據。

若無法回答以下問題，則不應被視為可治理記憶：

- 這段知識來自哪份文件？
- 是哪個版本？
- 使用的是哪個 ontology？
- 是誰允許它可被調用？
- 若知識過期，能否撤回？

## 7. v6 的知識邊界模型

### 7.1 邊界維度

知識邊界至少應由以下維度共同定義：

| 維度 | 說明 |
|------|------|
| `root_id` | 知識庫根邊界 |
| ontology domain / major | 知識語義邊界 |
| role auth | 角色授權邊界 |
| lifecycle status | 生效 / 過期 / 撤回邊界 |
| usage scope | 可被哪種 agent / task 使用 |

### 7.2 邊界控制原則

1. LLM 不可自行推測可否使用某知識
2. 所有檢索結果必須先過邊界判定，再進 evidence assembly
3. 超出邊界的知識，即使高相關，也不得被用於最終回答

---

## 8. v6 的向量與圖譜協作模型

### 8.1 向量不是答案，是召回器

Qdrant 的角色：

- 找回語義相近候選 chunk / evidence
- 補足語義模糊與表達差異
- 提供相似案例與局部上下文入口

Qdrant 不應直接決定回答內容。

### 8.2 圖譜不是答案，是事實網絡

ArangoDB 的角色：

- 表示結構化實體與關係
- 支援合法的關聯檢索與 path expansion
- 提供事實網絡與 anchor 對齊能力

Graph 不應被當成「大圖就是大智慧」的萬能宇宙。

### 8.3 HybridRAG v6 重新定義

v6 中，HybridRAG 不應再被理解為：

> vector search + graph search + RRF

而應被重新定義為：

> **bounded evidence assembly system**

它負責：

1. 依 query + root_id + ontology + role 找到候選證據
2. 把 vector / graph / raw chunk 組成 evidence pack
3. 保留 provenance、score、confidence、version、usable scope
4. 輸出可供後續 Inquiry Controller / Answer Generator 使用的最小必要證據集

## 9. 現行代碼基礎上的 v6 重點修正項

### 9.1 Canonical Link 必須升級為一等公民

目前向量點與圖譜節點之間缺少強制對應。

v6 必須要求：

- Qdrant payload 必須帶有可回查的 canonical id
- knowledge_graphs / knowledge_graph_edges 必須能對回 file_id / chunk_index / text_span
- entity / edge / vector point / raw chunk 必須形成可追溯鏈路

### 9.2 Graph 抽取契約必須結構化

目前 `kb_pipeline/graph.py` 依賴 free-form LLM JSON，再以修補方式解析。

v6 應明確要求：

- 使用嚴格 JSON Schema 或 function-calling 契約
- entity_type 必須正規化到 ontology base_class
- relation 必須能回對 ontology property 或標示為自定義推斷
- 每個 entity / relation 應攜帶 confidence 與 text span

### 9.3 Graph Search 必須從 keyword-like 邁向 evidence-grade retrieval

目前 Graph Search 偏向：

- keyword extraction
- LIKE match
- BM25 ranking

v6 應明確保留此模式作為 baseline，但新增：

- entity_id 對齊檢索
- relation-aware retrieval
- path-constrained expansion
- score normalization

### 9.4 UI 必須展示 provenance

目前 UI 能展示圖譜與節點，但缺少以下能力：

- 點擊節點查看原始來源片段
- 顯示實體抽取信心度
- 顯示 ontology 對齊結果
- 顯示知識版本 / 生效狀態
- 顯示 evidence pack 的來源類型與 fusion 依據

v6 必須將這些納入 UI 契約。

---

## 10. Ontology 在 v6 中的角色提升

### 10.1 Ontology 不再只是抽取提示

目前 ontology 主要作為：

- GraphExtractor prompt guidance
- Frontend domain / major 管理

v6 中 Ontology 應升級為：

- 知識邊界的語義定義器
- entity_type / relation_type 的標準來源
- evidence pack 的可用範圍判定依據
- future anchor / working set assembly 的基礎語義骨架

### 10.2 Ontology Versioning

v6 必須定義：

- ontology_version
- 抽取時所用 ontology_version
- 當 ontology 更新後，哪些 graph / vector / evidence 需要重建或標記過期

---

## 11. 知識生命週期治理

### 11.1 狀態模型

除現有 `vector_status` / `graph_status` 外，v6 需新增至少以下治理狀態：

| 狀態 | 說明 |
|------|------|
| `draft` | 已上傳但未生效 |
| `active` | 可被檢索與回答使用 |
| `deprecated` | 不建議使用，但保留歷史 |
| `revoked` | 禁止再被任何回答使用 |
| `expired` | 時效已過，需重新驗證 |

### 11.2 生命週期事件

必須定義以下事件：

- upload
- vectorized
- graph_extracted
- activated
- re-indexed
- revoked
- expired
- deleted

每個事件都應可審核。

---

## 12. API 與資料契約方向

### 12.1 Hybrid Search Response 必須升級

目前 HybridSearchResponse 偏檢索結果導向。

v6 需要回傳：

- normalized_score
- source_id
- source_type
- provenance
- extraction_confidence
- usable_scope
- lifecycle_status
- ontology_version

### 12.2 Knowledge File API 必須升級

文件詳情 API 應能回傳：

- file 的治理狀態
- 其 graph / vector 是否依附於哪個 ontology_version
- evidence pack 統計
- graph node / edge 的 provenance completeness

---

## 13. 驗收指標重新定義

v6 不應只以這些指標驗收：

- 上傳成功率
- 向量化成功率
- 圖譜成功率
- 檢索延遲

還必須加入以下指標：

### 13.1 邊界與治理指標

- 邊界違規攔截率
- evidence pack provenance completeness
- revoked / expired knowledge exclusion rate

### 13.2 證據品質指標

- answer-evidence alignment rate
- graph entity canonical linkage rate
- ontology normalization success rate

### 13.3 可審核性指標

- 節點可回查原文比例
- chunk / entity / vector point / answer 的 trace completeness
- 人工審核耗時

---

## 14. v6 明確拒絕的舊假設

以下假設在 v6 中應被明確否定：

1. **多上傳 = 更聰明**
2. **檢索命中率高 = 回答可靠**
3. **圖譜抽得多 = 更能推理**
4. **記憶越多 = 上下文越好**
5. **LLM 可以自行判斷哪些知識可用**
6. **現有 HybridRAG 已經足夠成熟，只要微調即可**

---

## 15. 與後續規格的關係

本 v6 規格是後續兩個方向的基礎：

### 15.1 HybridRAG 優化規格

知識管理 v6 定義的是邊界與證據契約；HybridRAG 優化規格將在此基礎上，進一步定義：

- evidence assembly 流程
- anchor / path / working set 的組裝規則
- retrieval / fusion / provenance 的執行細節

### 15.2 操作感知與意圖收斂規格

當 knowledge side 有了可治理的 evidence pack 與 clear boundary，後續 actionTrail / intent system 才能安全地調用並收斂使用者意圖。

---

## 16. 結論

v6 的知識管理，不再只是文件上傳與處理系統。

它應被重新定義為：

> **艾企系統中，負責管理知識邊界、維護知識生命週期、保證 AI 只能使用可審核證據、並為後續 HybridRAG / Memory / Inquiry Controller 提供可治理知識材料的核心底座。**

如果 v5 解決的是「如何把知識放進系統」，那麼 v6 解決的就是：

> **系統如何知道哪些知識能用、怎麼用、用到哪裡為止，並且在整個過程中保持可追溯、可治理、可審核。**
