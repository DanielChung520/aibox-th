## 1. 概述

### 1.1 工具定位

`tool_reports` 是一個報表產生工具，設計給任何 Agent / API 調用。

目標：
- 輸入一個資料集 + 報表目標（自然語言描述）
- 由 LLM 自動推薦圖表類別（若未指定）
- 若有知識領域需求，先查詢知識圖譜理解領域上下文
- 產生含圖表 + 文字說明的 HTML 報告
- 上傳至 SeaweedFS，回傳 URL 供前端決策

### 1.2 與既有 report_agent 的差異

| 項目 | 既有的 report_agent | 新的 tool_reports |
|------|--------------------|-------------------|
| 呼叫方式 | HTTP mount 路徑 | unified_agents `/mcp/execute` 統一介面 |
| LLM 解析 | 各自實作 provider 邏輯 | `shared/llm_resolver` 統一解析 |
| 多 Provider 支援 | Ollama only | ✅ DeepSeek / Ollama / 可擴展 |
| 輸入格式 | JSON `data: dict` | 結構化 Input Model |
| 報表目標 | ❌ 無 | ✅ `report_goal: str` |
| 知識領域理解 | ❌ 無 | ✅ `knowledge_domain` 參數 |
| 備註提示 | ❌ 無 | ✅ `hints: str` |
| 圖表推薦 | 基於資料結構 | 基於 `report_goal` + 領域知識 |
| Combo 圖表 | ❌ 無 | ✅ `combo` (Line+Bar) |
| 回傳格式 | 自訂 JSON | 統一 `ToolResult` |
| 執行模式 | 同步 | 同步（非同步設計中，見 §13） |

### 1.3 設計原則

- **無狀態**：每次呼叫獨立，不依賴 session 或歷史狀態（非同步模式除外）
- **Provider 解耦**：透過 `shared/llm_resolver` 統一處理 `model_id → provider → base_url + api_key`，新增 provider 無需改程式碼
- **可被任何 Agent 調用**：透過 `POST /mcp/execute` 或 `shared/tools/` registry
- **設定集中化**：相關參數存放於 `system_params` + `model_providers` 集合

## 3. LLM Provider 解析（v1.3.0 新增）

### 3.1 解析鏈

```
model_id = "deepseek:deepseek-v4-flash"
         ↓ shared/llm_resolver.resolve()
         ├─ 解析 provider:model
         │    provider = "deepseek"
         │    model    = "deepseek-v4-flash"
         ├─ 查詢 system_params llm.providers
         │    base_url = "https://api.deepseek.com/v1/chat/completions"
         ├─ 查詢 model_providers 集合
         │    api_key = "sk-..."
         └─ 構建 endpoint
              Ollama     → {base_url}/api/chat
              DeepSeek   → {base_url}（已為完整路徑）
```

### 3.2 支援的 Provider

| Provider | Model ID 範例 | base_url |
|----------|-------------|----------|
| Ollama | `llama3.2:latest` | `http://localhost:11434` |
| DeepSeek | `deepseek:deepseek-v4-flash` | `https://api.deepseek.com/v1/chat/completions` |

### 3.3 新增 Provider 的方法

1. 在 `system_params` 的 `llm.providers` 新增 provider 設定（base_url）  
2. 在 `system_params` 的 `llm.activated_models` 新增模型條目  
3. 在 `model_providers` 集合設定 api_key（透過前端 SystemParamsModels 頁面）  
4. 無需修改程式碼 — `shared/llm_resolver` 自動解析

## 4. 輸入規格

### 4.1 Input Model (`ToolReportsInput`)

```python
class ToolReportsInput(BaseModel):
    # ===== 必要欄位 =====
    dataset: dict | list[dict]
    """資料集，支援 dict（單筆）或 list[dict]（多筆）"""

    report_goal: str
    """報表目標，以自然語言描述（例如：「顯示本月各部門營收占比」、「分析庫存週轉趨勢」）"""

    # ===== 選填欄位 =====
    preferred_chart: str | None = None
    """期望圖表類別，可選值：pie / bar / line / area / scatter / combo"""

    knowledge_domain: str | None = None
    """知識領域（可選），例如：inventory / procurement / manufacturing / finance / sales"""

    hints: str | None = None
    """備註提示，例如：「紅字表示超標」、「僅顯示前10名」"""

    # ===== 報表參數 =====
    field_hints: str | None = None              # 🆕 v1.4.0
    """指定關注欄位（自然語言），例如：「關注銷售金額和利潤率兩欄；不需理會備註欄」"""

    special_notes: str | None = None            # 🆕 v1.4.0
    """特別提示（自然語言），例如：「數值超過1000以紅色標註；前五名放大顯示」"""

    legend_show: bool = True                    # 🆕 v1.4.0
    """圖例是否顯示，預設 True"""

    legend_position: str = "bottom"             # 🆕 v1.4.0
    """圖例位置，可選值：top / bottom / left / right"""

    # ===== 報告設定 =====
    title: str | None = None
    """報告標題，預設以 report_goal 前 30 字作為標題"""

    author: str = "system"
    """報告作者，預設 "system" """

    username: str = "anonymous"
    """用戶名（用於 SeaweedFS 路徑組織）"""

    chart_options: dict | None = None
    """圖表額外選項，例如 {"colors": ["#FF0000", "#00FF00"]}"""
```

### 4.2 參數約束

| 欄位 | 類型 | 約束 |
|------|------|------|
| `dataset` | dict \| list[dict] | 必填，大小限制 1MB |
| `report_goal` | string | 必填，長度 1-500 字 |
| `preferred_chart` | string | 可選，有效值見 4.1 |
| `knowledge_domain` | string | 可選，長度 1-100 字 |
| `hints` | string | 可選，長度 0-500 字 |
| `field_hints` | string | 🆕 可選，長度 0-300 字 |
| `special_notes` | string | 🆕 可選，長度 0-500 字 |
| `legend_show` | bool | 🆕 可選，預設 True |
| `legend_position` | string | 🆕 可選，有效值：top / bottom / left / right |
| `title` | string | 可選，長度 0-100 字 |
| `author` | string | 可選，長度 0-50 字 |
| `username` | string | 可選，長度 0-50 字 |

## 6. 處理流程

### 6.1 Step 1：輸入驗證

- 檢查必要欄位 `dataset` 和 `report_goal` 是否存在
- 檢查 `dataset` 大小是否超過 1MB
- 檢查 `preferred_chart` 是否為有效值
- 驗證失敗 → 回傳 `ToolResult` with `success=false`

### 6.2 Step 2：LLM Provider 解析（v1.3.0）

由 `shared/llm_resolver.resolve(model_id)` 統一處理：
1. 從 tool config 讀取 `llm_model`（如 `deepseek:deepseek-v4-flash`）
2. 解析 provider + model name
3. 從 `system_params.llm.providers` 取得 `base_url`
4. 從 `model_providers` 集合取得 `api_key`
5. 構建最終 endpoint（區分 Ollama `/api/chat` 與 OpenAI `/v1/chat/completions`）

### 6.3 Step 3：LLM 分析（僅產生資料，非排版）

```
1. 將 dataset 傳給 LLM（附帶 report_goal + domain_context）
2. LLM 任務（嚴格限制）：
   a. 理解 report_goal
   b. 對 dataset 進行有意義的聚合（不可逆推原始資料）
   c. 產生 chart_data（[{name, value}, ...] 格式）
   d. 產生 analysis_summary（繁體中文，200-300字）
   e. 推薦 chart_type（若未指定）

3. LLM 嚴格禁止輸出：
   - ❌ 任何 HTML/CSS 結構
   - ❌ 任何原始資料值
   - ❌ 可逆向工程取得原始資料的內容
   - ❌ 排版相關指令

4. 輸出的 chart_data 範例：
   [
     {"name": "A部門", "value": 5550000},
     {"name": "B部門", "value": 3700000},
     {"name": "C部門", "value": 3090000}
   ]
```

### 6.4 Step 4：HTML 報告生成（Template 負責排版）

我們只用 **1 個固定 HTML Template**，LLM 只負責資料分析。透過 `CHART_HTML_MAP` 切換 6 種 Recharts 組件。

```
┌─────────────────────────────────────┐
│  Header（固定：漸層色 + title slot）  │
├─────────────────────────────────────┤
│  圖表區（根據 chart_type 切換）      │
│  ┌──────────────────────────────┐   │
│  │  Recharts 組件（6選1）        │   │
│  └──────────────────────────────┘   │
├─────────────────────────────────────┤
│  分析區（analysis_summary slot）     │
├─────────────────────────────────────┤
│  備註區（hints 存在才顯示）          │
├─────────────────────────────────────┤
│  Footer（固定）                      │
└─────────────────────────────────────┘
```

### 6.5 Step 5：SeaweedFS 上傳

```
上傳路徑：/buckets/user_{username}/reports/{timestamp}_{safe_title}.html

username = "".join(c for c in username if c.isalnum() or c in "-_")
title = "".join(c for c in title if c.isalnum() or c in "-_ ")[:30]
filename = f"{timestamp}_{safe_title}.html"
```

### 6.6 Step 6：回傳結果

- 若成功 → 回傳 `ToolResult` with `success=true` + 完整 Output
- 若失敗 → 回傳 `ToolResult` with `success=false` + `error` 訊息

## 9. 錯誤處理

| 錯誤情境 | 回傳行為 |
|----------|----------|
| dataset 為空 | `success=false, error="資料集不得為空"` |
| dataset 超過 1MB | `success=false, error="資料集大小超過限制 (1MB)"` |
| report_goal 為空 | `success=false, error="報表目標不得為空"` |
| LLM 调用失敗 | `success=false, error="LLM 分析失敗: {reason}"` |
| LLM API Key 無效 | `success=false, error="Authentication Fails..."`（DeepSeek 401） |
| LLM Model 不存在 | `success=false, error="model not found"`（Ollama 404） |
| SeaweedFS 上傳失敗 | `success=false, error="報告上傳失敗: {reason}", warnings=["上傳失敗但報告已生成"]` |
| 未知 chart_type | `success=false, error="不支援的圖表類別: {type}"` |

## 13. 非同步報表設計（設計中 🔧）

### 13.1 目標

目前報表產生為**同步阻塞**模式（前端等待 30-300s）。改造目標：

1. **非同步提交**：使用者點「產生」後立即回傳，不阻塞 UI
2. **狀態追蹤**：每筆報告記錄有 `status` 欄位，前端顯示對應顏色
3. **自動命名**：以 `report_goal` 前 20 字作為 `report_name`

### 13.2 狀態定義

| 狀態 | 顯示顏色 | 說明 |
|------|----------|------|
| `generating` | 🟠 橘色 | Celery task 已提交，正在生成中 |
| `completed` | 🟢 綠色 | 報告已產生並上傳成功 |
| `error` | 🔴 紅色 | 產生失敗（附 error_message） |

### 13.3 架構變更

```
現況（同步）                     改造後（非同步）
────────────────                 ──────────────────
使用者點「產生」                  使用者點「產生」
  │                                 │
  ▼                                 ├─ ① 建立 DB 記錄
等待 30-300s                          │    status: "generating"
  │                                   │    report_name: goal[:20]
  ▼                                   │
結果回傳                              ├─ ② 提交 Celery task
  │                                   │    generate_report_task.delay(...)
  ▼                                   │
存 DB                                 ├─ ③ 立即回傳，關閉表單
                                       │
                                       └─ ④ Celery Worker 背景執行
                                          ├─ LLM 分析
                                          ├─ 生成 HTML
                                          ├─ 上傳 SeaweedFS
                                          └─ PATCH DB:
                                               成功 → status: completed + report_url
                                               失敗 → status: error + error_message
                                       │
                                       └─ ⑤ 前端輪詢/SSE 更新狀態
```

## 15. 設計決策記錄

### 15.1 為什麼只用 1 個 Template？

| 考量 | 說明 |
|------|------|
| LLM 不適合做排版 | HTML/CSS 產生太機械化，容易不一致、浪費 tokens |
| Token 節省 | 若每次請求都讓 LLM 產生排版，會浪費大量 tokens |
| 品牌形象統一 | 配色、字體、間距可集中管理，確保一致 |
| 維護性 | 修改排版只需改一個地方 |

### 15.2 LLM 與 Template 的分工

| 負責方 | 職責 |
|--------|------|
| **LLM** | 資料聚合、chart_data 生成、analysis_summary 產生、chart_type 推薦 |
| **Template** | HTML 結構、CSS 樣式、Recharts 圖表組件組合、品牌形象 |

### 15.3 為什麼要抽離 llm_resolver？

| 考量 | 說明 |
|------|------|
| 避免重複實作 | `aitask/main.py` 和 `llm_analyzer.py` 各有自行的 provider 解析 |
| 新增 Provider 零程式碼 | 只需更新 system_params + model_providers |
| URL 路徑差異 | Ollama 用 `/api/chat`，OpenAI/DeepSeek 用 `/v1/chat/completions`，統一處理 |
| API Key 雙來源 | 從 model_providers（用戶 UI 設定）和 system_params 自動查找 |

## 16. 風險與注意事項

| 風險 | 說明 | 緩解措施 |
|------|------|----------|
| LLM 產出不穩定 | 生成的 chart_data 可能格式不符 | 加強 prompt + 後處理驗證 |
| 資料逆向工程 | 使用者可能從 chart_data 反推原始資料 | 限制聚合程度，禁止輸出可逆推的原始資料 |
| 大資料集 | dataset 過大導致效能問題 | 設定 1MB 限制 + 提示切割 |
| API Key 過期 | DeepSeek API key 過期導致 401 | 錯誤訊息明確提示，用戶可在前端更新 |
| Model name 變更 | DeepSeek 隨時可能變更 model name | 集中管理在 llm.activated_models |
