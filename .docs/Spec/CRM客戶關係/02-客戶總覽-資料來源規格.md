# 客戶總覽 — 資料來源規格

## 1. 目的

定義 EEA-CRM「客戶總覽」功能的三源資料整合架構，包含資料模型、來源映射、同步策略與查詢介面。

### 1.1 用詞定義

| 用詞 | 定義 |
|------|------|
| **客戶總覽** | CRM 首頁功能，聚合三源資料以統一視圖呈現所有客戶/機構 |
| **產業潛在客戶** | 來自衛福部機構清單，尚未被業務觸及的長照機構 |
| **業務接觸中** | 來自業務王系統，業務已建立聯繫但尚未成單 |
| **既有客戶** | 來自 Ragic CRM，已有交易往來的客戶 |

---

## 2. 資料來源總覽

| 來源 | 儲存方式 | 資料角色 | 地圖顏色 | 同步機制 |
|------|---------|---------|---------|---------|
| **衛福部** | ArangoDB `crm_customers` | 產業潛在客戶 | 🟢 綠色 | CSV 排程（手動觸發或定期排程更新） |
| **業務王** | ArangoDB `crm_customers` | 業務接觸中 | 🟡 黃色 | 一次性導入（手動 CSV 匯入，匯入後不再同步） |
| **Ragic CRM** | API 即時查詢 | 既有客戶 | 🔵 藍色 | API 即時（schema 由 da_tables 管理） |

## 3. ArangoDB Collection：`crm_customers`

### 3.1 資料模型

```
Collection: crm_customers
Key: 自動 _key (UUID)
Indexes:
  - source (hash)
  - status (hash)
  - name (persistent, 用於搜尋)
  - lat_lng (geo, 用於地圖查詢)
  - phone (persistent, 用於去重比對)
  - unified_id (unique, sparse, 用於跨源關聯)
```

### 3.2 欄位定義

#### 基礎識別欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `_key` | string | auto | ArangoDB 自動產生的唯一 ID (UUID) |
| `source` | string | ✅ | 資料來源：`mohw` / `business_kindom` / `ragic` |
| `status` | string | ✅ | 狀態：`potential` / `lead` / `customer` / `merged` |
| `unified_id` | string | | 跨源統一 ID，供合併記錄關聯使用（相同機構在不同來源時共用） |

#### 來源原始 ID（保留 source 原始鍵值，供溯源使用）

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `mohw_id` | string | | 衛福部機構代碼（如：`1S1500012`），僅 source=mohw 時有值 |
| `business_kindom_id` | string | | 業務王流水號（如：`6336`），僅 source=business_kindom 時有值 |
| `ragic_sheet_id` | string | | Ragic Sheet 編號（如：`10`），僅 source=ragic 時有值 |
| `ragic_record_id` | number | | Ragic 記錄 ID，僅 source=ragic 時有值 |

#### 名稱與分類欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `name` | string | ✅ | 機構/客戶名稱（標準化後） |
| `name_short` | string | | 簡稱（Ragic 有「交易對象簡稱」欄位） |
| `name_raw` | string | | 來源原始名稱（未標準化前） |
| `category` | string[] | | 分類標籤（如：`["長照機構", "居家式"]`，彙整三源分類） |
| `abc_grade` | string | | ABC 分級：`A` / `B` / `C` / `E` / `null`（主要來自業務王） |
| `customer_attr` | string | | 客戶屬性（Ragic：下游業者/消費者） |
| `transaction_status` | string | | 交易狀態（Ragic：評估中/交易中/停止交易） |

#### 聯絡方式欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `phone` | string | | 主要電話號碼（標準化後） |
| `phone_raw` | string | | 來源原始電話號碼 |
| `phone_alt` | string[] | | 其他聯絡電話清單 |
| `email` | string | | 電子郵件 |
| `contact_person` | string | | 聯絡人姓名（業務王有「客戶名稱=聯絡人」） |
| `contact_title` | string | | 聯絡人職稱/部門 |

#### 地址與地理座標欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `address` | string | ✅ | 完整地址（標準化後） |
| `city` | string | ✅ | 縣市 |
| `district` | string | ✅ | 鄉鎮市區 |
| `lat` | number | | 緯度（WGS84） |
| `lng` | number | | 經度（WGS84） |
| `geo_source` | string | | 座標來源：`mohw` / `geocoded` / `manual` |

#### 業務資訊欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `sales_rep` | string | | 負責業務人員名稱 |
| `last_contact_at` | string (ISO datetime) | | 最近互動時間 |
| `last_contact_note` | string | | 最近互動備註 |
| `lead_source` | string | | 開發管道（如：`衛福部資料` / `陌開` / `轉介紹`） |
| `tags` | string[] | | 自訂標籤（彙整三源 tag） |

#### 去重合併欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `duplicate_group` | string | | 去重群組 ID，同一機構不同來源共用同一值 |
| `merge_status` | string | ✅ | `independent` / `primary` / `merged` |
| `merged_into` | string | | 當 merge_status=merged 時，指向 primary 記錄的 _key |
| `merge_history` | array | | 合併歷史記錄 |
| `match_confidence` | number | | 比對信心分數 0.0~1.0（用於自動比對時） |

#### 系統時間欄位

| 欄位 | 型態 | 必要 | 說明 |
|------|------|------|------|
| `created_at` | string (ISO datetime) | auto | ArangoDB 記錄建立時間 |
| `updated_at` | string (ISO datetime) | auto | 最後更新時間 |
| `synced_at` | string (ISO datetime) | | 資料來源最近同步時間（用於判斷資料新鮮度） |
| `source_updated_at` | string (ISO datetime) | | 資料來源端的更新時間（衛福部 CSV 發布時間／業務王建檔時間／Ragic 更新時間） |
| `import_batch` | string | | 匯入批次 ID（用於追蹤哪次匯入） |

## 4. 各來源實作細節

### 4.1 衛福部（source: `mohw`）

**存取方式：** HTTP GET `https://ltcpap.mohw.gov.tw/public/csv/all.csv`

**同步策略：** 可手動觸發或設定定期排程更新

**實作：**
- 提供後台「衛福部資料同步」按鈕，手動觸發 CSV 下載與匯入
- 可選設定定期排程（如每日/每週），由排程 Job 自動執行
- 解析 CSV（欄位：機構名稱, 機構代碼, 機構種類, 縣市, 區, 地址全址, 經度, 緯度, O_ABC, 特約服務項目, 機構電話, 電子郵件）
- 寫入 `crm_customers` collection，`source=mohw`, `status=potential`
- 若有相同 `mohw_id` 已存在，比對欄位差異後更新（不建立重複記錄）
- 每次匯入完成後自動觸發與既有 `business_kindom` 記錄的去重比對

**去重策略：**
- 第一層：`mohw_id` 完全相同 → 更新現有記錄
- 第二層：機構名稱 + 電話模糊比對（參考 jaro-winkler distance）→ 標記 `duplicate_group`

**排程設定：**
| 項目 | 值 |
|------|-----|
| 觸發方式 | 後台手動啟動（主要）／可選設定定期排程（每日/每週） |
| 超時 | 5 分鐘（31K+ 筆） |
| 錯誤處理 | 下載失敗時保留上次資料，記錄 error log |
| 首次執行 | 全量匯入（手動觸發） |

### 4.2 業務王（source: `business_kindom`）

**同步策略：** 一次性導入，匯入後資料固定不再同步

**存取方式：** 專人從業務王系統（https://braun.unidyna.com/ubmsys_customer/lists/）手動匯出 CSV，透過系統後台上傳匯入

**實作：**
- 提供 CSV 上傳匯入功能（一次性）
- 解析 CSV 欄位：流水號, 總店名稱, 分店名稱, 分店分類, 客戶名稱, 分店地址, 客戶電話, 執行人員, 階級, 建立時間
- 寫入 `crm_customers` collection，`source=business_kindom`, `status=lead`
- 地址欄位缺失座標 → 自動 geocode（若有整合 geocoding 服務）

**去重策略：**
- 以 `business_kindom_id`（流水號）為唯一鍵，避免重複匯入
- 匯入完成後自動與衛福部 `mohw` 記錄比對：若機構名稱 + 電話命中，標記 `duplicate_group`

### 4.3 Ragic CRM（source: `ragic`）— API 即時查詢

**存取方式：** 透過既有 `data_agent/ragic/` 的 Ragic API Client 查詢

**實作原則：**
- Ragic 資料不寫入 `crm_customers`，直接透過 Data Agent API 即時查詢
- Rust API Gateway 提供代理端點 `/api/v1/crm/customers/ragic`，轉發至 `unified_agents` 的 Ragic Data Agent
- 前端在載入「客戶總覽」時，分別查詢：
  1. `GET /api/v1/crm/customers` → 衛福部 + 業務王（ArangoDB）
  2. `GET /api/v1/crm/customers/ragic` → Ragic 既有客戶（API 代理）
- 前端合併兩組資料後統一呈現

**Ragic 客戶表單（CFG10_VENDOR 交易對象(客戶/供應商)）：**

| Ragic 欄位 ID | Ragic 欄位名 | 對應 API 欄位 | 類型 |
|---------------|-------------|--------------|------|
| 1015578 | 交易對象全稱 | `name` | string |
| 1015579 | 交易對象簡稱 | `name_short` | string |
| 1015577 | 交易對象編碼 | `code` | string |
| 1019926 | 客戶屬性 | `customer_attr` | string |
| 1015626 | 交易狀態 | `transaction_status` | string |
| 1015589 | 負責人 | `contact_person` | string |
| 1015611 | 部門/職稱 | `contact_title` | string |
| 1015598 | 是否為客戶 | `is_customer` | boolean |
| 1019116 | 客戶名稱 | `customer_name` | string |
| 1019117 | 統一編號 | `tax_id` | string |

> **Ragic 配置**：API Key 與 Database 參數存放於 `system_params`（ArangoDB），keys: `ragic.api_key` / `ragic.database` / `ragic.server_prefix`。環境變數備援：`RAGIC_API_KEY` / `RAGIC_MASTER_ACCOUNT` / `RAGIC_MASTER_SERVER`。
>
> 正式環境若 Ragic 帳號與程式碼預設值不同（如 code defaults: `2025shianyong`/`ap15`，實際: `2026carhouse`/`ap16`），以 system_params 儲存的值為準。

## 5. API 端點定義

### 5.1 `GET /api/v1/crm/customers`

查詢 ArangoDB 中的客戶資料（衛福部 + 業務王）。

```
Request Query Parameters:
  source?       string    — 篩選來源：mohw | business_kindom
  status?       string    — 篩選狀態：potential | lead | customer
  city?         string    — 篩選縣市
  district?     string    — 篩選區
  abc_grade?    string    — 篩選 ABC 分級
  q?            string    — 全文搜尋（name / phone / address）
  page?         number    — 分頁，預設 1
  page_size?    number    — 每頁筆數，預設 50
  bbox?         string    — 地圖邊界框篩選 "sw_lat,sw_lng,ne_lat,ne_lng"

Response:
{
  "data": [ CustomerObject ],
  "pagination": {
    "page": 1,
    "page_size": 50,
    "total": 31400,
    "total_pages": 628
  },
  "summary": {
    "total": 31400,
    "by_source": { "mohw": 31000, "business_kindom": 400 },
    "by_status": { "potential": 31000, "lead": 400 }
  }
}
```

### 5.2 `GET /api/v1/crm/customers/ragic`

代理查詢 Ragic API 的既有客戶資料（透通轉發）。

```
Request Query Parameters:
  q?            string    — 搜尋關鍵字（轉發至 Ragic Data Agent）
  page?         number    — 分頁
  page_size?    number    — 每頁筆數

Response: RagicQueryResult（由 data_agent/ragic 定義的格式）
```

### 5.3 `GET /api/v1/crm/customers/map`

地圖專用端點，合併三源資料為統一格式供 Leaflet 直接渲染。

```
Request Query Parameters:
  bbox?         string    — "sw_lat,sw_lng,ne_lat,ne_lng"
  source?       string    — mohw | business_kindom | ragic
  status?       string    — potential | lead | customer
  abc_grade?    string    — A | B | C | E
  city?         string    — 縣市

Response:
{
  "markers": [
    {
      "id": "mohw_1S1500012",
      "source": "mohw",
      "status": "potential",
      "name": "機構名稱",
      "lat": 22.9874,
      "lng": 120.2114,
      "color": "#52c41a",       // 客戶端據此決定顏色
      "abc_grade": "B",
      "phone": "06-2143510",
      "address": "臺南市東區..."
    }
  ],
  "summary": {
    "total": 31400,
    "in_viewport": 342,
    "by_source": { "mohw": 300, "business_kindom": 30, "ragic": 12 }
  }
}
```

> **顏色規範：**
> - 🟢 `#52c41a` (green-6) — `source=mohw`、`status=potential`
> - 🟡 `#fadb14` (yellow-6) — `source=business_kindom`、`status=lead`
> - 🔵 `#1677ff` (blue-5) — `source=ragic`、`status=customer`
> - ⚪ `#d9d9d9` (gray-5) — `status=merged`

### 5.4 `PATCH /api/v1/crm/customers/:key`

更新單筆客戶資料（人工覆核、狀態變更、標籤修改等）。

```
Request Body (partial):
{
  "status": "customer",
  "abc_grade": "A",
  "sales_rep": "業務員姓名",
  "tags": ["重點客戶", "已拜訪"],
  "last_contact_at": "2026-06-13T10:00:00",
  "last_contact_note": "已初步洽談..."
}
```

### 5.5 `POST /api/v1/crm/customers/merge`

手動合併多筆記錄（人工確認去重）。

```
Request Body:
{
  "primary_key": "mohw_1S1500012",        // 保留的主記錄 _key
  "merge_keys": ["bk_6336", "ragic_101"], // 被合併的記錄 _key
  "reason": "同一機構，不同來源"             // 合併原因
}
```

### 5.6 `POST /api/v1/crm/customers/import/business-kindom`

業務王 CSV 一次性匯入端點（僅首次導入使用，不支援增量排程）。

```
Request: multipart/form-data (CSV file)
Response:
{
  "imported": 420,
  "updated": 15,
  "skipped": 3,
  "errors": [],
  "batch_id": "bk_import_20260613_001"
}
```

### 6.2 Marker 顏色規則（前端實作）

```typescript
function getMarkerColor(source: string, status: string): string {
  if (status === 'merged') return '#d9d9d9';
  switch (source) {
    case 'mohw':            return '#52c41a'; // 綠色
    case 'business_kindom': return '#fadb14'; // 黃色
    case 'ragic':           return '#1677ff'; // 藍色
    default:                return '#bfbfbf';
  }
}
```

## 7. 去重比對策略

### 7.1 比對層級

```
第一層：來源內部唯一鍵比對
  衛福部: mohw_id
  業務王: business_kindom_id
  Ragic:  (不寫入 DB，無需比對)

第二層：跨源機構名稱 + 電話比對
  名稱正規化（去除「財團法人」、「社團法人」等前綴）
  電話正規化（去除 hyphen、空格）
  Similarity Score = weighted avg(名稱相似度, 電話相似度)
  Threshold > 0.85 → 自動建議合併
  0.7 ~ 0.85 → 人工確認

第三層：人工確認
  後台提供「待確認合併」清單
  一鍵確認合併（POST /merge）
```

### 7.2 比對觸發時機

| 觸發時機 | 動作 | 備註 |
|---------|------|------|
| 衛福部 CSV 更新匯入後 | 自動執行比對（與既有的 business_kindom 記錄） | 每次衛福部資料更新時觸發 |
| 業務王首次/重新匯入後 | 自動執行比對（與既有的 mohw 記錄） | 一次性匯入後執行一次 |

## 9. 風險與注意事項

| 風險 | 說明 | 緩解方式 |
|------|------|---------|
| 衛福部 CSV 格式異動 | 欄位增減或名稱改變可能導致匯入失敗 | 事先定義欄位映射，匯入時做欄位驗證，異常時告警 |
| 業務王資料為一次性匯入 | 匯入後如果業務王有新客戶資料，需手動補匯 | 一次性為設計決定，後續如有增量需求可重啟匯入流程 |
| 衛福部 31K 筆地圖渲染效能 | 全量顯示 Leaflet 卡頓 | 使用 MarkerCluster 分群 + bbox 過濾 |
| 三源資料地址格式不一致 | 比對準確率偏低 | 地址正規化前處理，人工覆核降低誤判 |
| Ragic API 變更 | API 端點或 auth 方式異動 | Data Agent 已有封裝，異動時只需修改 client.py |
