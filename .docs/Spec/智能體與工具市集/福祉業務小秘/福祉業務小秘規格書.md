## 1. Agent 定義

### 1.1 基本資訊

| 項目 | 內容 |
|:----|:----|
| **名稱** | 福祉業務小秘（Welfare Business Secretary） |
| **Agent Key** | `welfare_secretary` |
| **類型** | BPA（Business Process Agent） |
| **Endpoint** | `/welfare-secretary/chat`（掛載於 unified_agents :8011） |
| **程式碼位置** | `ai-services/bpa/welfare_secretary/` |
| **對應模型** | `qwen3:latest`（Ollama）／依 `model_providers` 動態解析 |
| **狀態** | `active` |

### 1.2 雙場景定義

福祉業務小秘同時服務兩種使用者角色，透過請求來源分流（`source=customer | internal`）：

| | 場景一：客戶端 LINE Bot | 場景二：內部工作助理 |
|---|---|---|
| **使用者** | 客戶（外部） | 業務人員（內部） |
| **互動管道** | 客戶個人 LINE → 福祉業務小秘官方 LINE 帳號 | 業務個人 LINE / 網頁後台 → 福祉業務小秘 |
| **加入方式** | 業務分享官方 LINE 給客戶加入好友 | 業務直接開啟聊天或後台 |
| **資訊權限** | ⛔ 不可接觸 ERP 明細（金額、數量、成本） | ✅ 可查詢 ERP / CRM 完整資料 |
| **互動發起** | 客戶主動發訊 | 業務主動發訊或系統排程觸發 |
| **自主性** | 有限度：僅回覆授權範圍，機密婉轉拒答 | 較高：可執行業務操作 |

### 1.3 設計目標

- 一個 Agent 服務所有業務員，不需為每人部署獨立 Agent
- 資料按業務員隔離（客戶、對話、Timeline）
- 平台抽象化：新增平台不影響核心路由邏輯
- 情境感知：根據使用者身份動態調整 persona 與權限

## 2. 系統架構

### 2.1 請求流程

```
LINE 使用者（客戶或業務）
     │
     ▼
LINE Platform（Messaging API）
     │ webhook
     ▼
Cloudflare Tunnel → Rust API Gateway (:6500)
     │ proxy（passthrough x-line-signature）
     ▼
unified_agents webhook (:8011)
  POST /api/v1/webhook/line/{channel_key}
     │
     ├── 查 channels 集合 → channel_key → linked_agent_key="welfare_secretary"
     ├── 驗證 x-line-signature
     ├── 建立 session_id：line:{channel_key}:{user_id}
     └── POST /welfare-secretary/chat
           │
           ▼
     router.py — 統一入口
           │
           ├── resolve_identity(session_id, channel_key)
           │     └── 查 channels → business_user_key → business_users → persona_config
           │
           ├── build_persona_prompt(identity)
           │     └── 動態組合 system prompt（姓名、區域、專業領域、簽名檔）
           │
           ├── source == "customer" ──→ customer_router.py
           │     ├── intent_classifier（rule-based 關鍵字 + intent_catalog）
           │     ├── L3/L4 rule-based 攔截（不經 LLM）
           │     ├── greeting → greeting_engine skill
           │     ├── greeting_image → image_processor skill
           │     ├── faq_question → knowledge_agent skill（⚠️ 未接線）
           │     ├── timeline_query → timeline_engine skill (level=summary)
           │     ├── confidential_q → customer_safe_reply + business_notification
           │     ├── business_card → image_processor skill (mode=card)
           │     └── unclear → customer_safe_reply skill
           │
           └── source == "internal" ──→ internal_router.py
                 ├── intent_classifier（關鍵字 + intent_catalog）
                 ├── erp_query → Data Agent (NL2SQL)
                 ├── crm_query → crm_query skill（⚠️ inline LLM 取代）
                 ├── greeting_customer → greeting_engine + push_engine（⚠️ push stub）
                 ├── broadcast → push_engine（⚠️ push stub）
                 ├── send_card_intro → contact_share skill（❌ 待新建）
                 ├── card_to_contact → image_processor skill (mode=card, scene=internal)
                 ├── market_subscribe → market_intel handoff（❌ 待新建）
                 ├── schedule_visit → visit_plan skill（⚠️ Phase 2 stub）
                 ├── timeline_full → timeline_engine skill (level=full)
                 ├── timeline_write → timeline_engine skill (action=write)
                 └── ragic_sync → ragic_timeline_poller skill（⚠️ 獨立執行）
```

### 2.2 頻道身份解析流程

```
session_id = "line:ch_abc123:Uxxxxxxxx"
     │
     ├── split(":") → channel_key = "ch_abc123", line_user_id = "Uxxxxxxxx"
     │
     ├── 查 channels 集合
     │     FOR c IN channels FILTER c._key == "ch_abc123" RETURN c
     │     → { business_user_key: "sales_001", role: "業務員", config: {...} }
     │
     ├── 查 business_users 集合
     │     FOR u IN business_users FILTER u._key == "sales_001" RETURN u
     │     → { name: "王大明", region: "北區", persona_config: { ... } }
     │
     └── 組合 persona
           → "你現在是王大明的個人業務助理。角色：業務員。負責區域：北區。..."
```

```
                   ┌──────────────────────────────────────┐

                   └──────────┬───────────────┬─────────────┘
                              │               │

              ┌──────────────────┐  ┌──────────────────┐
```

### 3.3 Trust Tier 定義

| Tier | 定義 | 對應操作 |
|:----:|:-----|:---------|
| **T1** | 公開資料 | 可任意回覆，無安全限制 |
| **T2** | 客戶授權資料 | 需經身份驗證，限本人查詢 |
| **T3** | 業務員權限資料 | 需通過 channel 身份解析，限所屬業務員 |
| **T4** | 敏感操作 | 需人工確認或 rule-based 攔截（不經 LLM） |

### 3.4 意圖分類機制

| 項目 | customer_router.py | internal_router.py |
|:-----|:-------------------|:-------------------|
| **分類方式** | rule-based 關鍵字優先 → LLM 補償（低溫 0.1） | 關鍵字快速匹配 → intent_catalog 比對 |
| **比對來源** | `intent_catalog` collection + L3/L4 關鍵字黑名單 | `intent_catalog` collection |
| **L3/L4 攔截** | rule-based（不經 LLM，防 jailbreak） | 無需攔截 |
| **fallback** | `customer_safe_reply` skill（LLM + L0-L4 規則） | LLM 生成（完整權限） |

### 3.5 資訊分級規則（場景一）

| 分級 | 定義 | 範例 | 可否回覆 |
|:----:|:-----|:-----|:--------:|
| L0 | 公開資訊 | 產品介紹、服務項目、營業時間 | ✅ 可直接回覆 |
| L1 | FAQ | 常見問題、使用說明 | ✅ Knowledge Agent |
| L2 | 互動摘要 | Timeline 時間／類型／摘要 | ✅ 僅摘要，無明細 |
| L3 | 機密明細 | 報價金額、訂單成本、合約條款 | ❌ 婉轉拒答 → 通知業務 |
| L4 | 內部操作 | 下單、改單、取消訂單 | ❌ 婉轉拒答 → 通知業務 |

### 4.2 各技能詳細說明

```
  │ 組長        │ 組長             │
  │ 教授/博士   │ 教授/博士        │
  │ 先生        │ 先生             │
```

## 7. Handoff 關係

### 7.1 Handoff 模型

福祉業務小秘採用 **tail-call handoff** 模型：當意圖需交由其他 Agent 處理時，福祉業務小秘釋放 agent frame，由目標 Agent 直接回覆使用者，不回傳至福祉業務小秘。

### 7.2 Handoff 到其他 Agent

| 目標 Agent | 觸發意圖 | 傳遞資料 | 說明 |
|:-----------|:---------|:---------|:-----|
| **訂單小秘** (`order_secretary`) | 客戶要求下單、查詢訂單明細（L3/L4 情境中若已確認授權） | `session_id`, `message`, `customer_id`, `channel_key` | 客戶意圖 `confidential_q` 婉轉拒答後，若客戶仍堅持需要訂單操作，經業務授權後 handoff |
| **市場觀察助手** (`market_intel`, A02) | `market_subscribe` 訂閱市場快報 | `business_key`, `industry_tags`, `frequency`, `channels` | 福祉業務小秘僅建立訂閱記錄，實際市場資訊產生由 A02 Celery task 執行 |

### 7.3 Handoff 到福祉業務小秘

| 來源 | 觸發方式 | 傳遞資料 | 說明 |
|:-----|:---------|:---------|:-----|
| **unified_agents LINE webhook** | `POST /welfare-secretary/chat` | `session_id`, `message`, `channel_key`, `attachment` | LINE webhook.py 解析 channel 後呼叫 |
| **Rust API Gateway** | `POST /api/v1/bpa/welfare-secretary/*` | 同上 + `source` 標記 | 內部 API Token 認證後轉發 |
| **內部排程器** (`scheduler.py`) | `POST /welfare-secretary/timeline/write` | `customer_id`, `event` | Ragic 輪巡、自動問候排程等背景任務 |

### 7.4 session_id 格式與路由

```
line:{channel_key}:{user_id}              → 個人 1:1 對話
line:group:{channel_key}:{group_id}:{user_id}  → 群組對話
line:room:{channel_key}:{room_id}:{user_id}    → 聊天室對話

internal:{business_user_key}:{session_uuid}    → 內部 API 呼叫
```

### 7.5 Handoff 流程範例

```
客戶（透過 LINE）：「我想看報價單的明細」
    │
    ▼
福祉業務小秘 customer_router：
  → intent=confidential_q（L3/L4 攔截）
  → 婉轉拒答：「已轉達業務，將由業務直接回覆」
  → business_notification 通知業務
    │
    ▼
業務（收到通知後）：「客戶要看報價單#Q-2026-0089」
    │
    ▼
福祉業務小秘 internal_router：
  → intent=erp_query
  → handoff to Data Agent（NL2SQL）
  → Data Agent 直接回覆業務查詢結果
```

## 9. 影像處理管道（Image Processing Pipeline）

### 9.1 概述

影像處理管道負責處理兩個場景中所有圖片訊息（LINE 傳送的圖片），根據圖片類型分流至不同處理邏輯。底層重用 `shared/multimedia.py` 的 `analyze_image()` 與 `qwen3-vl:latest` 多模態模型。

### 9.2 流程

```
客戶/業務傳送圖片（LINE）
    │
    ▼
LINE Webhook → router.py 分流
    │
    ▼
image_processor.py (skill)
    │
    ├── 1. classify(image)
    │    │  prompt: "這張圖片是「問候」、「名片」還是「其他」？只回傳一個詞。"
    │    │  用 qwen3-vl 快速分類
    │    │
    │    ├── "greeting" ──→ handle_greeting()
    │    │
    │    ├── "business_card" ──→ handle_business_card()
    │    │
    │    └── "other" ──→ handle_other()
    │
    ├── 2. 所有路徑共用：
    │    ├── SeaweedFS 備份（重用 shared/multimedia.upload_to_seaweedfs）
    │    └── 寫入 customer_timelines
    │
    └── 3. 回傳結果給 router → LINE 回覆
```

### 9.3 三種處理邏輯

#### handle_greeting — 問候圖片處理

```
輸入：客戶傳送的問候圖片（節日賀卡、早安圖等）
流程：
  1. analyze_image(content, prompt="請描述這張問候圖片的風格與氛圍")
  2. 將描述餵給 LLM（同一個 qwen3-vl）：
     prompt="根據以上描述，以{{客戶名稱}}的名義，生成一個溫暖禮貌的問候回覆"
  3. 回覆給客戶
  4. 寫入 timeline：event_type="greeting_received"
```

#### handle_business_card — 名片處理

```
輸入：客戶或業務傳送的名片圖片
流程：
  1. analyze_image(content, prompt="從這張名片提取 JSON：name, company, title, phone, email, address")
  2. 後處理驗證：json.loads() → 檢查 name/phone/company 至少一項不為 null
  3. 分流（根據來源）：
     ┌─ 場景一（客戶端）：→ pending_contacts（status: pending）
     │                     回覆「已收到名片，將轉交業務同仁確認後建檔」
     └─ 場景二（業務端）：→ crm_contacts 直接寫入（status: active）
                          回覆「名片已建檔完成」
  4. 寫入 timeline
```

#### handle_other — 其他圖片摘要

```
輸入：非問候非名片的圖片（產品照片、文件翻拍、場景照等）
流程：
  1. analyze_image(content, default prompt)
  2. 生成圖片摘要
  3. 回覆摘要給發送者
  4. 寫入 timeline：event_type="image_shared"
```

## 10. Platform Adapter 抽象層

### 10.1 動機

支援多個業務員同時使用，每個業務員有自己的 LINE 頻道，且未來可能擴展至 DingTalk、WhatsApp、WeCom 等其他平台。

### 10.2 帳號 ↔ 頻道 ↔ 客戶 關係

```
AIBox 使用者（accounts 管理）
  │
  ├── 王業務 (user_key: "sales_001", role: "business")
  │     └── LINE 頻道 (channels._key: "ch_a", platform: "line")
  │           ├── 客戶 A-001（陳董）→ crm_contacts.owner_key = "sales_001"
  │           ├── 客戶 A-002（林經理）→ crm_contacts.owner_key = "sales_001"
  │           └── pending_contacts.owner_key = "sales_001"
  │
  ├── 林業務 (user_key: "sales_002", role: "business")
  │     └── LINE 頻道 (channels._key: "ch_b", platform: "line")
  │           └── 客戶 B-001（張老闆）→ crm_contacts.owner_key = "sales_002"
  │
  └── Admin (user_key: "admin", role: "admin")
        └── 可管理所有頻道設定，但看不到對話內容
```

### 10.3 PlatformMessage 統一模型

```python
@dataclass
class PlatformMessage:
    platform: str            # "line" | "dingtalk" | "whatsapp" | "wecom"
    channel_key: str         # channels._key
    business_user_key: str   # 綁定哪個業務員
    sender_id: str           # 平台使用者 ID
    sender_name: str         # 平台使用者名稱
    content: str             # 統一文字內容
    content_type: str        # "text" | "image" | "file" | ...
    raw: dict                # 原始 payload（給 adapter 自己用）
```

### 10.4 PlatformAdapter 介面

```python
class PlatformAdapter(ABC):
    @abstractmethod
    async def parse_webhook(self, raw: dict, channel: dict) -> PlatformMessage:
        """將平台 webhook payload 轉為統一訊息"""

    @abstractmethod
    async def send_message(self, channel: dict, recipient_id: str, content: dict) -> bool:
        """透過平台 API 發送訊息"""

    @abstractmethod
    async def get_user_profile(self, channel: dict, user_id: str) -> dict:
        """取得使用者基本資料"""
```

### 10.5 Webhook 路由

```
POST /api/v1/webhook/line/{channel_key}
    │
    ├── 查 channels 集合 → 取得 platform + config
    ├── 根據 platform 選擇 adapter
    │     ├── "line" → LINEAdapter.parse_webhook()
    │     ├── "dingtalk" → DingTalkAdapter.parse_webhook()（未來）
    │     └── ...
    ├── 轉為 PlatformMessage
    └── 送入 router.classify_and_route(msg)
```

## 12. 潛在風險與注意事項

| 風險項目 | 說明 | 緩解措施 |
|:---------|:-----|:---------|
| ERP API 規格未明 | 影響 Ragic 輪巡的 adapter 開發 | 先以現有 Ragic 表結構實作，保留 adapter 抽象層 |
| 資訊分級誤判 | intent_classifier 將 L3/L4 誤判為 L0/L1 | rule-based 關鍵字攔截作為最後防線（不經 LLM） |
| LINE 官方帳號申請審核 | 每位業務員需要 LINE OA，審核時程不可控 | 先以一個 OA 試行，通過後再擴充 |
| LINE Messaging API 群發頻率限制 | Free plan 僅 500 則/月 | 確認商業方案或分批發送 |
| OCR 準確率 | qwen3-vl 對中日英混合名片辨識率可能不足 | 場景一 pending_contacts 機制讓業務確認後才建檔 |
| 地圖 API 成本 | Google Maps Distance Matrix API 為付費服務 | 評估免費替代方案（OSRM、GraphHopper） |
| Webhook 回應時限 | LINE 要求 5 秒內回應 HTTP 200 | webhook.py 先回覆 HTTP 200，非同步處理後 push_message |
| 簽名驗證 | 每個 channel 有獨立 channel_secret | 既有實作已支援 channel 對應 secret 驗證 |
| Token 管理 | access_token 有有效期 | 需實作 token 自動更新機制 |
