# NL → Ragic 資料查詢系統規劃書

> **架構決策（2026-04-13）**：已確定採用 **B+C 混合架構**（兩階段 Tool-Calling + Pandas/DuckDB）。
> 詳細遷移計劃及三階段迭代路線圖見 [遷移計劃及迭代規劃](./遷移計劃及迭代規劃.md)。

## 0. 背景與問題定位

### 0.1 為什麼不是 Text-to-SQL

SQL 是**聲明式**查詢語言，資料庫引擎負責執行规划與優化：

```sql
SELECT a.name, b.amount
FROM orders a
JOIN suppliers b ON a.supplier_id = b.id
WHERE b.status = 'active' AND a.date >= '2026-03-01'
```

**Text-to-SQL 的核心挑戰**是：
- 解析 SQL 語法（SELECT、JOIN、WHERE...）
- 對應到真實資料庫的 Schema（table name、column name）
- 處理複雜語法（NESTED SELECT、GROUP BY、HAVING...）

Ragic API 是**程序式 REST API**，查詢能力極其有限：

```
GET /{account}/{table_path}/{sheet_index}
    ?api
    &naming=EID
    &where=field_id,operator,value
    &where=field_id,operator,value   ← 多重篩選（AND邏輯）
    &order=field_id,ASC|DESC
    &limit=offset,count
    &subtables=0
```

**沒有 JOIN、沒有子查詢、沒有聚合**。所有複雜邏輯必須在客戶端實現。

---

**262 張 Ragic 表（不含 SAP 的 16 張）**，涵蓋採購、進銷存、庫存、生產、CRM、HR、ISO 表單等模組。

因此，NL → Ragic 的核心挑戰**不是語法解析**，而是：

> **將商業意圖翻譯為「一系列簡單 API 呼叫 + 客戶端合併」**

---

### 0.2 自然語言查詢的本質

使用者的自然語言蘊含以下資訊：

| 資訊類型 | 範例 | 電腦需要翻譯為 |
|-----------|------|----------------|
| **目標實體** | 「供應商」「進貨單」 | 262 張表中的哪一張？ |
| **篩選條件** | 「2026年3月」「已完成的」 | `where` 參數（field_id + operator + value）|
| **時間範圍** | 「這個月」「近一週」 | 日期區間（gte + lte）|
| **歸屬關係** | 「統一企業的進貨」 | FK 鏈（誰的？→ 跨錶查詢）|
| **排序分頁** | 「最新10筆」「最貴的前三名」 | `order` + `limit` |
| **輸出格式** | 「匯出成Excel」「給我CSV」 | response 格式轉換 |

## 1. 五大子問題框架

NL → Ragic 不是單一問題，而是五個各自獨立的子問題：

```
使用者輸入：「2026年3月供應商統一企業的進貨記錄」

         ┌─────────────────────────────────────────────────┐
         │           1. 表格選取 (Table Selection)           │
         │  「進貨記錄」→ 進貨明細表 (purchase-order/3)       │
         │  「供應商」→ 交易對象表 (configuration-file/10)    │
         └────────────────────────┬──────────────────────────┘
                                  │
         ┌────────────────────────▼──────────────────────────┐
         │         2. 欄位對應 (Field Mapping)               │
         │  「統一企業」→ 1015578 (交易對象全稱)             │
         │  「2026年3月」→ 1015600 (進貨日期)                │
         └────────────────────────┬──────────────────────────┘
                                  │
         ┌────────────────────────▼──────────────────────────┐
         │       3. 運算子推斷 (Operator Inference)           │
         │  「統一企業的」(從屬)→ lookup/eq                   │
         │  「3月份」(區間)→ gte + lte                       │
         └────────────────────────┬──────────────────────────┘
                                  │
         ┌────────────────────────▼──────────────────────────┐
         │        4. 取值格式化 (Value Formatting)            │
         │  「2026年3月」→ (2026/03/01, 2026/03/31)         │

         └────────────────────────┬──────────────────────────┘

         ┌────────────────────────▼──────────────────────────┐
         │        5. 關係圖遍歷 (Graph Traversal)            │
         │  進貨明細.供應商 → 交易對象.ID (FK)               │
         │  需要知道如何串接多表查詢                           │
         └─────────────────────────────────────────────────┘
```

### 3.1 Intent Router（意圖分類器）

**職責**：判斷 NL 屬於哪種查詢模式

**Prompt 設計**：

```
你是 Ragic 資料查詢的意圖分類器。

【查詢模式定義】
simple:       單表 + 單一篩選條件（where x eq y）
multi_filter: 單表 + 多重篩選條件（where x eq y AND where z gt w）
cross_table:  多表 + FK 串接（查 A 表的結果用於查 B 表）
aggregate:    目前不支援，請回傳 unsupported

【額外資訊】

【使用者輸入】
{user_query}

【輸出】
```

### 3.2 Query Planner（查詢規劃器）

**職責**：根據意圖，生成多步查詢計劃

**QueryPlan 結構**：

```python
class QueryPlanStep(BaseModel):
    step_index: int
    table_key: str                          # e.g., "configuration-file/10"
    table_name: str                         # e.g., "交易對象(客戶/供應商)"
    where: list[WhereCondition]            # 篩選條件
    order_field: str | None = None         # 排序欄位
    order_direction: str = "DESC"          # ASC | DESC
    limit: int = 1000
    # FK 擴展資訊
    linked_filter: LinkedFilter | None = None
    # 解析後的 value（用於後續步驟）
    resolved_values: dict[str, str] = {}    # field_name → resolved value

class WhereCondition(BaseModel):
    field_id: str                          # 欄位編號
    field_name: str                        # 原始欄位名稱（用於除錯）
    operator: str                          # eq | like | gt | gte | lt | lte
    raw_value: str                         # 使用者輸入的原始值
    formatted_value: str                   # 格式化後的值（日期、數值等）

class LinkedFilter(BaseModel):
    source_field: str                      # 本步驟中作為 FK 的欄位
    target_table: str                      # 目標表
    target_field: str                      # 目標表用於篩選的欄位
    resolve_value: str                     # 需要 resolve 的值（可能是 linked value）

class QueryPlan(BaseModel):
    steps: list[QueryPlanStep]
    total_timeout_s: float = 30.0
    mode: str                              # simple | multi_filter | cross_table
```

### 3.3 Field Mapper（欄位對應器）

**職責**：將 NL 中的欄位名稱對應到 Ragic 的 field_id

**挑戰**：
- 使用者說「供應商名稱」，但 Schema 中可能叫「交易對象全稱」「廠商名稱」
- 262 張表，每張表數十個欄位，總數千個欄位

**解決方案**：

```
Step 1: 候選欄位檢索
  使用 embedding search：
  - 查詢：「統一企業」
  - 目標：在所有 tables 中找「名稱」「交易對象」相關欄位
  - 在 Qdrant schema_store 中以 NL query 搜尋，取 top-k

Step 2: 候選驗證
  對候選欄位，檢查：
  - field_type 是否合理（text/select/number）
  - 在 Intent Store 中是否有已知的 pattern
  - table_key 是否符合意圖（如果已知 primary_table）

Step 3: 欄位別名對映表（新增）
  在 RagicTableSchema 中擴充 business_aliases：
  
  {
    "table_key": "configuration-file/10",
    "fields": {
      "1015578": {
        "name": "交易對象全稱",
        "business_aliases": [
          "供應商名稱", "廠商名稱", "供應商", "廠商",
          "統一企業", "客戶名稱", "供應商名稱"
        ]
      }
    }
  }
```

**Schema Enrichment（新增需求）**：

目前 `RagicFieldSchema.business_aliases` 是空陣列。需要：
1. 從 Ragic API 的「備註」欄位（Memo）自動提取
2. 從 Intent Store 的 nl_patterns 自動學習
3. 從使用者的反饋中持續擴充

### 3.4 Operator Resolver（運算子解析器）

**職責**：將 NL 中的比較意圖翻譯為 Ragic 運算子

**NL 意圖 → Ragic 運算子 對映表**：

| NL 關鍵字 | 運算子 | 範例 |
|-----------|--------|------|
| 是、等於、為、就是 | `eq` | 「狀態是已完成」 |
| 不是、不等於 | `ne`（不支援，用 `not eq`）| 「狀態不是已取消」 |
| 包含、有、含有 | `like` | 「名稱包含電腦」 |
| 開始於、前綴是 | `like`（正則）| 「編號開頭是 AG-」 |
| 結束於 | `like`（正則）| 「編號結尾是 -001」 |
| 大於、超過、以上 | `gt` / `gte` | 「金額大於1000」「數量至少100」 |
| 小於、未達、以下 | `lt` / `lte` | 「年齡小於18」 |
| 在...之間、介於 | `gte` + `lte` | 「數量在100到200之間」 |
| 是的、對、True | `eq` | 「已啟用是嗎」→ `eq,true` |
| 空的、沒有、空白 | `eq` | 「沒有備註」→ `eq,` |

**日期特殊處理（新增模組）**：

```python
class DateResolver:
    """將自然語言日期轉換為 Ragic 格式的日期區間"""

    PATTERNS = [
        # 絕對日期
        (r"(\d{4})年(\d{1,2})月(\d{1,2})日?", "date_full"),      # 2026年3月1日
        (r"(\d{4})/(\d{1,2})/(\d{1,2})", "date_full"),          # 2026/03/01
        (r"(\d{4})-(\d{1,2})-(\d{1,2})", "date_full"),          # 2026-03-01
        (r"(\d{4})年(\d{1,2})月", "date_month"),                # 2026年3月
        (r"(\d{4})/(\d{1,2})", "date_month"),                  # 2026/03
        #  相對日期
        (r"今天|今日", "relative_today"),
        (r"昨天", "relative_yesterday"),
        (r"明天", "relative_tomorrow"),
        (r"這個月|本月", "relative_this_month"),
        (r"上個月|上月", "relative_last_month"),
        (r"近(\d+)天", "relative_days"),                         # 近7天
        (r"近(\d+)週", "relative_weeks"),                       # 近2週
        (r"近(\d+)月", "relative_months"),                      # 近3月
    ]

    def resolve(self, nl_text: str) -> dict | None:
        """回傳 {start, end} 或 None（如果沒有日期）"""
```

### 3.5 Value Formatter（取值格式化器）

**職責**：將解析後的值格式化為 Ragic API 接受的格式

**處理規則**：

| 類型 | 輸入範例 | 輸出格式 |
|------|----------|----------|
| 日期 | 2026年3月1日 | 2026/03/01 |
| 日期 | 2026/03/01 | 2026/03/01 |
| 日期區間 | 2026年3月 | (2026/03/01, 2026/03/31) |
| 數值 | 1000 | 1000 |
| 數值 | 1,000.50 | 1000.50（移除逗號）|
| 布林 | 是、Yes、true、已啟用 | true_value（如「已啟用」→ 需查 Schema options）|
| 空值 | 空白、空、無 | 空字串 |

**Select 欄位選項解析**：

Ragic 的單選欄位（如「狀態」）有固定選項。當使用者說「已完成」，需要找到對應的選項值：

```
Schema:
  1015602: {
    "name": "進貨狀態",
    "field_type": "select",
    "options": ["待處理", "已核准", "已完成", "已取消"]
  }

當使用者說「已完成」→ 找到 options 中最接近的 → value = "已完成"
```

### 3.6 Linked Field Resolver（連結欄位解析器）

**職責**：將 Ragic API 回傳的 `(linked value)` 置換為實際值

**為什麼需要這個**：

Ragic API 回傳時，連結欄位顯示為 `(linked value)`：

```json
{
  "建檔代碼": "(linked value)",    // 這是 FK，但顯示為 "(linked value)"
  "員工姓名": "王大明",
  "建檔類型": "員工建檔"
}
```

當我們需要拿「建檔代碼」作為 FK 查其他表時，必須先 resolve 出實際值。

**處理流程**：

```
1. 偵測：掃描所有回傳 record，找出值為 "(linked value)" 的欄位
2. 查 Graph：根據 table_key + field_name，找到該欄位連結到哪張目標表
3. 提取 KEY：在同一筆 record 中，找到目標表的關鍵欄位值
4. 查詢目標表：用提取的值作為 filter，查詢目標表
5. 置換：將 "(linked value)" 替換為目標表查到的顯示值
```

**實作參考**：

```python
class LinkedFieldResolver:
    
    def __init__(self, ragic_client: RagicAPIClient, graph: RagicGraphQuery):
        self.client = ragic_client
        self.graph = graph
    
    async def resolve_record(self, record: dict, table_key: str) -> dict:
        """對單筆 record 進行 linked value resolution"""
        resolved = record.copy()
        
        for field_name, value in resolved.items():
            if value != "(linked value)":
                continue
            
            # 查 Graph，找到連結目標
            link_info = await self.graph.find_link_target(
                table_key, field_name
            )
            if link_info is None:
                continue
            
            # 從 record 中提取用於查詢的值
            # （通常是有實際值的相鄰欄位，如員工姓名）
            display_field = self._find_display_field(resolved, field_name)
            if display_field:
                # 查目標表，用顯示值當作 filter
                target_value = resolved.get(display_field)
                actual = await self._fetch_linked_value(
                    link_info.target_table,
                    link_info.target_field,
                    target_value
                )
                resolved[field_name] = actual
        
        return resolved
    
    async def resolve_step_results(
        self, records: list[dict], table_key: str
    ) -> list[dict]:
        return [await self.resolve_record(r, table_key) for r in records]
```

### 3.7 Result Merger（結果合併器）

**職責**：將多步查詢的結果根據 FK 關係合併

**現有 `result_merger.py` 的限制**：

目前實作是簡單的 FK-based join。對於「一對多」關係（如統一企業有 N 筆進貨），合併後應為：

```json
[
  {
    "交易對象.建檔代碼": "AG-00001",
    "交易對象.交易對象全稱": "統一企業",
    "進貨明細[0].進貨日期": "2026/03/05",
    "進貨明細[0].進貨數量": "100",
    "進貨明細[1].進貨日期": "2026/03/15",
    "進貨明細[1].進貨數量": "200"
  }
]
```

**增強需求**：

| 問題 | 現有實作 | 需要改進 |

## 4. Ragic API 的根本限制

### 4.1 支援的功能

```
✅ GET 讀取（單表、篩選、排序、分頁）
✅ 多重 where（AND 邏輯）
✅ 子表格讀取（subtables=0|1）
✅ 系統欄位（info=true）
✅ 分頁（limit=offset,count）
```

### 4.2 不支援的功能

| 功能 | 替代方案 |
|------|----------|
| JOIN（跨表關聯）| 客戶端 chain + merge |
| 子查詢（nested SELECT）| 多步查詢 |
| 聚合（COUNT, SUM, AVG）| 客戶端計算 |
| GROUP BY | 客戶端分組 |
| HAVING | 客戶端過濾 |
| UNION | 多次查詢 + 合併 |
| DISTINCT | 客戶端去重 |
| ORDER BY 多欄位 | 客戶端二次排序 |
| OFFSET-only（無 LIMIT）| 固定大 LIMIT |

### 4.3 Ragic API URL 格式

```
https://{server_prefix}.ragic.com/{account}/{table_path}/{sheet_index}
    ?api
    &naming=EID                              # 使用欄位編號
    &where={field_id},{operator},{value}      # 篩選（可多重）
    &where={field_id},{operator},{value}
    &order={field_id},{ASC|DESC}             # 排序
    &limit={offset},{count}                  # 分頁
    &subtables=0                             # 是否包含子表格
    &info=true                               # 是否包含系統欄位
```

## 10. 驗證結果（2026-04-12 實作對照）

> 本章節記錄規劃書與現有程式碼的交叉驗證結果，標註所有已確認的差異與待修正事項。

### 10.1 ⚠️ MultiStepOrchestrator 與 RagicStepExecutor 介面不相容

**問題**：`multi_step_orchestrator.py` 定義了 `StepExecutorLike` Protocol：

```python
class StepExecutorLike(Protocol):
    async def execute(self, request: MultiStepQuery | StepResult) -> StepResult: ...
```

但 `step_executor.py` 的 `RagicStepExecutor` 實際簽名為：

```python
async def execute(self, step_index, table_name, table_key, query_params, account, timeout_s=15.0) -> StepResult
async def execute_dependent(self, step_index, table_name, table_key, fk_field_id, fk_values, account, timeout_s=15.0) -> StepResult
```

**影響**：無法直接將 `RagicStepExecutor` 注入 `MultiStepOrchestrator`。目前 `router_import.py` 有使用 orchestrator，需確認是否有中間 adapter 層。

**修正方案**（二選一）：
- **方案 A（推薦）**：建立 Adapter 類別，實作 `StepExecutorLike` Protocol，將 `MultiStepQuery`/`StepResult` 轉譯為 `RagicStepExecutor.execute()` / `execute_dependent()` 的呼叫。
- **方案 B**：修改 `MultiStepOrchestrator` 直接呼叫 `step_executor.execute(step_index, ...)` 與 `execute_dependent(...)`。

---

### 10.2 ⚠️ ResultMerger._build_relation_map key 映射 Bug

**問題**：`result_merger.py` 的 `merge()` 方法使用以下方式查找 FK 資訊：

```python
fk_info = rel_map.get((primary.table_name, dep_step.table_name))
```

但 `_build_relation_map()` 建立的 key 卻是：

```python
key = (rel.source_field, rel.target_table)  # ← 與 merge() 使用的 key 不一致
```

**影響**：FK join 永遠找不到對應關係，`merge()` 退化為簡單串接（prefix-only），無法正確合併多步查詢結果。

**修正方案**：將 `_build_relation_map()` 改為以 `(source_table, target_table)` 作為 key，使其與 `merge()` 的 lookup 一致。

## §12 三層錯誤處理框架

### 12.1 設計原則

NL→Ragic 查詢流程中的錯誤分為三個階段處理：

| 階段 | 時機 | 策略 |
|------|------|------|
| **前置驗證** | `router.py` 進入 `parse()` 之前 | 攔截無效輸入，回應澄清問題 |
| **意圖解析** | `nl_parser.py` 的 `parse()` 中 | 依信心分數分三級處理 |
| **後置錯誤** | `router.py` 查詢結果返回前 | 由友善訊息回應，說明可能原因 |

#### 標準回應協定 (Standard Response Protocol)

Data Agent 為無狀態代理，所有回應統一使用以下五區塊結構。前端根據 `status` 判斷要渲染哪個區塊，每個區塊 nullable — 只在相關情境下有值。

```json
{
  "code": 0,
  "status": "success | clarification_needed | error",
  "clarification": {
    "message": "查詢內容過短，請提供更詳細的描述",
    "suggestions": ["查詢上個月的進貨單", "列出所有採購訂單"]
  },
  "result": {
    "records": [{ "ragic_id": "1", "fields": { "1000001": "PO-2026-001" } }],
    "record_count": 50,
    "pagination": { "offset": 0, "limit": 1000, "returned_count": 50, "has_more": false },
    "field_labels": { "1000001": "採購單號" },
    "execution_time_ms": 123.4,
    "stats": {
      "total_fields": 12,
      "estimated_tokens": 4500
    }
  },
  "intent": {
    "intent_id": "list_erp_48",
    "score": 0.73,
    "confidence": "high",
    "action": "list",
    "table_key": "erp/48"
  },
  "post_error": {
    "error_code": 504,
    "raw_error": "Request timed out",
    "message": "查詢逾時，Ragic 伺服器回應較慢，請稍後再試"
  },
  "metadata": {
    "connection": "2025shianyong",
    "table_key": "erp/48",
    "output_format": "json",
    "query": "查詢上個月的進貨單",
    "translated_params": { "where": [...], "limit": 1000, "offset": 0 }
  }

```

#### 區塊填充規則

| status | clarification | result | intent | post_error | metadata |
|--------|--------------|--------|--------|-----------|----------|
| `success` | 中確信時填入提示 | ✅ 必填 | ✅ 必填 | 0 筆結果時填入 | ✅ 必填 |
| `clarification_needed` | ✅ 必填 | ✗ null | 有匹配時填入 | ✗ null | 有解析時填入 |
| `error` | ✗ null | ✗ null | 有匹配時填入 | ✅ 必填 | 有解析時填入 |

#### Python Model 定義

```python
class NLQueryResponse(BaseModel):
    code: int = 0
    status: str = "success"                          # success | clarification_needed | error
    clarification: Optional[NLClarification] = None
    result: Optional[NLResultSet] = None
    intent: Optional[NLIntentMatch] = None
    post_error: Optional[NLPostError] = None
    metadata: Optional[NLQueryMetadata] = None

class NLClarification(BaseModel):
    message: str
    suggestions: list[str] = []

    records: list[RagicRecord] = []
    record_count: int = 0
    pagination: RagicPagination
    field_labels: dict[str, str] = {}
    execution_time_ms: float = 0.0
    stats: Optional[NLResultStats] = None

    total_fields: int = 0
    estimated_tokens: int = 0                        # len(json.dumps(records)) // 4

class NLIntentMatch(BaseModel):
    intent_id: str
    score: float
    confidence: str = ""                             # high | medium | low
    action: str = ""
    table_key: str = ""

class NLPostError(BaseModel):
    error_code: int = 0
    raw_error: str = ""
    message: str = ""                                # 面向用戶的友善訊息

    table_key: str = ""
```

### 12.2 第一層：前置驗證 (Pre-Validation)

在 `router.py` 的 `nl_query()` endpoint 中，進入 `_nl_parser.parse()` 之前執行。

| 檢查 | 條件 | code | message |
|------|------|------|---------|
| 空查詢 | `len(query.strip()) == 0` | 1 | `"請輸入查詢內容"` |
| 過短 | `len(query.strip()) < 4` | 1 | `"查詢內容過短，請提供更詳細的描述"` |
| 無有效語句 | 不含 `[\u4e00-\u9fff]` 且不含 `[a-zA-Z]` | 1 | `"無法識別有效的查詢語句"` |

```python
# router.py — nl_query() 內，parse() 之前
import re

stripped = request.query.strip()
if len(stripped) == 0:
    return NLQueryResponse(code=1, message="請輸入查詢內容")
if len(stripped) < 4:
    return NLQueryResponse(code=1, message="查詢內容過短，請提供更詳細的描述")
if not re.search(r"[\u4e00-\u9fff]", stripped) and not re.search(r"[a-zA-Z]", stripped):
    return NLQueryResponse(code=1, message="無法識別有效的查詢語句")
```

### 12.3 第二層：意圖解析信心分級 (Intent Confidence Tiers)

在 `nl_parser.py` 中，根據 intent 向量匹配分數分三級：

| 等級 | 分數區間 | confidence 標籤 | 策略 |
|------|----------|----------------|------|
| 高確信 | ≥ 0.65 | `"high"` | Template 直接翻譯，正常執行 |
| 中確信 | 0.45 ~ 0.65 | `"medium"` | LLM 輔助翻譯，附提示訊息 |
| 低確信 | < 0.45 或無命中 | `"low"` | 不執行查詢，回應澄清問題 |

#### 閾值常數

```python
# nl_parser.py
CONFIDENCE_HIGH_THRESHOLD = 0.65   # 原 TEMPLATE_CONFIDENCE_THRESHOLD
CONFIDENCE_LOW_THRESHOLD = 0.45    # 低於此不執行查詢
```

#### ParseResult 擴充

```python
class ParseResult:
    __slots__ = (
        "intent_matched",
        "translated_params",
        "table_key",
        "parse_time_ms",
        "multi_table_hint",
        "confidence",           # ← "high" | "medium" | "low"
        "llm_fallback_failed",  # ← True if LLM 翻譯失敗
    )
```

#### 分級邏輯

```python
# nl_parser.py parse() 內
if matched_intent and match_score >= CONFIDENCE_HIGH_THRESHOLD:
    translated = self._translate_from_template(matched_intent, opts)
    confidence = "high"
    llm_failed = False
elif matched_intent and match_score >= CONFIDENCE_LOW_THRESHOLD:
    translated = await self._translate_via_llm(query, account, resolved_table_key, opts)
    confidence = "medium"
    llm_failed = (len(translated.where) == 0 and not translated.order_field)
else:
    translated = TranslatedParams(limit=opts.limit, naming="EID")
    confidence = "low"
    llm_failed = False
```

#### LLM Prompt 日期修復

`_build_llm_prompt()` 必須加入基準日期，避免「上個月」翻譯為錯誤年份：

```python
    return (
        "你是 RagicDataAgent 的查詢參數翻譯器。"
        "將使用者的自然語言轉換為 Ragic API 查詢參數。"
        f"\n【今天日期】{today}"
        f"{schema_section}"
        # ... 其餘不變
    )
```

### 12.4 第三層：後置錯誤處理 (Post-Execution)

在 `router.py` 查詢結果返回前，根據不同結果產生友善訊息：

#### 查詢成功但無資料

```python
if engine_result.record_count == 0:
    message = "查詢完成，但未找到符合條件的資料。可能原因：1. 該時段無相關記錄 2. 篩選條件過嚴"
```

#### RagicError 對照表

| 例外類型 | code | message |
|---------|------|---------|
| `RagicTimeoutError` | 504 | `"查詢逾時，Ragic 伺服器回應較慢，請稍後再試"` |
| `RagicAuthError` | 401 | `"API 金鑰已失效，請至系統設定更新 Ragic 連線資訊"` |
| `RagicForbiddenError` | 403 | `"權限不足，無法存取此 Ragic 表單"` |
| `RagicNotFoundError` | 404 | `"找不到對應的 Ragic 表單，請確認表單路徑是否正確"` |
| `RagicRateLimitError` | 429 | `"查詢頻率過高（Ragic 限制每秒 5 次），請稍候再試"` |
| 其他 `RagicError` | 502 | `"查詢過程中發生錯誤：{簡化描述}。請稍後重試"` |

#### 中確信附加提示

當 `confidence == "medium"` 時，在成功回傳中附加：

```python
message = f"系統推測您想查詢「{schema_name}」，若不正確請換方式描述"
```

#### 低確信攔截

當 `confidence == "low"` 時，不執行查詢，直接回傳：

```python

    code=5,
    message="無法理解您的查詢意圖，請嘗試更具體的描述，例如：「查詢上個月的進貨單」",
    confidence="low",
    data=NLQueryData(
        query=request.query,
        intent_matched=parsed.intent_matched,

```

### 12.5 Error Code 完整對照表

| code | 名稱 | 觸發條件 | 層級 |
|------|------|---------|------|
| 0 | 成功 | 查詢正常完成 | — |
| 1 | 前置驗證失敗 | 空查詢/過短/無有效語句 | 第一層 |
| 2 | NL 解析例外 | `parse()` 拋出未預期的 exception | 第二層 |
| 3 | 無法判斷表格 | 解析後 `table_key` 為空 | 第二層 |
| 4 | table_key 格式錯 | `table_key` 不符合 `tab/sheet` 格式 | 第二層 |
| 5 | 低確信攔截 | intent 分數 < 0.45，不執行查詢 | 第二層 |
| 401 | Auth 失敗 | Ragic API Key 無效或過期 | 第三層 |
| 403 | 權限不足 | Ragic 拒絕存取 | 第三層 |
| 404 | 資源不存在 | Ragic 表單不存在 | 第三層 |
| 429 | 頻率限制 | 超過 Ragic 5 req/s 限制 | 第三層 |
| 502 | 伺服器錯誤 | 其他 Ragic API 錯誤 | 第三層 |
| 504 | 逾時 | Ragic 請求超時 | 第三層 |

```typescript
  confidence: string;   // "high" | "medium" | "low"
  action: string;
  table_key: string;
}

interface RagicNLPostError {
  error_code: number;
  raw_error: string;

}

interface RagicNLQueryMetadata {
```

#### QueryPlayground UI 渲染規則

前端根據 `status` 決定渲染邏輯：

| status | 渲染 |
|--------|------|
| `success` | 顯示結果表格 + 意圖匹配 + 統計資訊（含 tokens 預估）|
| `clarification_needed` | 顯示 clarification.message + suggestions（可點擊帶入查詢框）|
| `error` | 顯示 post_error.message（紅色 Alert）|

統計區塊固定顯示：
- 執行時間 ms
- 結果筆數
- 預估 Tokens
- confidence 信心徽章（綠/橙/紅）
- 欄位數
