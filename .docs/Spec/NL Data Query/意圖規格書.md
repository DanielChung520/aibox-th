## 1. 概述

### 1.1 兩階段意圖匹配架構

NL 查詢採用兩階段動態架構：

```
使用者輸入 (NL)
    │
    ▼
[Phase 1: 選表]
Qdrant da_expressions 向量搜索
    │
    ├─► 信心度 > 門檻 ──► 取得 table_key
    └─► 信心度不足 ───► 進入澄清流程 (clarification_needed)
    │
    ▼
[Phase 1b: 推斷路由]
query_type_inferrer.py
    │
    ├─► 關鍵字 Regex 匹配
    ├─► da_tables.capabilities 交叉驗證
    └─► 決定 query_type + difficulty
    │
    ▼
[Phase 2: 路徑路由]
根據 query_type + difficulty 分發策略
```

### 1.2 三級 Schema 結構

| Collection | 用途 | 說明 |
|------------|------|------|
| `da_tables` | 表結構定義 | fields, capabilities, relationships |
| `da_expressions` | 表達角度 | 每表的 aliases + nl_examples |
| `da_intents` | 聚合意圖模板 | 跨表的複雜查詢模式 |

### 1.3 規模

| 指標 | 數量 |
|------|------|
| `da_tables` 總數 | 262 筆 |
| `da_expressions` 總數 | 1191 筆 |
| `da_intents` 總數 | 21 筆 |
| Qdrant 同步筆數 | 206 筆 |

## 3. 意圖匹配流程

### 3.1 選表流程 (Phase 1)

1. 使用者輸入 NL 查詢
2. 向量化查詢文本 (`embedding_text`)
3. Qdrant 向量搜索 `da_expressions` collection
4. 取得 top-k 候選表達角度
5. 信心度 > 門檻 → 取得 `table_key`
6. 信心度不足 → 回傳 `clarification_needed`

### 3.2 動態路由推斷 (Phase 1b)

`query_type_inferrer.py` 根據以下優先順序動態推斷：

1. **關鍵字正規表達式匹配**：
   - `aggregate`: 「總計」、「平均」、「最大」、「最小」、「統計」等
   - `time_series`: 「趨勢」、「按月」、「每日」等
   - `cross_table`: 「關聯」、「連同」等
2. **能力檢查**：檢查 `da_tables.capabilities` 是否支援推斷出的類型
3. **預設降級**：若無匹配，預設為 `simple_filter`

### 3.3 路徑路由 (Phase 2)

根據推斷的 `query_type` + `difficulty_level` 決定策略：

| 策略 | 觸發條件 | 說明 |
|------|----------|------|
| **TEMPLATE** | easy 難度 | Rule-based 翻譯，最快 (~0.8s) |
| **SMALL_LLM** | medium 難度 | 小模型輔助翻譯 (~45.8s) |
| **LARGE_LLM** | hard 難度 + aggregate | 大模型處理複雜查詢 |

## 4. 路由策略邏輯

### 4.1 策略矩陣

```
query_type = simple_filter:
  - difficulty = easy   → TEMPLATE (rule-based)
  - difficulty = medium → SMALL_LLM

query_type = aggregate:
  - difficulty = easy   → TEMPLATE (rule-based)
  - difficulty = medium → SMALL_LLM
  - difficulty = hard   → LARGE_LLM
```

### 4.2 Path A: Tool-Calling (TEMPLATE/SMALL_LLM)

利用 Ollama 的 `format` 參數做 JSON Schema 約束，確保 LLM **只能**輸出合法的 `field_id`：

```python
# Phase 2: 載入目標表 schema 後，建構 JSON Schema
tool_schema = intent.tool_schema  # 從意圖中取得

resp = ollama.generate(
    model=model,
    prompt=prompt,      # 含 field label 清單 + 使用者查詢
    format=tool_schema  # JSON Schema enum 硬約束
)
```

**幻覺防治**：`field_id` 的 `enum` 陣列只包含該表的合法欄位，LLM 無法捏造不存在的值。

### 4.3 Path B: Pandas/DuckDB (LARGE_LLM)

適用於 Ragic API 無法處理的複雜查詢（SUM/AVG/GROUP BY/JOIN）：

```
1. 意圖匹配 → 確定 query_type = aggregate / cross_table / time_series
2. Ragic API 撈全量資料（→ JSON）
3. 載入 DuckDB 記憶體表
4. LLM 生成 DuckDB SQL（欄位 enum 約束同 Path A）
5. DuckDB 本地執行 SQL
6. 回傳結果
```

### 4.4 執行時間分析

| 策略 | 數量 | 平均耗時 | 佔比 |
|------|------|----------|------|
| **TEMPLATE** | 168 | **0.8 秒** | 9% |
| **SMALL_LLM** | 32 | **45.8 秒** | 91% |

**瓶頸**：91% 的時間花在 SMALL_LLM 策略上（LLM 推理）。

### 5.2 Payload 欄位

|-------------|------|------|

| `difficulty_level` | `da_intents.difficulty_level` | 難度標記 |
| `name` | `da_intents.name` | 意圖名稱 |
| `description` | `da_intents.description` | 意圖描述 |
| `nl_examples` | `da_intents.nl_examples` | NL 範例句 |
| `tool_schema` | `da_intents.tool_schema` | JSON Schema 約束 |
| `status` | `da_intents.status` | 狀態 |

### 5.3 Embed Text 建構

```python
def _intent_to_embed_text(intent: dict) -> str:
    parts = list(intent.get("nl_examples", []))
    if intent.get("description"):
        parts.append(intent["description"])
    if intent.get("name"):
        parts.append(intent["name"].replace("_", " "))
    return " ".join(parts)
```

## 6. 同步機制

### 6.1 同步端點

| 端點 | 說明 |
|------|------|
| `POST /da/intent-rag/sync` | 同步 da_expressions 到 Qdrant |
| `POST /da/intent-rag/sync-intents` | 同步 da_intents 到 Qdrant |

### 6.2 同步流程

```
觸發方式：前端「同步到 Qdrant」按鈕
     │
     ▼
Python unified_agents (da_sync.py)
     │
     ├─ 1. fetch_intents_from_arango("da_intents")
     │      → AQL: FOR doc IN da_intents
     │
     ├─ 2. 對每筆意圖生成向量嵌入
     │      → Ollama /api/embed (model = bge-m3:latest)
     │
     ├─ 3. 清理 orphan intents
     │      → 刪除 Qdrant 中不存在於 ArangoDB 的 points
     │
     └─ 4. 批次 upsert 到 Qdrant
            → PUT /collections/da_intents/points
```

### 7.4 失敗案例（2 個）

| ID | 場景名稱 | 問題 |
|----|----------|------|
| FORMS4_13_search | 商機風險-關鍵字搜尋 | query_type 標註為 aggregate 但實際是 simple_filter |
| RAGICSALES_14_default | 合約管理 | 同上 |

**根本原因**：這兩個案例的意圖名稱中沒有「統計」等 aggregate 關鍵字，但意圖本身被標記為 aggregate。這是**資料標註問題**——意圖的 `nl_examples` 與 `query_type` 不匹配。

**建議修復方向**：
1. 修正 `da_expressions` 中這兩個意圖的 `nl_examples`，加入「統計」、「彙總」等關鍵字
2. 或修正 `query_type` 為 `simple_filter`（如果確實是簡單查詢）
