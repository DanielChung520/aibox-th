## 1. 概述

### 1.1 Data Agent 意圖的定位

Data Agent 意圖是「使用者自然語言查詢」與「資料查詢動作」之間的映射。與 Orchestrator 意圖（任務路由）和 Knowledge 意圖（知識庫檢索）不同，Data Agent 意圖聚焦於：

- **目標表選取**：262 張表中確定查詢對象
- **查詢類型分類**：簡單篩選 / 聚合 / 跨表 / 時間序列
- **參數約束**：透過 `tool_schema` 提供 JSON Schema enum 約束，防止 LLM 幻覺

### 1.2 規模

| 指標 | 數量 |
|------|------|
| Data Agent 意圖總數 | ~155 筆（intent_catalog 中 `agent_scope = "data_agent"`） |
| 覆蓋表數 | 262 張 |
| 每表平均意圖 | ~0.6（部分表無意圖，核心表有多筆） |

### 1.3 與共用基礎設施的邊界

| 層面 | 共用（意圖管理系統規格書） | DA 專屬（本文件） |
|------|--------------------------|-------------------|
| 儲存 | `intent_catalog` collection | DA 欄位定義（§2） |
| 向量索引 | scope-aware embed-sync API | `data_agent_intents` collection payload（§4） |
| CRUD API | `GET/POST/PUT/DELETE /api/v1/intents/catalog` | — |
| 匹配邏輯 | — | 三級信心度 + Path A/B 路由（§3） |
| Runtime Model | — | `RagicIntent` Pydantic model（§2.3） |

## 2. 意圖 Schema

### 2.1 ArangoDB `intent_catalog` 中的 DA 欄位

> 共用欄位（`_key`, `intent_id`, `agent_scope`, `name`, `description`, `status`, `priority`, `created_at`, `updated_at`, `updated_by`）見 [意圖管理系統規格書 §3.1](../意圖管理/意圖管理系統規格書.md#31-arangodb-intent_catalog-文件結構)。

#### 基礎欄位

| 欄位 | 類型 | 必填 | 說明 |
|------|------|------|------|
| `table_id` | string | ✅ | 正規化表單識別碼（如 `ERP_13`），與 Schema Graph 一致 |
| `sheet_key` | string | ✅ | Ragic sheet key（如 `1018457`） |
| `tables` | string[] | ✅ | 關聯表單列表（`table_id` 格式），支援多表 |
| `action` | string | — | 動作類型：`list` / `count` / `search` / `filter` |
| `group` | string | — | 業務群組（如 `採購-供應商`） |
| `intent_type` | string | — | 意圖類型：`filter` / `aggregate` / `join` / `time_series` |
| `generation_strategy` | string | — | SQL 生成策略：`template` / `small_llm` / `large_llm` / `tool_calling` |
| `sql_template` | string | — | AQL 模板（template 策略用） |
| `core_fields` | string[] | — | 核心欄位列表 |
| `nl_examples` | string[] | ✅ | 自然語言範例句（用於嵌入與匹配） |
| `nl_patterns` | string[] | — | 多語系 NL 樣板（自動生成用） |
| `example_sqls` | string[] | — | SQL 範例 |
| `filter_template` | object | — | 預設篩選條件（`{field_id, operator, value}`） |
| `api_template` | string | — | API URL 模板 |
| `bpa_domain_intent` | string | — | 對應的 BPA domain intent |

#### B+C 混合架構擴充欄位（v1.2.0）

> 以下欄位在迭代一（B+C 混合架構）中新增，向下相容，舊意圖可不填。

| 欄位 | 類型 | 必填 | 說明 | 用途 |
|------|------|------|------|------|
| `query_type` | string | ✅ | `simple_filter` / `aggregate` / `cross_table` / `time_series` | Path A/B 路由判斷 |
| `tool_schema` | object | — | LLM JSON Schema 約束（含 `field_id` enum 陣列） | Path A Tool-Calling |
| `involved_tables` | string[] | — | 跨表查詢涉及的所有 `table_id` | `cross_table` 類型必填 |
| `join_keys` | object[] | — | `[{source_table, source_field, target_table, target_field}]` | 跨表 JOIN FK 映射 |
| `expected_output` | object | — | 預期結構化輸出 | 迭代二訓練 label |
| `difficulty_level` | string | — | `easy` / `medium` / `hard` | 迭代二分層抽樣 |
| `golden_sql` | string | — | 標準 SQL 範例（DuckDB 方言） | 迭代二 Path B 訓練 |
| `test_cases` | object[] | — | `[{input, expected_output}]` | 自動化測試 |

#### 查詢路由規則

`query_type` 決定 NL 查詢走哪條路徑：

| query_type | 路由 | 機制 |
|------------|------|------|
| `simple_filter` | **Path A** Tool-Calling | Ollama `format` JSON Schema enum 約束 → Ragic API |
| `aggregate` | **Path B** Pandas/DuckDB | Ragic API 撈全量 → 本地 SQL 執行 |
| `cross_table` | **Path B** Pandas/DuckDB | 多表 JOIN |
| `time_series` | **Path B** Pandas/DuckDB | 時間序列分析 |

### 2.4 table_id 與 sheet_key 映射

映射來源為 ArangoDB `da_table_info_ragic` 集合（262 筆，100% 覆蓋率已驗證）：

```aql
  LET table_key = CONCAT(t.tab, "/", t.sheet_number)
  RETURN {
    table_key: table_key,       -- "erp/52"
    table_id:  t.table_id,      -- "ERP_13"
    sheet_key: t.sheet_key,     -- "1018457"
    table_name: t.table_name    -- "採購單"

```

## 3. 意圖匹配流程

### 3.1 三級信心度系統

NL Parser 使用三級信心度決定處理策略：

| 等級 | 分數閾值 | 處理方式 |
|------|---------|---------|
| **High** | ≥ 0.65 | 直接使用模板翻譯（最快） |
| **Medium** | 0.45–0.65 | 呼叫 Small LLM 輔助翻譯 |
| **Low** | < 0.45 | 回傳預設參數，請使用者釐清 |

> 閾值由 `system_params` 的 `intent.match_threshold`（Low）控制，High 門檻硬編碼在 `nl_parser.py`。

### 3.2 匹配流程圖（B+C 混合架構）

```
使用者輸入
    │
    ▼
RagicNLParser.parse()
    │
    ├─► IntentVectorStore.search() ──► Qdrant data_agent_intents
    │                                   │
    │                          ┌────────┘
    │                          ▼
    │                   top-3 候選意圖
    │                          │
    │              ┌───────────┼───────────┐
    │              ▼           ▼           ▼
    │           score≥0.65  0.45≤s<0.65  s<0.45
    │           (High)      (Medium)     (Low)
    │              │           │           │
    │              ▼           ▼           ▼
    │         template    LLM fallback  clarification
    │         translate    translate    _needed
    │              │           │           │
    └──────────────┴───────────┘           │
                    │                      │
                    ▼                      ▼
            query_type 判斷          回傳澄清問題
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
    simple_filter         aggregate /
         │               cross_table /
         ▼               time_series
    Path A:                    │
    Tool-Calling               ▼
    (JSON Schema          Path B:
     enum 約束             Pandas/DuckDB
     → Ragic API)         (Ragic API 撈全量
                           → 本地計算)
         │                     │
         └──────────┬──────────┘
                    ▼
              NLQueryResponse
```

### 3.3 Path A: Tool-Calling 核心機制

利用 Ollama 的 `format` 參數做 JSON Schema 約束，確保 LLM **只能**輸出合法的 `field_id`：

```python
# Phase 2: 載入目標表 schema 後，建構 JSON Schema
tool_schema = intent.tool_schema  # 從意圖中取得

resp = ollama.generate(
    model=model,
    prompt=prompt,      # 含 field label 清單 + 使用者查詢
    format=tool_schema  # JSON Schema enum 硬約束
)
```

**幻覺防治**：`field_id` 的 `enum` 陣列只包含該表的合法欄位，LLM 無法捏造不存在的值。

### 3.4 Path B: Pandas/DuckDB 機制

適用於 Ragic API 無法處理的複雜查詢（SUM/AVG/GROUP BY/JOIN）：

```
1. 意圖匹配 → 確定 query_type = aggregate / cross_table / time_series
2. Ragic API 撈全量資料（→ JSON）
3. 載入 DuckDB 記憶體表
4. LLM 生成 DuckDB SQL（欄位 enum 約束同 Path A）
5. DuckDB 本地執行 SQL
6. 回傳結果
```

### 3.5 語意不清處理

Data Agent 是**無狀態的被委派 Agent**。對於任何語意不清的查詢：

- 回傳 `clarification_needed` 類型回應
- 指出需要澄清的具體問題（如「請問您要查哪張表？」「請提供具體日期範圍」）
- 由前端 Orchestrator 負責指代消解與對話歷史管理

### 4.3 Embed Text 建構

```python
def _intent_to_embed_text(intent: dict) -> str:
    parts = list(intent.get("nl_patterns", []))
    if intent.get("description"):
        parts.append(intent["description"])
    parts.append(intent["intent_id"].replace("_", " "))
    return " ".join(parts)
```

> `nl_patterns` + `description` + `intent_id` 組成嵌入文本。`nl_examples` 目前**不**參與嵌入（預留迭代二訓練用）。

## 5. Embed-Sync 同步行為

### 5.1 同步端點

```
POST /intent-rag/data_agent/embed-sync
```

### 5.2 同步流程

```
觸發方式：前端「同步到 Qdrant」按鈕
     │
     ▼
Rust API (proxy_sync_qdrant)
     │
     ▼
Python Data Agent (embed-sync endpoint)
     │
     ├─ 1. fetch_intents_from_arango("data_agent")
     │      → AQL: FOR doc IN intent_catalog
     │        FILTER doc.agent_scope == "data_agent"
     │
     ├─ 2. 對每筆意圖生成向量嵌入
     │      → Ollama /api/embed (model = da.embedding_model)
     │
     ├─ 3. 重建 Qdrant collection
     │      → DELETE + PUT /collections/data_agent_intents
     │
     └─ 4. 批次寫入所有 points
            → PUT /collections/data_agent_intents/points
```

### 5.3 同步策略

目前採用**全量重建**策略（清除後重新寫入），原因：

- 意圖數量不大（< 200 筆），全量重建耗時 < 30 秒
- 避免增量同步的複雜度（刪除偵測、更新偵測）
- 嵌入向量在模型切換時需完整重新生成

未來若意圖數量超過 1000 筆，可考慮增量同步。

## 8. 迭代路線圖

### 8.1 B+C 混合架構（迭代一 — 進行中）

NL 查詢系統從簡單的意圖匹配升級為兩階段混合架構：

| 路徑 | 機制 | 適用場景 |
|------|------|---------|
| **Path A: Tool-Calling** | Ollama `format` JSON Schema enum 約束 | 簡單篩選（WHERE + ORDER + LIMIT） |
| **Path B: Pandas/DuckDB** | Ragic API 撈全量 → 本地 SQL 執行 | 聚合（SUM/AVG）、分組（GROUP BY）、跨表（JOIN） |

意圖文件新增 `query_type` 欄位決定路由，`tool_schema` 欄位攜帶 JSON Schema 約束。

> 完整任務清單見 [遷移計劃及迭代規劃](./遷移計劃及迭代規劃.md)

### 8.2 小模型訓練（迭代二 — 預留）

利用迭代一累積的意圖資料訓練兩個專精小模型：

| 模型 | 任務 | 輸入 | 輸出 | 資料量需求 |
|------|------|------|------|-----------|
| **模型 A：意圖分類** | NL → table_id + query_type | 自然語言查詢 | `{table_id, query_type}` | 500+ 筆 |
| **模型 B：參數生成** | Schema + NL → filters | NL + field 清單 | JSON filters | 2000+ 筆 |

啟動條件：500+ 筆經驗證意圖資料 + 分類 Accuracy > 90%。

訓練資料來源（迭代一預留欄位）：

| 欄位 | 用途 |
|------|------|
| `nl_examples` | 訓練 input |
| `expected_output` | 訓練 label |
| `difficulty_level` | 分層抽樣 |
| `test_cases` | 自動化 eval |
| `golden_sql` | Path B SQL 範例 |

### 8.3 PyO3 效能遷移（迭代三 — 預留）

將成熟的 Python 計算密集模組透過 PyO3 遷移至 Rust。

啟動條件：效能數據顯示 Python 是瓶頸（目前 LLM 推理 2-5 秒佔主導）。

候選模組：`date_resolver.py`、`schema_linker.py`、`sql_builder.py`。
