## 1. 概述

### 1.1 Data Agent 意圖的定位

Data Agent 意圖（現稱為「表達角度」Expression Angles）是「使用者自然語言查詢」與「資料表」之間的映射。與舊版架構不同，DA 意圖不再直接定義查詢場景，而是定義對特定表的表達方式：

- **目標表選取**：從 262 張 `da_tables` 中確定查詢對象（Phase 1 = 選表）
- **表達角度**：每個 `da_expressions` 僅對應一張表，定義該表的別名、範例與語意角度
- **動態推斷**：查詢類型（query_type）不再靜態存於意圖，而是由 `query_type_inferrer.py` 根據關鍵字與表能力動態推斷（Phase 2）

### 1.2 規模

| 指標 | 數量 |
|------|------|
| `da_tables` 總數 | 262 筆 |
| `da_expressions` 總數 | 262 筆（每表預設一個表達角度） |
| Qdrant 同步筆數 | 262 筆 |

### 1.3 與共用基礎設施的邊界

| 層面 | 現有實作 |
|------|-------------------|
| 儲存 | `da_tables` + `da_expressions` collection |
| 向量索引 | `da_expressions` Qdrant collection |
| CRUD API | `/api/v1/da/tables` 與 `/api/v1/da/expressions` (Rust) |
| 匹配邏輯 | Qdrant 選表 → 動態 `query_type` 推斷（§3） |
| Runtime Model | `da_tables` 與 `da_expressions` Pydantic models |

## 2. 意圖 Schema

Data Agent 採用二級 Schema 結構：`da_tables` 定義結構，`da_expressions` 定義查詢角度。

### 2.1 da_tables (表元資料)

| 欄位 | 類型 | 說明 |
|------|------|------|
| `_key` | string | Table Key (如 `erp/52`) |
| `display_name` | string | 顯示名稱 |
| `description` | string | 表描述 |
| `domain` | string | 業務領域 (如 `採購`, `銷售`) |
| `status` | string | 狀態 (`enabled`/`disabled`) |
| `identifiers` | object | Ragic 識別碼 (`table_id`, `sheet_key`) |
| `source_meta` | object | 來源系統元資料 |
| `capabilities` | object | 查詢能力 (`simple_filter`, `aggregate`, `time_series`, `cross_table`) |
| `fields[]` | array | 欄位列表 (`field_id`, `name`, `type`, `semantic_type`, `filterable`, `aggregatable`, `aliases`) |
| `relationships[]` | array | 關聯關係 |
| `updated_at` | string | 更新時間 |

### 2.2 da_expressions (表達角度)

| 欄位 | 類型 | 說明 |
|------|------|------|
| `_key` | string | Expression Key |
| `table_key` | string | 關聯表 key |
| `angle` | string | 表達角度類型 (如 `default`, `summary`) |
| `name` | string | 角度名稱 |
| `description` | string | 角度描述 |
| `aliases` | string[] | 別名 (用於向量嵌入) |
| `nl_examples` | string[] | 自然語言範例句 |
| `embedding_text` | string | 向量化文本 (自動生成) |
| `status` | string | 狀態 |
| `updated_at` | string | 更新時間 |

### 2.3 查詢路由規則 (動態推斷)

`query_type` 不再儲存在意圖中，而是透過 `query_type_inferrer.py` 根據以下優先順序動態推斷：

1. **關鍵字正規表達式匹配**：
   - `aggregate`: 「總計」、「平均」、「最大」、「最小」等
   - `time_series`: 「趨勢」、「按月」、「每日」等
   - `cross_table`: 「關聯」、「連同」等
2. **能力檢查**：檢查 `da_tables.capabilities` 是否支援推斷出的類型。
3. **預設降級**：若無匹配，預設為 `simple_filter`。

## 3. 意圖匹配流程

### 3.1 兩階段匹配與路由

NL 查詢主流程升級為兩階段動態架構：

```
使用者輸入 (NL)
    │
    ▼
[Phase 1: 選表]
Qdrant da_expressions 向量搜索
    │
    ├─► 信心度 > 門檻 ──► 取得 table_key
    └─► 信心度不足 ───► 進入澄清流程 (clarification_needed)
    │
    ▼
[Phase 1b: 推斷路由]
query_type_inferrer.py
    │
    ├─► 關鍵字 Regex 匹配
    ├─► da_tables.capabilities 交叉驗證
    └─► 決定動態 query_type
    │
    ▼
[Phase 2: 路徑路由]
根據推斷的 query_type 分發：
    │
    ├─► simple_filter ───────► Path A: Tool-Calling (Ragic API)
    └─► aggregate/cross_table ─► Path B: Pandas/DuckDB (全量運算)
```

## 3. 意圖匹配流程

### 3.1 三級信心度系統

NL Parser 使用三級信心度決定處理策略：

| 等級 | 分數閾值 | 處理方式 |
|------|---------|---------|
| **High** | ≥ 0.65 | 直接使用模板翻譯（最快） |
| **Medium** | 0.45–0.65 | 呼叫 Small LLM 輔助翻譯 |
| **Low** | < 0.45 | 回傳預設參數，請使用者釐清 |

> 閾值由 `system_params` 的 `intent.match_threshold`（Low）控制，High 門檻硬編碼在 `nl_parser.py`。

### 3.2 匹配流程圖（B+C 混合架構）

```
使用者輸入
    │
    ▼
RagicNLParser.parse()
    │
    ├─► IntentVectorStore.search() ──► Qdrant data_agent_intents
    │                                   │
    │                          ┌────────┘
    │                          ▼
    │                   top-3 候選意圖
    │                          │
    │              ┌───────────┼───────────┐
    │              ▼           ▼           ▼
    │           score≥0.65  0.45≤s<0.65  s<0.45
    │           (High)      (Medium)     (Low)
    │              │           │           │
    │              ▼           ▼           ▼
    │         template    LLM fallback  clarification
    │         translate    translate    _needed
    │              │           │           │
    └──────────────┴───────────┘           │
                    │                      │
                    ▼                      ▼
            query_type 判斷          回傳澄清問題
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
    simple_filter         aggregate /
         │               cross_table /
         ▼               time_series
    Path A:                    │
    Tool-Calling               ▼
    (JSON Schema          Path B:
     enum 約束             Pandas/DuckDB
     → Ragic API)         (Ragic API 撈全量
                           → 本地計算)
         │                     │
         └──────────┬──────────┘
                    ▼
              NLQueryResponse
```

### 3.3 Path A: Tool-Calling 核心機制

利用 Ollama 的 `format` 參數做 JSON Schema 約束，確保 LLM **只能**輸出合法的 `field_id`：

```python
# Phase 2: 載入目標表 schema 後，建構 JSON Schema
tool_schema = intent.tool_schema  # 從意圖中取得

resp = ollama.generate(
    model=model,
    prompt=prompt,      # 含 field label 清單 + 使用者查詢
    format=tool_schema  # JSON Schema enum 硬約束
)
```

**幻覺防治**：`field_id` 的 `enum` 陣列只包含該表的合法欄位，LLM 無法捏造不存在的值。

### 3.4 Path B: Pandas/DuckDB 機制

適用於 Ragic API 無法處理的複雜查詢（SUM/AVG/GROUP BY/JOIN）：

```
1. 意圖匹配 → 確定 query_type = aggregate / cross_table / time_series
2. Ragic API 撈全量資料（→ JSON）
3. 載入 DuckDB 記憶體表
4. LLM 生成 DuckDB SQL（欄位 enum 約束同 Path A）
5. DuckDB 本地執行 SQL
6. 回傳結果
```

### 3.5 語意不清處理

Data Agent 是**無狀態的被委派 Agent**。對於任何語意不清的查詢：

- 回傳 `clarification_needed` 類型回應
- 指出需要澄清的具體問題（如「請問您要查哪張表？」「請提供具體日期範圍」）
- 由前端 Orchestrator 負責指代消解與對話歷史管理

### 4.3 Embed Text 建構

```python
def _intent_to_embed_text(intent: dict) -> str:
    parts = list(intent.get("nl_patterns", []))
    if intent.get("description"):
        parts.append(intent["description"])
    parts.append(intent["intent_id"].replace("_", " "))
    return " ".join(parts)
```

> `nl_patterns` + `description` + `intent_id` 組成嵌入文本。`nl_examples` 目前**不**參與嵌入（預留迭代二訓練用）。

## 5. Embed-Sync 同步行為

### 5.1 同步端點

```
POST /intent-rag/data_agent/embed-sync
```

### 5.2 同步流程

```
觸發方式：前端「同步到 Qdrant」按鈕
     │
     ▼
Rust API (proxy_sync_qdrant)
     │
     ▼
Python Data Agent (embed-sync endpoint)
     │
     ├─ 1. fetch_intents_from_arango("data_agent")
     │      → AQL: FOR doc IN intent_catalog
     │        FILTER doc.agent_scope == "data_agent"
     │
     ├─ 2. 對每筆意圖生成向量嵌入
     │      → Ollama /api/embed (model = da.embedding_model)
     │
     ├─ 3. 重建 Qdrant collection
     │      → DELETE + PUT /collections/data_agent_intents
     │
     └─ 4. 批次寫入所有 points
            → PUT /collections/data_agent_intents/points
```

### 5.3 同步策略

目前採用**全量重建**策略（清除後重新寫入），原因：

- 意圖數量不大（< 200 筆），全量重建耗時 < 30 秒
- 避免增量同步的複雜度（刪除偵測、更新偵測）
- 嵌入向量在模型切換時需完整重新生成

未來若意圖數量超過 1000 筆，可考慮增量同步。

### 5.4 Scope 與 Collection 映射

```python
SCOPE_QDRANT_MAP = {
    "data_agent":   "data_agent_intents",
    "orchestrator": "orchestrator_intents",
}
```

## 7. 前端介面

Data Agent 遷移至專屬 Schema 後，前端介面也同步重構，不再與通用意圖目錄混雜。

### 7.1 Data Agent 專屬管理
