## 1. 背景與動機

### 1.1 現有架構的核心問題

| 問題 | 說明 | 嚴重度 |
|------|------|--------|
| **LLM 幻覺** | `_translate_via_llm` 捏造不存在的 `field_id` | 🔴 高 |
| **意圖系統不完整** | 只有 `list/count/search` 三種動作，無篩選/聚合/分組能力 | 🔴 高 |
| **圖譜+向量未參與查詢** | `graph_query.py` 和 `schema_store.py` 未串入 NL 查詢主流程 | 🟡 中 |
| **Ragic API 能力有限** | 無 JOIN / GROUP BY / SUM，複雜查詢無法在伺服器端完成 | 🟡 中 |
| **`business_aliases` 為空** | `schema_converter.py` 設 `business_aliases=[]`，欄位匹配靠 LLM 猜測 | 🟡 中 |

### 1.2 評估過的方案

| 方案 | 幻覺風險 | 簡單篩選準確率 | 聚合能力 | 實作複雜度 | 結論 |
|------|---------|--------------|---------|-----------|------|
| A: 現有+改進 | ⚠️ 中 | 70-80% | ❌ | 低 | 不足以滿足需求 |
| **B: Tool-Calling** | ✅ **近零** | **95%+** | ❌ | 中 | ✅ 簡單篩選最佳 |
| **C: Pandas/DuckDB** | ⚠️ 中 | 80-85% | ✅ | 中-高 | ✅ 聚合/跨表必備 |
| D: sqlcoder→DuckDB | ⚠️ 中-高 | 60-70% | ✅ | 極高 | ❌ 兩層出錯、field_id 數字問題 |

**最終決策**：方案 B+C 混合。

### 2.1 B+C 混合架構 (遷移後)

```
                           ┌──────────────────────────────────────────┐
                           │    Phase 1b: 查詢分類 (動態推斷)         │
                           │                                          │
                           │  query_type_inferrer.py 動態推斷類型     │

                           │   filters     │    │                    │

                           │               │    │ - SUM/AVG/COUNT   │

                           │ - WHERE 篩選  │    │ - JOIN (多表)     │

```

### 2.2 查詢路由規則

`query_type` 現在由 `query_type_inferrer.py` **動態推斷**（關鍵字 Regex + 表能力交叉驗證），不再從意圖中靜態取得。

| 查詢類型 | 路由 | 判斷依據 |
|----------|------|---------|
| 簡單篩選（WHERE + ORDER + LIMIT） | **Path A** Tool-Calling | `query_type_inferrer` 推斷結果為 `simple_filter` |
| 聚合統計（SUM / AVG / COUNT） | **Path B** Pandas/DuckDB | `query_type_inferrer` 推斷結果為 `aggregate` |
| 分組排序（GROUP BY + HAVING） | **Path B** Pandas/DuckDB | `query_type_inferrer` 推斷結果為 `aggregate` |
| 跨表查詢（JOIN） | **Path B** Pandas/DuckDB | `query_type_inferrer` 推斷結果為 `cross_table` |
| 時間序列分析 | **Path B** Pandas/DuckDB | `query_type_inferrer` 推斷結果為 `time_series` |


### 2.3 Path A: Tool-Calling 核心機制

利用 Ollama 的 `format` 參數做 JSON Schema 約束，確保 LLM **只能**輸出合法的 `field_id`：

```python
# Phase 2: 載入目標表 schema 後，建構 JSON Schema
tool_schema = {
    "type": "object",
    "properties": {
        "filters": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "field_id": {
                        "type": "string",
                        "enum": ["1018484", "1018528", "1019091", "1019092"]
                    },
                    "operator": {
                        "type": "string",
                        "enum": ["eq", "ne", "like", "gt", "gte", "lt", "lte"]
                    },
                    "value": {"type": "string"}
                },
                "required": ["field_id", "operator", "value"]
            }
        },
        "order_field": {
            "type": "string",
            "enum": ["1018484", "1018528", "1019091", "1019092"]
        },
        "order_direction": {
            "type": "string",
            "enum": ["ASC", "DESC"]
        },
        "limit": {"type": "integer", "minimum": 1, "maximum": 5000}
    },
    "required": ["filters"]
}

resp = ollama.generate(
    model=model,
    prompt=prompt,      # 含 field label 清單 + 使用者查詢
    format=tool_schema  # JSON Schema enum 硬約束
)
```

**幻覺防治**：`field_id` 的 `enum` 陣列只包含該表的合法欄位，LLM 無法捏造不存在的值。

|------|------|---------|------|
| 簡單篩選 | 「查詢供應商為一六八的收貨單」 | 正確回傳 2 筆，field_id `1019092` | A |
| 日期篩選 | 「2026 年 3 月的採購單」 | 日期區間 gte/lte 正確 | A |
| 聚合統計 | 「三月份各供應商的進貨總金額」 | SUM + GROUP BY 結果 | B |

| 語意不清 | 「上個月的東西」 | 回傳 clarification_needed | — |

## 5. 迭代二：意圖資料訓練小模型

> **啟動條件**：迭代一穩定運行 + 累積 500+ 筆經人工驗證的意圖資料

### 5.1 目標

| 目標 | 說明 |
|------|------|
| 降低延遲 | 本地推理取代 LLM API call（目標 < 200ms） |
| 降低成本 | 不需呼叫大模型 |
| 離線能力 | 桌面應用可在無網路環境運行 |

### 5.2 小模型定位

**建議拆成兩個專精小模型**，而非一個通用模型：

| 模型 | 任務 | 輸入 | 輸出 | 訓練資料量 | 模型選擇 |
|------|------|------|------|-----------|---------|
| **模型 A：意圖分類** | NL → 哪張表 + 查詢類型 | 自然語言查詢 | `{table_id, query_type}` | 500+ 筆 | DistilBERT / all-MiniLM |
| **模型 B：參數生成** | Schema + NL → filters | NL + field 清單 | JSON filters | 2000+ 筆 | Fine-tuned Mistral-7B / Phi-3 |

### 5.3 資料準備（迭代一預留的欄位）

迭代一的意圖 schema 已預留以下欄位，直接作為訓練資料來源：

| 欄位 | 用途 |
|------|------|
| `nl_examples` | 訓練 input（自然語言） |
| `expected_output` | 訓練 label（結構化輸出） |
| `difficulty_level` | 按難度分層抽樣 |
| `test_cases` | 自動化 eval 用 |
| `golden_sql` | DuckDB 方言 SQL 範例（Path B 訓練用） |

### 5.4 Eval Pipeline

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ 測試資料集    │ →   │ 小模型推理    │ →   │ 自動評估     │
│ (test_cases) │     │              │     │              │
│              │     │ 模型 A 或 B  │     │ - Accuracy   │
│              │     │              │     │ - F1 Score   │
│              │     │              │     │ - Latency    │
└──────────────┘     └──────────────┘     └──────────────┘
```

### 5.5 決策指標

| 指標 | 門檻 | 不達標行動 |
|------|------|-----------|
| 分類 Accuracy | > 90% | 繼續使用 Qdrant 向量匹配 |
| 參數生成 F1 | > 85% | 繼續使用 Tool-Calling enum 約束 |
| 推理延遲 | < 200ms | 繼續使用大模型（延遲不是瓶頸時） |

## 6. 迭代三：PyO3 效能遷移（預留）

> **啟動條件**：效能數據顯示 Python 是瓶頸（目前不是：LLM 推理 2-5 秒佔主導）

### 6.1 遷移候選模組

| 模組 | Python→Rust 價值 | 遷移難度 | 優先順序 |
|------|-----------------|---------|---------|
| `date_resolver.py` | 中（regex 密集） | 低 | P1 |
| `schema_linker.py` | 中（enum 建構） | 低 | P2 |
| `sql_builder.py` | 中（字串建構） | 低 | P2 |
| `tool_calling_engine.py` | 低（I/O bound） | 中 | P3 |
| `pandas_engine.py` | 高（計算密集）但 Polars 更適合 | 高 | P3 |

### 6.2 設計預留（迭代一就要做的）

為了讓迭代三在需要時能順利進行，迭代一的程式碼設計需要：

| 設計原則 | 做法 |
|----------|------|
| **邏輯與 I/O 分離** | 純計算函數獨立（可直接移植 Rust）；HTTP 呼叫封裝在薄層 |
| **Pydantic model → Rust struct** | 所有核心 model 用 Pydantic，未來 1:1 映射 `serde::Deserialize` |
| **Protocol / ABC 介面** | 所有引擎用 Protocol 定義介面，方便替換實作 |
| **無全域狀態** | 不使用全域變數或模組級 singleton |

## 7. 風險與緩解

| 風險 | 影響 | 機率 | 緩解措施 |
|------|------|------|---------|
| Ollama `format` 約束在 edge case 失效 | field_id 幻覺回歸 | 低 | 後驗證層：檢查 LLM 輸出的 field_id 是否在合法清單中 |
| Ragic API 撈全量資料太慢（Path B） | 聚合查詢延遲 > 30s | 中 | 快取策略：DuckDB 本地 cache + TTL；大表分頁撈取 |
| 意圖分類錯誤（Path A/B 路由錯） | 查詢失敗或結果不完整 | 中 | Fallback：Path A 失敗時自動降級到 Path B |
| DuckDB 記憶體不足（大表 JOIN） | OOM crash | 低 | 設定 DuckDB memory_limit；超過閾值改用分頁 API |
| 迭代二小模型品質不足 | 訓練白費 | 中 | 明確的品質門檻（見 §5.5）；不達標就繼續用 Tool-Calling |
