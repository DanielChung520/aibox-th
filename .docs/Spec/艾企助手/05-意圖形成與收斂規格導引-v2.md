## 1. 文件定位

本文件不是最終實作規格，也不是意圖哲學宣言。

## 3. 現階段已確定的事

### 3.1 意圖不是 query-to-label mapping

未來實作不得再以「輸入一句 query，輸出一個 intent_id」作為完整中心。

更進一步說，後續規格應把意圖表達為：

- 假設（hypothesis）
- 證據（evidence）
- 不確定性（uncertainty）
- 邊界判定（boundary status）
- 下一步（next question / next action）

### 3.2 ActionTrail 是一級輸入，不是附屬 log

後續所有規格若忽略 actionTrail、page context、active anchor、recent UI path，都視為偏離方向。

### 3.3 Rule 與 Intent LLM 必須共同存在

後續規格不得走向純模板化，也不得走向純 LLM 猜測。

### 3.4 意圖的輸出不只是 guess list

後續規格應逐步轉向輸出以下資訊：

- current intent state
- candidate directions
- confidence band
- missing evidence
- recommended next action

並至少保留一個 `prediction_id`，讓後續 accept / reject / confirm 能精準回對當次候選集合與上下文快照。

---

## 4. 現階段故意不定死的事

### 4.1 不先定最終 intent state schema

雖然方向已明確，但：

- intent_state 的最終欄位
- intent_evidence 的具體結構
- confidence band 的數學定義

應在後續資料模型細規中落地。

### 4.2 不先定 rule engine DSL

目前只確定 rule 必須存在，但不先定：

- rule 語法
- 執行引擎形式
- 是否使用 JSON / YAML / DSL

### 4.3 不先定 intent llm prompt 與小模型選型

只確定它必須作為語義補全與模糊理解層，不先定具體模型與 prompt 形式。

---

## 5. 後續拆規格的正確順序

### Phase 1：多維訊號與 Intent State 規格

必須回答：

- language / behavior / structure / context / implicit signals 如何建模
- pre-intent / narrowing / commitment / learning 的 state 如何表示
- 什麼訊號進 working set，什麼訊號只做統計

### Phase 2：Rule Engine 與 Intent LLM 協作規格

必須回答：

- 哪些場景 rule 可直接處理
- 哪些場景交給 intent llm
- 兩者如何交替與回退
- 最後如何回到可驗證結構

### Phase 3：事件流與 API 契約規格

必須回答：

- accept / reject / confirm / clarify / revise 事件怎麼記錄
- 前端與後端如何交換 intent state
- 什麼時候寫 log，什麼時候只更新 session state
- `prediction_id` 如何生成、回傳、追蹤與回放

### Phase 4：學習與回放規格

必須回答：

- 學習材料從哪裡來
- 怎麼把 log / action / result 對齊
- 哪些成功路徑可沉澱成 rule / prior / memory

---

## 6. 每份後續規格至少要回答的問題

### 6.1 資料問題

- 需要哪些 state / event / evidence 結構
- required / optional / derived 欄位有哪些

### 6.2 流程問題

- 何時進入 pre-intent
- 何時算 narrow 成功
- 何時進入 commitment
- 何時回退到 clarify

### 6.3 邊界問題

- 什麼可由前端即時處理
- 什麼必須送後端
- 什麼必須經過 knowledge boundary 驗證

### 6.4 驗證問題

- 什麼算收斂成功
- 什麼算錯誤 commitment
- 用哪些信號評估 rule / llm 效果
- 什麼情況必須升級為 human-in-the-loop，而不是自動推進

### 6.5 遷移問題

- 現有 intent catalog 如何保留為先驗層
- 現有 intent logs 如何轉成學習材料
- 舊流程與新流程是否允許雙軌並存

---

## 7. 對 coder agent 的使用方式

### 7.1 可以做的事

- 用本文件判斷後續先補哪份細規
- 檢查某意圖方案是否仍停留在 catalog / guess 中心
- 評估某實作是否忽略多維訊號與收斂流程

### 7.2 不應直接做的事

- 直接依本文件改寫 intentEngine
- 直接依本文件定 API payload
- 直接依本文件重寫學習器

因為本文件仍屬導引層，不是實作契約。

---

## 8. 對後續細規的硬要求

後續任何意圖相關細規，至少必須滿足：

1. 不得把 intent system 寫回 intent catalog 中心
2. 必須把 actionTrail 視為第一級訊號
3. 必須處理多維訊號，而非只處理 query text
4. 必須明確說明 rule 與 intent llm 的協作與回退
5. 必須與 knowledge boundary / evidence assembly / Inquiry Controller 對齊
6. 必須定義「何時停止、何時澄清、何時交由人決策」

---

## 9. 本文件結論

意圖系統的未來，不是讓艾企「更會猜」，而是讓艾企：

> **在多維訊號下，更早開始理解、更穩定地收斂、更晚才做承諾，並且在每次成功互動後真正學到可重用的收斂方法。**

這也是後續實作時，所有 agent 都必須遵守的中心紀律。
