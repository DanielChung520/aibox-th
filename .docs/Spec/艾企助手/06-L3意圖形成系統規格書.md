# L3 意圖形成系統規格書

> **範疇**：艾企助手 Inquiry Orchestrator — 學習型引導式諮詢系統
> **層級**：L3 控制層（五層模型）
> **目標讀者**：AI Coder Agent（用於實作開發）

---

## 1. 系統定位

L3 是**學習型引導式諮詢系統**，不是意圖分類器。

核心職責：使用者進入系統後，透過多維信號感知 + 多輪引導式對話，逐步收斂使用者意圖，路由到正確的執行層。

### 1.1 不是什麼

- ❌ 不是 Intent Catalog 中心（紅線 #1）
- ❌ 不是 actionTrail 第一級設計（紅線 #2）
- ❌ 不是單次分類器（是多輪收斂）

### 1.2 邊界

| 在 L3 範圍內 | 不在 L3 範圍內 |
|-------------|--------------|
| 艾企助手的意圖引導（浮動助手對話） | **任務聊天**（taskChatStore / AITask LangGraph） |
| 操作意圖引導（「我要查庫存」） | Data Agent 內部 NL→SQL 意圖邏輯 |
| 知識庫查詢路由 | HybridRAG 檢索細節 |
| 跨場景問題收斂 | 工具執行邏輯 |
| User Profile Summary 沉澱 | LLM 推理本身 |

> **⚠️ 關鍵區分：艾企 vs 任務聊天 vs 其他 Agent 意圖系統**
>
> - **艾企助手（本規格）**：使用 `aiqChatStore`，走獨立 API 路徑 `/api/v1/aiq/*`。處理任意頁面 + 任意 query 的操作意圖、知識查詢、跨場景問題。
> - **任務聊天**：使用 `taskChatStore`，走 `orchestrator.rs` → AITask LangGraph。有自己的 `intent_classifier.py` + `matcher_node.py`。**L3 不介入。**
> - **Data Agent**：進入資料綱要 tab 後觸發，有自己的 `intent_classifier.py` + NL→SQL pipeline。L3 可路由到 DA，但 DA 內部邏輯獨立。
> - **未來其他 Agent**：各自有自己的意圖邏輯，與本系統是兩碼事。
>
> 這些是**完全獨立的意圖系統**，不共用狀態、不共用路由邏輯。

## 3. Perception Layer（感知層）

### 3.1 職責

- 持續運作，Rule-based，低成本
- **首要任務**：識別活躍 Anchor（草案 §9 強調）
- 不做決策，不調用 LLM
- 累積多維信號，產出 Working Context

### 3.2 五維信號

| 維度 | 說明 | 來源 |
|------|------|------|
| Language | 使用者輸入的自然語言 query | ChatModal 提交 |
| Behavior | 點擊、停留、排序、篩選、搜尋 | actionTrail.ts |
| Structure | 當前頁面路由、表格 schema、記錄數 | FloatingAssistant DOM extraction |
| Context | 對話歷史、當前 session 狀態 | chatStore |
| Implicit | User Profile Summary（活躍領域統計） | SeaWeedFS + localStorage |

### 3.3 信號推送策略

**智能過濾（只推送關鍵 state-change）**：

不是每個 actionTrail 事件都推送到後端。只有以下狀態變化才觸發 `/signals/push`：

| 觸發條件 | 說明 |
|---------|------|
| 頁面切換 | `page_navigate` 事件 |
| 表格焦點變化 | 從一個 table 切到另一個 table |
| query 提交 | 使用者在對話框送出訊息 |
| 顯著行為累積 | 同類事件連續 N 次（如連續篩選 3 次） |

> **實作位置**：前端 SignalCollector（新模組），訂閱 `actionTrail.subscribe()`，做 debounce + 過濾後推送。

### 3.4 Working Context 結構

```typescript
interface WorkingContext {
  // 第一級公民
  active_anchors: Anchor[];

  // 頁面與行為
  page_context: {
    path: string;
    page_name: string;
    page_type: string;        // from PAGE_TYPE_MAP
    domain_name?: string;
    table_name?: string;
    record_count?: number;
  };
  behavior_snapshot: {
    recent_actions: ActionEvent[];  // 最近 N 筆
    dwell_hotspots: string[];       // 停留熱點
    filter_patterns: string[];      // 篩選模式
  };

  // 使用者先驗
  user_prior: {
    active_domains: Record<string, number>;  // 領域 → 活躍度百分比
    frequent_queries: string[];               // 常見查詢類型
    skill_level: 'beginner' | 'intermediate' | 'advanced';
  };

  // 信號累積
  signal_accumulation: {
    total_signals: number;
    last_anchor_change: number;  // timestamp
    confidence_trend: number[];  // 最近 5 次 confidence
  };
}

interface Anchor {
  type: 'page' | 'entity' | 'task' | 'query';
  value: string;
  confidence: number;
  source: 'behavior' | 'language' | 'structure';
  timestamp: number;
}
```

### 3.5 Rule Engine 規則（待逐步定義）

Perception 層使用純規則，不用 LLM。規則範例：

```
IF page_navigate TO /data-agent/* THEN anchor = { type: 'page', value: 'data_query' }
IF cell_click COUNT >= 3 ON same_table THEN anchor = { type: 'entity', value: table_name }
IF query CONTAINS '庫存|inventory' THEN anchor = { type: 'query', value: 'inventory_inquiry' }
```

> **規則維護**：規則儲存於 `system_params`，可透過管理界面動態調整。

## 4. Inquiry Layer（引導層）

### 4.1 觸發條件

| 觸發 | 說明 |
|------|------|
| query 提交 | 使用者送出自然語言訊息 |
| anchor 有意義變化 | Perception 層偵測到 anchor 切換或 confidence 大幅變動 |

### 4.2 狀態機

```
觸發（query OR anchor 變化）
    ↓
Pre-Intent → 累計 N 個信號（anchor + 頁面類型 + 查詢意圖信號）
    ↓
Narrowing → top-3 hypotheses，Working Context + LLM 共同收斂
    ↓
    ├── H1-H2 差距 > gap_threshold AND boundary == sufficient → Commitment
    ├── boundary == insufficient → Clarification（LLM 生成澄清問題）
    └── else → 留在 Narrowing（等待更多信號或下一輪對話）
    ↓
Commitment → 選定 execution_path → 路由到 Execution Layer
    ↓
Learning → 每 completed turn 觸發
```

### 4.3 Hypothesis 管理

同時維護 top-3 hypotheses：

```typescript
interface Hypothesis {
  id: string;
  intent_label: string;           // 如 'inventory_query', 'knowledge_search'
  execution_path: ExecutionPath;
  confidence: number;             // 0.0 ~ 1.0
  evidence_chain: Evidence[];     // 可追溯性（草案 Provenance）
  parameters: Record<string, unknown>;
}

type ExecutionPath =
  | 'knowledge_search'     // → HybridRAG
  | 'operation_guide'      // → 操作手冊知識庫
  | 'route_to_data'        // → Data Agent（交接後 DA 自行處理）
  | 'todo_generate'        // → Todo 生成
  | 'llm_answer'           // → 直接 LLM 回答
  | 'web_fallback'         // → 網路搜尋
  | 'tool_call';           // → MCP 工具

interface Evidence {
  source: 'anchor' | 'query' | 'behavior' | 'clarification' | 'user_profile';
  signal: string;
  contribution: number;  // 對 confidence 的貢獻量
  timestamp: number;
}
```

### 4.4 Commitment 條件

```
COMMIT WHEN:
  hypotheses[0].confidence - hypotheses[1].confidence > gap_threshold (default: 0.3)
  AND boundary_status == 'sufficient'

CLARIFY WHEN:
  boundary_status == 'insufficient'
  （LLM 生成最多 2 個澄清問題，不超過 3 輪）

STAY IN NARROWING WHEN:
  gap < gap_threshold AND boundary == 'sufficient'
  （等待下一個信號或對話輪次）
```

### 4.5 Boundary 評估

與 Knowledge Agent 的 `boundary_checker.py` 對齊：

```typescript
interface BoundaryStatus {
  status: 'sufficient' | 'insufficient' | 'out_of_scope';
  missing_dimensions: string[];   // 缺什麼維度的信息
  suggested_questions: string[];  // LLM 生成的澄清問題
}
```

### 4.6 Rule 與 LLM 協作（導引 §8 紅線 #4）

| 層 | 使用 | 職責 |
|----|------|------|
| Perception | Rule-based | 信號累積、Anchor 識別、Working Context 構建 |
| Inquiry | LLM-based | Hypothesis 評估、Boundary 判斷、Clarification 生成、Routing 決策 |

> **正式定義**：Perception 層的規則是確定性的（同輸入同輸出），不依賴 LLM。Inquiry 層使用 LLM 處理模糊性和開放式決策，但 Routing 最終結果必須是可枚舉的 `ExecutionPath`。

## 6. Learning Layer（學習層）

### 6.1 觸發

每個 completed turn（使用者收到回覆且未 reject）觸發。

### 6.2 User Profile Summary

**不是事件日誌，是統計總結。**

```typescript
interface UserProfileSummary {
  user_key: string;
  last_updated: number;

  // 活躍領域統計
  domain_distribution: Record<string, number>;  // 如 { inventory: 0.6, orders: 0.3, hr: 0.1 }

  // 查詢模式
  query_patterns: {
    frequent_intents: string[];           // 常觸發的 execution_path
    avg_clarification_rounds: number;     // 平均澄清輪數
    preferred_response_depth: 'brief' | 'detailed';
  };

  // 成功/失敗模式
  success_patterns: Pattern[];
  failure_patterns: Pattern[];
}

interface Pattern {
  context_signature: string;    // 如 'inventory_page + filter_apply + query'
  execution_path: ExecutionPath;
  success_rate: number;
  sample_count: number;
}
```

### 6.3 儲存

| 儲存位置 | 用途 |
|---------|------|
| ArangoDB `user_profiles` collection | 持久化主存（per-user JSON document，`_key` = user_key） |
| localStorage | 前端快取（減少網路請求） |

> **為何不用 SeaWeedFS**：UserProfileSummary 是小型結構化 JSON（每人 2-5 KB），不是大檔案。ArangoDB 可直接用 `_key` 查詢，支援聚合分析，且與現有 `users`、`system_params` 等 collection 一致。

> **同步策略**：Learning 更新後寫入 ArangoDB，前端透過獨立的 `userProfileStore` 在 login 時拉取最新版覆蓋 localStorage。後續每次 turn complete 後端更新 profile 時，透過 SSE 推送 `profile_updated` 事件通知前端重新拉取。

### 6.4 前端同步架構

前端新建獨立的 `src/stores/userProfileStore.ts`，職責單一：

```typescript
// 生命週期
// 1. Login 成功 → userProfileStore.load(user_key)
//    → GET /api/v1/aiq/user-profile/{user_key}
//    → 存入 localStorage
// 2. SSE 收到 profile_updated → userProfileStore.reload()
// 3. Perception / FloatingAssistant 需要 user_prior 時直接讀取
// 4. Logout → userProfileStore.clear()
```

> **不放 signalCollector 的原因**：signalCollector 負責「推送信號」，userProfileStore 負責「拉取偏好」，職責方向相反，不應混合。

## 7. API 端點

### 7.1 艾企獨立 API 路徑

艾企助手使用獨立的 API 路徑 `/api/v1/aiq/*`，**不經過** `orchestrator.rs`（那是任務聊天的路由器）。

| 方法 | 端點 | 說明 | 認證 |
|------|------|------|------|
| POST | `/api/v1/aiq/signals/push` | 前端推送 debounced state-change 信號 | 是 |
| GET | `/api/v1/aiq/intent-state` | 查詢當前 Perception Working Context | 是 |
| POST | `/api/v1/aiq/intent-state/commit` | 確認 Hypothesis → 執行 | 是 |
| SSE | `/api/v1/aiq/intent-state/stream` | 即時推送 hypotheses 更新 | 是 |
| POST | `/api/v1/aiq/chat` | 艾企對話入口（帶 Working Context） | 是 |
| POST | `/api/v1/aiq/learning/turn-complete` | 學習觸發：turn 完成後更新 UserProfile | 是 |
| GET | `/api/v1/aiq/user-profile` | 取得當前使用者的 UserProfileSummary | 是 |
| PUT | `/api/v1/aiq/user-profile` | 更新當前使用者的 UserProfileSummary | 是 |

### 7.2 SSE 事件（艾企專用通道）

艾企使用自己的 SSE 通道 `/api/v1/aiq/intent-state/stream`，不與任務聊天的 SSE 混用。

新增事件名稱（擴展 `sseManager.ts`）：

| 事件名 | 說明 | 推送時機 |
|--------|------|---------|
| `perception_update` | Working Context 更新 | anchor 變化 |
| `hypothesis_update` | top-3 hypotheses 變化 | confidence Δ > 0.2 |
| `clarification_request` | 引導層要求澄清 | boundary == insufficient |
| `commitment` | 意圖確認，準備執行 | Commitment 條件達成 |
| `profile_updated` | 使用者 Profile 已更新 | Learning turn-complete 寫入後 |

> **相容性**：現有 `intent_detected`、`tool_call_start`、`da_query_start` 等事件不受影響。

### 7.3 Signal Push Payload

```typescript
}

interface SignalEvent {
  type: 'page_navigate' | 'table_focus' | 'query_submit' | 'behavior_accumulation';
  timestamp: number;
  page: string;
  meta: Record<string, unknown>;
}
```

## 11. 設計紅線（不可違反）
