## 2. 配置持久化 (system_params)

### 2.1 集合結構

艾企的所有配置存放在 ArangoDB `system_params` 集合：

```json
{
  "_key": "floating_assistant.modalWidth",
  "param_key": "floating_assistant.modalWidth",
  "param_value": "480",
  "param_type": "string",
  "require_restart": false,
  "category": "floating_assistant"
}
```

### 2.2 Key 命名規則

| 前綴 | 用途 | 範例 |
|------|------|------|
| `floating_assistant.*` | 聊天窗樣式配置（38 項） | `floating_assistant.modalWidth` |
| `basic.avatar` | 頭像名稱 | `basic.avatar` → `"可瑤"` |

### 2.3 API 端點

| 方法 | 端點 | 說明 | 認證 |
|------|------|------|------|
| GET | `/api/v1/system-params` | 取得全部參數 | 否 |
| GET | `/api/v1/system-params/{key}` | 取得單一參數 | 否 |
| PUT | `/api/v1/system-params/{key}` | 更新參數（自動 upsert） | 否 |

### 2.4 前端 API 封裝

```typescript
// src/services/api.ts
export const paramsApi = {
  list: () => api.get<{ code: number; data: SystemParam[] }>('/api/v1/system-params'),
  get: (key: string) => api.get<{ code: number; data: SystemParam }>(`/api/v1/system-params/${key}`),
  update: (key: string, param_value: string) => api.put(`/api/v1/system-params/${key}`, { param_value }),
};
```

### 2.5 注意事項

- 所有值以 `string` 型態存入 DB（`param_type` 固定為 `"string"`）
- 數值型配置需在前端做 `parseInt()` / `parseFloat()` 轉換
- PUT 端點具備 upsert 行為：key 不存在時自動建立
- 不需要 JWT 認證（系統參數為公開配置）

## 3. AI 對話整合

### 3.1 現有架構

目前任務聊天室（`/app/task-session/chat`）的 AI 對話已完整實作，艾企助手將複用此架構。

#### 對話流程

```
使用者輸入
  ↓
前端 POST /api/v1/chat/sessions/{key}/messages
  ↓
Rust API Gateway (chat.rs → orchestrator)
  ↓
SSE 串流代理 → AITask (port 8001) /chat/stream
  ↓
LangGraph Pipeline:
  classify_intent → matcher → resolve_coreference
    → route_by_action_plan
      → chat_responder (一般對話)
      → da_query (資料查詢)
      → ka_search (知識庫搜尋)
      → tool_executor (工具呼叫)
      → bpa_orchestrator (流程自動化)
    → memory_manager
  ↓
SSE chunks 回傳前端
```

#### 現有 API 端點

| 方法 | 端點 | 說明 |
|------|------|------|
| POST | `/api/v1/chat/sessions` | 建立對話 Session |
| GET | `/api/v1/chat/sessions` | 列出使用者的 Sessions |
| GET | `/api/v1/chat/sessions/{key}` | 取得 Session + 歷史訊息 |
| PUT | `/api/v1/chat/sessions/{key}` | 更新 Session（標題、狀態） |
| DELETE | `/api/v1/chat/sessions/{key}` | 刪除 Session + 關聯資料 |
| POST | `/api/v1/chat/sessions/{key}/messages` | 發送訊息（SSE 串流回應） |

### 3.2 艾企接入方案

艾企助手接入 AI 對話後端有兩種模式：

#### 模式 A：共用 Session（推薦）

艾企建立專屬的 `chat_session`，與任務聊天室共用相同的後端架構：

```
艾企開啟 → 建立/恢復 Session (type: 'assistant')
  ↓
使用者輸入 → POST /api/v1/chat/sessions/{key}/messages
  ↓
SSE 串流回應 → ChatModal 逐 chunk 顯示
```

**優點**：
- 複用現有完整架構（LangGraph、記憶、5W1H 標記）
- 對話歷史自動持久化至 `chat_messages`
- 無需新增 API 端點

**Session 區分**：
- 在 `CreateSessionRequest` 中加入 `source` 欄位：`"assistant"` vs `"chat"`
- 或在 `chat_sessions` 集合中新增 `source` 欄位用於過濾

#### 模式 B：輕量端點

新增獨立的艾企專用端點，跳過 LangGraph Pipeline，直接呼叫 LLM：

```
POST /api/v1/assistant/chat
{
  "message": "如何新增用戶？",
  "page_context": { "name": "用戶管理", ... },
  "history": [ ... ]    // 最近 N 條對話
}
```

**適用場景**：需要極低延遲（< 1s）的簡單問答

**建議**：先實作模式 A，後續根據性能需求再考慮模式 B。

### 3.3 SSE 串流整合

#### Rust 端 SSE 架構 (api/src/api/sse.rs)

```rust
// 已有的 SseEvent 結構
pub struct SseEvent {
    pub event: String,   // chat_chunk, chat_done, error, heartbeat
    pub data: String,    // JSON payload
    pub id: Option<String>,
    pub retry: Option<u64>,
}
```

#### 前端 SSE 消費

ChatModal 需要實作 SSE 訊息消費：

```typescript
// 概念性程式碼
const eventSource = new EventSource(`/api/v1/sse/chat/${contextId}`);

eventSource.addEventListener('chat_chunk', (e) => {
  const chunk = JSON.parse(e.data);
  appendToMessage(chunk.content);
});

eventSource.addEventListener('chat_done', (e) => {
  finalizeMessage();
});

eventSource.addEventListener('error', (e) => {
  handleError(e);
});
```

或使用 `fetch` + `ReadableStream` 直接消費 POST 端點回傳的 SSE：

```typescript
const response = await fetch(`/api/v1/chat/sessions/${sessionKey}/messages`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
  body: JSON.stringify({ content: message }),
});

const reader = response.body!.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const chunk = decoder.decode(value);
  // 解析 SSE 格式的 chunk
  parseAndAppendChunks(chunk);
}
```

### 3.4 System Prompt 注入

頁面感知的上下文需注入 AI 的 System Prompt：

```
你是「艾企」，AIBox 管理系統的 AI 助手。

## 當前情境
- 使用者目前在「{pageContext.name}」頁面
- 頁面描述：{pageContext.description}
{方案 B 的 detail 資訊（如有）}

## 行為準則
- 回答時優先參考使用者當前頁面的上下文
- 使用繁體中文回答
- 簡潔、專業、友善
- 如果不確定，告訴使用者你不知道，不要編造
```

**注入方式**：在 `SendMessageRequest` 中新增 `system_prompt` 或 `context` 欄位，由 Rust 端合併至 AI 請求。

## 4. 對話歷史持久化

### 4.1 DB Collections

| 集合 | 用途 | 索引 |
|------|------|------|
| `chat_sessions` | 對話 Session 記錄 | `user_key`, `status` |
| `chat_messages` | 對話訊息記錄 | `session_key`, `created_at` |
| `chat_checkpoints` | LangGraph 檢查點 | `thread_id`, `checkpoint_id` (unique) |
| `chat_checkpoint_writes` | LangGraph 檢查點寫入 | `thread_id + task_id + idx` (unique) |
| `tool_executions` | 工具呼叫記錄 | `session_key`, `tool_name` |

### 4.2 chat_sessions Schema

```json
{
  "_key": "uuid",
  "title": "用戶管理相關問題",
  "provider": "ollama",
  "model": "llama3.2:latest",
  "status": "active",
  "tags_5w1h": { "who": "admin", "what": "新增用戶", ... },
  "user_key": "user_001",
  "source": "assistant",        // 新增：區分來源 "assistant" | "chat"
  "page_context": {             // 新增：記錄啟動時的頁面上下文
    "name": "用戶管理",
    "description": "管理系統使用者帳號"
  },
  "created_at": "2026-04-15T09:00:00Z",
  "updated_at": "2026-04-15T09:05:00Z"
}
```

### 4.3 chat_messages Schema

```json
{
  "_key": "uuid",
  "session_key": "session_uuid",
  "role": "user | assistant | system",
  "content": "如何新增用戶？",
  "thinking": null,
  "tokens": 150,
  "created_at": "2026-04-15T09:01:00Z"
}
```

### 4.4 艾企 Session 管理策略

| 策略 | 說明 |
|------|------|
| **建立時機** | 使用者首次在艾企發送訊息時 |
| **Session 恢復** | 如果已有當天的 `source: 'assistant'` Session，恢復而非建立 |
| **自動標題** | 首次 AI 回覆後觸發 5W1H 標記，取 `what` 作為標題 |
| **Session 過期** | 不主動關閉；使用者明確點擊「清除對話」時重建 |
| **歷史載入** | 開啟艾企時載入最近一個 active Session 的歷史訊息 |

## 5. 知識庫 RAG 整合（方案 C）

### 5.1 Knowledge Agent (port 8007)

Knowledge Agent 提供向量化知識庫檢索能力：

| 端點 | 說明 |
|------|------|
| `GET /api/v1/knowledge/roots` | 列出知識庫 |
| `GET /api/v1/knowledge/files/{id}/vectors` | 取得向量 Chunks |
| `GET /api/v1/knowledge/files/{id}/similar` | 語意相似檢索 |

### 5.2 動態建議 API（待新增）

用於方案 C 的 RAG 動態建議：

```
POST /api/v1/ai/suggestions
Authorization: Bearer <token>
```

#### Request

```json
{
  "page_context": {
    "name": "Schema 管理",
    "description": "資料庫結構瀏覽與管理",
    "detail": {
      "entity": "customers",
      "entityType": "table"
    }
  },
  "count": 3,
  "language": "zh-TW"
}
```

#### Response

```json
{
  "code": 0,
  "data": {
    "suggestions": [
      "customers 表有哪些主要欄位？",
      "如何建立 customers 與 orders 的關聯查詢？",
      "這個表的資料量有多大？"
    ],
    "source": "rag",
    "model": "qwen2.5:1.5b"
  }
}
```

### 5.3 實作流程

```
1. Rust API Gateway 接收 POST /api/v1/ai/suggestions
2. 代理至 AITask (port 8001) 或 Knowledge Agent (port 8007)
3. 根據 page_context 組裝 prompt：
   「使用者在 {name} 頁面，正在 {description}。
    請根據以下知識庫內容，生成 {count} 個使用者可能會問的問題。」
4. 從 Qdrant 檢索相關知識 Chunks（按 page name / description 語意搜尋）
5. 小模型（qwen2.5:1.5b / gemma2:2b）根據 Chunks 生成建議
6. 回傳建議列表
```

### 5.4 Fallback 策略

```
嘗試呼叫 /api/v1/ai/suggestions
  ├─ 成功 → 使用 AI 生成的建議
  ├─ 超時 (>3s) → Fallback 至 PAGE_CONTEXT_MAP 中的靜態 suggestions
  └─ 失敗 → Fallback 至靜態 suggestions
```

### 5.5 前端快取

- 同一頁面 + 同一 detail 的建議結果快取 5 分鐘
- 快取 key：`suggestions:${pathname}:${JSON.stringify(detail)}`
- 頁面切換時檢查快取，命中則直接使用，未命中則發起 API 請求
- 使用 `Map` 或 `sessionStorage` 存儲

## 6. LangGraph AI Pipeline

### 6.1 架構

AITask 使用 LangGraph 構建的 AI Pipeline：

```
START
  ↓
classify_intent        ← 意圖分類（rule / semantic / llm）
  ↓
matcher                ← TopIntentRAG 匹配（從 Qdrant 檢索意圖庫）
  ↓
resolve_coreference    ← 指代消解（「它」→「customers 表」）
  ↓
route_by_action_plan   ← 路由分發
  ├── direct_answer    → chat_responder    （一般聊天回覆）
  ├── tool_call        → tool_executor     （工具呼叫）
  ├── process_orch.    → bpa_orchestrator  （流程自動化）
  │                    → da_query          （資料查詢）
  │                    → ka_search         （知識庫搜尋）
  └── unknown          → chat_responder    （兜底回覆）
  ↓
memory_manager         ← 記憶管理（短期 + 長期）
  ↓
END
```

### 6.2 State 結構 (TopState)

```python
class TopState(TypedDict):
    session_id: str
    user_id: str
    mode: Literal["chat", "task"]
    messages: Annotated[list[BaseMessage], add_messages]
    current_intent: Optional[str]
    intent_confidence: float
    intent_method: Literal["rule", "semantic", "llm"]
    action_plan: Literal["direct_answer", "tool_call", "process_orchestration", "unknown"]
    matched_intent_data: Optional[dict[str, object]]
    entities: dict[str, str]
    coreference_resolved: bool
    context_entities: dict[str, str]
    active_bpa: Optional[str]
    bpa_workflow_id: Optional[str]
    bpa_state: Literal["idle", "executing", "waiting_for_user", "completed", "failed"]
    tool_results: list[dict[str, object]]
    pending_tool_calls: list[dict[str, object]]
    short_term_memory: list[dict[str, object]]
    long_term_memory: list[dict[str, object]]
    memory_turn_count: int
    protocol_version: str
    state_version: int
    checkpoint_version: int
```

### 6.3 艾企的 mode 與 action_plan

- 艾企對話使用 `mode: "chat"`
- 預期主要觸發 `direct_answer`（一般問答）和 `ka_search`（知識庫搜尋）
- 當使用者在 Data Agent 頁面時，可能觸發 `da_query`
- 頁面上下文注入 System Prompt 後，LLM 可自然理解情境

## 7. 多模型供應商支持

### 7.1 已支持供應商

AITask 支持多個 LLM 供應商：

| 供應商 | 預設 Base URL | API 路徑 |

### 7.2 模型供應商管理

前端透過「模型供應商」頁面管理（`model_providers` 集合），每個供應商可配置：

- 可用模型清單

- **預設模型**：從 `system_params` 或 `model_providers` 中取得啟用的預設模型
- **建議用途對應**：
  - 一般聊天回覆：主力模型（如 `qwen3:32b`、`llama3.2:latest`）
  - 5W1H 標記：標記模型（如 `qwen3-coder:30b`）
  - 動態建議（方案 C）：小模型（如 `qwen2.5:1.5b`、`gemma2:2b`）

## 8. Memory Agent 整合（port 8008）

### 8.1 能力

Memory Agent 提供 AI 增強記憶系統：

| 模組 | 說明 |
|------|------|
| `working_memory` | 工作記憶（當前對話的短期上下文） |
| `session_memory` | 會話記憶（跨輪次的對話狀態） |
| `recall` | 召回模組（從長期記憶中檢索相關內容） |
| `consolidation` | 離線整理（將短期記憶歸納至長期記憶） |

### 8.2 艾企的記憶策略

- 短期記憶：當前對話的最近 N 條訊息（N 由 `memory_turn_count` 控制）
- 長期記憶：透過 `memory_manager` 節點自動管理
- 跨 Session 記憶：使用者在不同頁面的對話可透過記憶模組關聯

## 10. 服務依賴與健康檢查

### 10.1 服務依賴圖

```
艾企前端
  └── Rust API Gateway (port 6500) ← 必需
        ├── ArangoDB (port 8529)   ← 必需（配置、Session、訊息）

        ├── Knowledge Agent (8007) ← 可選（RAG 建議）
        ├── Memory Agent (8008)    ← 可選（增強記憶）
        ├── Qdrant (port 6333)     ← 可選（向量檢索）
        └── Ollama (port 11434)    ← 必需（LLM 推理）
```

### 10.2 健康檢查端點

| 服務 | 端點 | 預期回應 |
|------|------|---------|
| API Gateway | `GET /health` | `{ status: "ok", services: { ... } }` |
| AITask | `GET :8001/health` | `{ status: "ok", service: "aitask" }` |
| Knowledge Agent | `GET :8007/health` | `{ status: "ok" }` |

### 10.3 降級策略

| 服務不可用 | 降級行為 |
|-----------|---------|
| AITask | 顯示錯誤提示，禁用發送按鈕 |
| Knowledge Agent | 方案 C fallback 至靜態建議 |
| Memory Agent | 不影響基本對話，只是缺少跨 Session 記憶 |
| Qdrant | TopIntentRAG 失效，fallback 至 rule-based 分類 |

## 11. 安全考量

### 11.1 認證

- 艾企對話 API 需要 JWT Token（`Authorization: Bearer <token>`）
- Token 由 Axios interceptor 自動附加
- 401 回應自動跳轉至登入頁

### 11.2 權限

- 所有已登入使用者可使用艾企助手
- 對話內容綁定 `user_key`，不同使用者間隔離
- 系統參數配置（外觀設置）目前無權限控制，未來可考慮限制管理員

### 11.3 輸入安全

- 使用者輸入經 LLM 處理，需防範 Prompt Injection
- Rust 端應對訊息長度做限制（現有 `max_tokens` 設定）
- 不允許在 System Prompt 中暴露敏感的系統資訊
