### 2.2 各模組瓶頸詳解

#### 2.2.1 graph.py（最嚴重）

**檔案**: `ai-services/kb_pipeline/graph.py`

**瓶頸點**:

| 函式                         | 行為                                             | CPU/記憶體負擔 |
| ---------------------------- | ------------------------------------------------ | -------------- |
| `_sanitize_llm_json()`     | Regex 處理、`{` 找起點、`}` 找終點、字串截取 | **高**   |
| `_repair_truncated_json()` | 修補截斷的 JSON、補 `]` 和 `}`               | **高**   |
| `_extract_single_chunk()`  | 每次 LLM 呼叫後的處理迴圈                        | **中**   |
| `extract_chunks()`         | ThreadPoolExecutor 並行處理 5 個 chunks          | **中**   |
| `_deduplicate_entities()`  | O(n) dict + string.lower() 比對                  | **中**   |

**問題程式碼範例**:

```python
# graph.py:28-40
def _sanitize_llm_json(raw: str) -> str:
    text = raw.strip()
    if text.startswith("```"):
        text = re.sub(r"^```(?:json)?\s*", "", text)
        text = re.sub(r"\s*```$", "", text)
    brace_start = text.find("{")     # 字串掃描
    brace_end = text.rfind("}")      # 字串掃描
    # ... 更多處理
    return text
```

**預估影響**: 處理 50 個 chunks 時，sanitize + parse 佔總時間 60-70%

#### 2.2.2 qdrant_ops.py（嚴重）

**檔案**: `ai-services/kb_pipeline/qdrant_ops.py`

**瓶頸點**:

| 函式         | 行為                               | CPU/記憶體負擔 |
| ------------ | ---------------------------------- | -------------- |
| `upsert()` | 建構大型 JSON payload、JSON 序列化 | **高**   |
| `scroll()` | 解析大 JSON 回應                   | **中**   |
| `search()` | 解析結果 JSON                      | **低**   |

**問題程式碼範例**:

```python
# qdrant_ops.py:72-101
def upsert(self, collection: str, points: list[Point]) -> int:
    payload = {
        "points": [
            {
                "id": p.id,
                "vector": p.vector,  # 768/1024 維浮點陣列
                "payload": {
                    "file_id": p.file_id,
                    "root_id": p.root_id,
                    "chunk_index": p.chunk_index,
                    "text": p.text[:500],        # ✅ 已優化
                    "text_full": p.text_full,    # ❌ 問題：存完整文字
                },
            }
            for p in points
        ]
    }
    # 整個 payload 序列化成 JSON string
    # 記憶體峰值 = 所有 vectors + 所有 text_full
```

**預估影響**: 每筆 upsert 的 CPU/記憶體成本中，text_full 佔 70-90%

### 3.2 P0 方案詳細說明

#### 方案 1：Qdrant Payload 縮小

**目標**: 減少每筆 payload 大小，降低網路傳輸與記憶體峰值

**現況**:

```python
# qdrant_ops.py
"payload": {
    "text": p.text[:500],        # 只存前 500 字
    "text_full": p.text_full,    # 存完整文字（可能 5KB-50KB）
}
```

**建議做法**:

| 方案               | 實作                                     | 效益           |
| ------------------ | ---------------------------------------- | -------------- |
| **A (推薦)** | 只存 `text[:200]`，完整文字存 S3/MinIO | 省 90% payload |
| **B**        | 只存 `text[:500]`，完全不存完整文字    | 省 80% payload |
| **C**        | 只存 `text[:500]`，其餘從原文檔案讀取  | 平衡方案       |

**對準確率影響**: 無（向量已存入，payload 純顯示用）

---

#### 方案 2：Embedding 批次優化

**目標**: 減少網路來回次數

**現況**:

```python
# pipeline.py:118
BATCH_SIZE = 10  # 太小
```

**建議**:

```python
BATCH_SIZE = 100  # 調大
```

**效益**: 50 個 chunks，從 5 次網路來回 → 1 次

## 5. Qdrant Payload 說明

### 5.1 Payload 結構

```
Qdrant Point：
{
    id: 123456,
    vector: [0.1, -0.3, 0.7, ...],  ← 768/1024 維向量（用於相似度計算）
    payload: {                         ← 純顯示用metadata
        "file_id": "abc123",
        "root_id": "kb1",
        "chunk_index": 5,
        "text": "這是文本片段前500字...",
        "text_full": "這是完整文本（可能5KB-50KB）..."  ← 可移除
    }
}
```

### 5.2 向量 vs Payload 的角色

| 組成              | 作用                                  | 影響搜尋準確率？       |
| ----------------- | ------------------------------------- | ---------------------- |
| **vector**  | 數學向量，用於 Cosine Similarity 計算 | ✅**決定準確率** |
| **payload** | 文字內容，用於顯示給用戶              | ❌**無關**       |

### 5.3 Payload 縮小不會影響準確率的原因

1. **向量化在存入前完成**

   - `text` → Embedding Model → `vector`（已存入 Qdrant）
   - Payload 只是「順便」儲存的文字副本
2. **搜尋只比較 vector**

   - Qdrant 只用 vector 做相似度計算
   - Payload 不參與任何數學運算
3. **`text[:500]` 和 `text_full` 產生的向量相同**

   - 因為 embedding model 處理的是同一段文字
   - 只是選擇存多少「顯示用」的文字

## 7. 總結

### 7.1 關鍵發現

1. **最大瓶頸在 graph.py**（LLM 回應處理），佔總時間 60-80%
2. **Payload 過大**（存 text_full）是記憶體峰值主因
3. **PyO3 效益高**的模組：graph.py 和 qdrant_ops.py
4. **Celery 本身不是瓶頸**，是同步 blocking I/O 造成 worker 空轉

### 7.2 建議優先順序

| 順序 | 行動                | 理由             |
| ---- | ------------------- | ---------------- |
| 1    | Payload 縮小        | 立即見效，風險低 |
| 2    | 批次優化            | 簡單改動，效益高 |
| 3    | PyO3 sanitize/parse | 最大加速潛力     |
| 4    | PyO3 payload build  | 第二大加速潛力   |

### 7.3 非 PyO3 的替代方案

| 問題           | 非 Rust 替代                 | 說明                       |
| -------------- | ---------------------------- | -------------------------- |
| JSON 處理      | `orjson` (純 Python C ext) | 可獲得 10x 加速，不需 Rust |
| Payload 序列化 | 減小 payload                 | 最簡單有效                 |
