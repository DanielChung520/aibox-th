## 1. 文件目的

本文件不是功能規格，也不是實作計畫。

本文件的目的只有一個：

> **在進入實作前，先確立艾企未來 3～5 年可持續演化的核心架構原則。**

避免系統再次落入「補一個功能、再補一個功能，最後形成彼此衝突的拼裝架構」的循環。

本草案依據以下核心精神整理：

- AI 的本質是**輔助，不是替代**
- 知識的邊界，就是安全的邊界
- 企業 AI 的根本目標是**穩定、精確、可追溯**
- 企業問題真正有價值的部分，不在單點資料，而在**關係路徑與證據鏈**
- 系統必須能面對**未知情境**，而不是只處理預先定義過的問題

---

## 2. 我們真正要解的問題

### 2.1 不是「讓 AI 更會回答」

艾企未來架構的核心問題，不是：

- 如何讓 LLM 記更多內容
- 如何讓 SQL 生得更準
- 如何讓 Intent Catalog 更完整
- 如何讓 Graph 更大
- 如何讓 RAG 找更多文件

這些都只是子問題。

### 2.2 真正的核心問題

艾企要解的是：

> **當使用者提出一個過去從未定義過、跨表、跨流程、跨角色的未知問題時，系統如何仍然能在有限記憶、有限成本、有限風險下，逐步縮小不確定性，沿著證據與結構路徑推進，並在必要時停下來向使用者澄清。**

這是控制問題，不只是查詢問題。

---

## 3. 艾企未來架構的唯一中心

## 3.1 中心原則

艾企未來架構不應以以下任何單點能力為中心：

- Intent Catalog
- NL→SQL Pipeline
- HybridRAG
- Graph Database
- User Behavior Log

這些都重要，但都不是中心。

### 正確的中心是：

# **Bounded Inquiry / Decomposition**
# **有界探詢與分解引擎**

也就是：

> **系統的第一責任，不是立刻回答問題，而是把問題轉化成一連串可驗證、可停止、可追溯的小步。**

---

## 4. 設計總原則

### 4.1 AI 只能在邊界內工作

AI 不可以將整個企業世界視為任意推理空間。

AI 每一次檢索、推理、生成，都必須受到以下至少一種邊界約束：

- 知識邊界（knowledge root / ontology / domain）
- 結構邊界（schema / relation / legal path）
- 行為邊界（user 當前頁面 / 最近操作 / working set）
- 成本邊界（top-k / traversal depth / query budget / token budget）
- 責任邊界（需要人確認的決策不可越權）

### 4.2 回答不是目的，收斂問題才是目的

艾企的第一責任是：

1. 找出目前缺少什麼關鍵資訊
2. 判斷下一步最值得確認的證據是什麼
3. 以最小成本縮小範圍
4. 在證據不足時要求澄清，而不是硬生成

### 4.3 所有子模組都只能提供「候選與證據」

任何單一模組都不應成為真相來源。

| 模組 | 正確角色 |
|------|----------|
| HybridRAG | 提供候選知識片段與來源證據 |
| Graph Traversal | 提供合法路徑與鄰近關聯 |
| NL→SQL | 提供某一步資料存取能力 |
| Intent Memory | 提供歷史上可能有用的先驗模式 |
| Behavior Signals | 提供使用者當前關注範圍 |
| LLM | 協助分解、對映、澄清，不直接拍板 |

### 4.4 系統必須可重放、可審計、可回溯

每一個高價值回答，理論上都應能回溯：

- 問題如何被拆解
- 使用了哪些證據
- 經過了哪些路徑
- 為何停在這裡
- 哪一步需要人確認

企業 AI 若不可追溯，就不可治理。

## 5. 為何現有常見架構方向不足以支撐未來

### 5.1 Intent Catalog 中心的問題

若架構以「先分類到既有 intent」為中心，則未知問題會被硬塞進最近似類別。

結果：

- 看起來像理解，其實是誤歸類
- 一旦第一步錯，後面所有路徑都會錯
- 越補 catalog，越把系統綁死在既有場景

### 5.2 NL→SQL 中心的問題

很多企業問題根本不是 SQL 問題，而是：

- 關聯問題
- 路徑問題
- 來源追溯問題
- 多步驗證問題

NL→SQL 很重要，但它只是其中一種執行手段。

### 5.3 HybridRAG 中心的問題

檢索只能取回材料，不能決定：

- 目前缺少什麼資訊
- 下一步該往哪裡查
- 何時該停
- 何時該問 user

所以 RAG 不能成為整個系統的思考中心。

### 5.4 巨大全域圖譜中心的問題

如果把 Graph 視為萬能宇宙，將導致：

- 不可控遍歷
- 成本爆炸
- 無法判定當前哪條邊真的有價值
- 容易把「可連接」誤認成「有意義」

Graph 是約束與候選來源，不是萬能答案機器。

## 6. 未來架構的五層模型

艾企未來架構建議採用以下五層：

```
┌────────────────────────────────────────────────────────────┐
│ 第5層：Learning Layer（學習層）                            │
│ 成功路徑沉澱 │ working set 優化 │ anchor 對映演化 │ 行為統計   │
├────────────────────────────────────────────────────────────┤
│ 第4層：Execution Layer（執行層）                           │
│ NL→SQL │ Graph Query │ Hybrid Retrieval │ Tool Calling │ Validate │
├────────────────────────────────────────────────────────────┤
│ 第3層：Inquiry Controller（探詢控制層）                    │
│ 問題分解 │ 下一步選擇 │ 成本控制 │ 停止條件 │ 澄清決策         │
├────────────────────────────────────────────────────────────┤
│ 第2層：Working Set Layer（工作集層）                       │
│ 當前頁面 │ 最近操作 │ 活躍 tables │ 活躍 anchors │ 候選證據       │
├────────────────────────────────────────────────────────────┤
│ 第1層：Evidence & Structure Layer（證據與結構層）          │
│ Schema Graph │ Entity Anchors │ Knowledge Graph │ Documents │ Cache │
└────────────────────────────────────────────────────────────┘
```

---

## 7. 各層職責

### 7.1 第1層：Evidence & Structure Layer

這一層不是「答案層」，而是「可被調用的證據底座」。

包含：

- Ragic schema 與 relation graph
- 跨表實體錨點（item_id / supplier_id / customer_id / batch_id 等）
- 知識圖譜與向量化文件
- 前端當前頁面可見資料
- 快取與局部資料狀態

職責：

- 定義可行路徑
- 提供原始證據
- 定義不應越過的邊界

### 7.2 第2層：Working Set Layer

Working Set 是艾企未來架構的關鍵。

它的目的不是記更多，而是：

> **只保留當前問題真正需要的局部上下文。**

來源包括：

- 使用者目前所在頁面
- 最近 5～20 個 actionTrail 事件
- 當前打開的 table / row / field
- 最近命中的 intent / anchor / document
- 已驗證與未驗證的中間結論

Working Set 應該取代「把大量上下文灌進 prompt」的做法。

### 7.3 第3層：Inquiry Controller

這是整個系統中心。

它負責：

1. 接收使用者問題
2. 建立 working set
3. 判斷目前最缺的資訊
4. 選擇下一步應該調用哪個子能力
5. 決定要不要繼續、停止、或要求澄清

這一層的輸出不應是「最終答案」，而應是：

- 下一步查什麼
- 為什麼查
- 使用什麼邊界
- 預期得到什麼證據

### 7.4 第4層：Execution Layer

所有執行能力放在這一層，包括：

- HybridRAG
- NL→SQL / AQL
- Graph Traversal
- Tool calling
- Validation / Guardrail

這一層不做最終決策。
它只接受 Inquiry Controller 的有界指令，回傳結果與 provenance。

### 7.5 第5層：Learning Layer

學習不是累積更多問題，而是沉澱：

- 哪些 decomposition pattern 有效
- 哪些 anchor mapping 常成功
- 哪些行為序列代表哪種問題空間
- 哪些下一步通常最有價值

這一層輸出的不是直接答案，而是：

- 更好的先驗
- 更好的 working set 建立策略
- 更好的下一步排序

---

## 8. 三種關鍵圖，不再平行競爭，而是角色分工

### 8.1 Structural Graph（結構圖）

來源：Ragic schema relations / table-field graph

用途：

- 定義合法 traversal path
- 定義 join / dependency / relation 邊界
- 提供 anchor 候選

不是用途：

- 不直接替代意圖理解
- 不直接產生回答

### 8.2 Behavioral Graph（行為圖）

來源：actionTrail / recent UI path / session trace

用途：

- 推斷 user 當前問題空間
- 調整下一步優先順序
- 建立 working set

不是用途：

- 不直接當作真實知識
- 不直接主導資料邏輯

### 8.3 Intent / Experience Graph（意圖與經驗圖）

來源：成功 query、feedback、人工定義模板、歷史分解結果

用途：

- 提供先驗模式
- 提供成功範例
- 提供常見 next-step 建議

不是用途：

- 不作為未知問題的最終分類器
- 不應壓過當前證據

---

## 9. Cross-Table Entity Anchor 的地位

未來架構中，Anchor 不是附屬物，而是第一級公民。

### 9.1 Anchor 定義

Anchor 是跨表、跨流程、跨層共同指向的業務實體，例如：

- item_id / material_code / part_no
- supplier_id
- customer_id
- batch_id
- order_id

### 9.2 Anchor 的作用

Anchor 用來把以下三者連起來：

- 結構圖（哪些表承載這個實體）
- 行為圖（使用者最近正在看哪個實體）
- 意圖圖（哪些問題常圍繞這個實體發生）

### 9.3 未來原則

未知問題進來時，系統的首要任務之一，通常不是直接找答案，而是：

> **先找出這個問題的活躍 Anchor 是誰。**

---

## 10. 艾企如何面對未來未知情境

未來的複雜問題，不可能全部預定義。

因此系統必須具備以下能力：

### 10.1 不靠預設答案，而靠可重複的方法

系統應處理的是：

- 問題如何拆解
- 證據如何收集
- 路徑如何縮小
- 何時停下來

而不是預先擁有每個問題的答案。

### 10.2 面對未知問題的標準流程

```
使用者提出未知問題
    ↓
建立 working set（頁面 + 行為 + cache + anchor 候選）
    ↓
識別目前最缺的資訊
    ↓
沿著結構圖或知識圖取得下一步證據
    ↓
若證據不足，向 user 澄清
    ↓
若證據足夠，形成可回溯答案
```

### 10.3 未知問題的成功關鍵

不是更大的模型，而是：

- 更好的工作集
- 更好的 decomposition
- 更好的邊界控制
- 更好的停止條件

| 模組 | 未來定位 | 說明 |
|------|----------|------|
| `graph_query.py` | 核心底座 | 保留，升級為有權重、有 anchor awareness 的結構路徑引擎 |
| `hybrid_rag/service.py` | 核心底座 | 保留，升級為證據檢索層，而不是最終回答層 |
| `actionTrail.ts` | 核心底座 | 保留，作為 working set 與行為收斂的信號來源 |

| `intentEngine.ts` | UX 薄層 | 保留做前端提示與回饋，不承擔真正的學習中心 |

## 12. 設計紅線（不可違背）

### 12.1 不允許單一模組直接主導答案

任何單一模組都只能輸出：

- 候選
- 證據
- 路徑
- 風險

不能直接成為最終定論。

### 12.2 不允許以巨大上下文取代 working set

上下文過大不代表更懂，只代表更模糊、更昂貴、更危險。

### 12.3 不允許沒有 provenance 的高價值回答

重要回答若不可追溯來源，則不可視為可靠企業回答。

### 12.4 不允許為了覆蓋率犧牲邊界

企業 AI 寧可保守、要求澄清，也不能越界亂猜。

---

## 13. 近期架構討論的正確順序

在進入實作前，後續討論應按以下順序進行：

### Phase A：先定義 Inquiry Controller

必須先回答：

- 它的輸入輸出是什麼？
- working set 怎麼表示？
- 下一步選擇如何表示？
- 停止條件有哪些？

### Phase B：再定義 Anchor 模型

必須先回答：

- 哪些 Anchor 是第一批核心實體？
- 如何從現有 schema relations 導出？
- 如何讓 Behavior / Intent / Structure 三者共享 anchor？

### Phase C：最後才討論具體執行能力如何接入

例如：

- NL→SQL 怎麼改造
- HybridRAG 怎麼接入
- Graph traversal 怎麼加權

順序不能反過來。

---

## 14. 本草案的結論

艾企未來架構的核心，不應再是：

- 更完整的意圖目錄
- 更大的圖譜
- 更強的 SQL 生成
- 更大的 RAG 上下文

而應是：

> **一個能在企業知識邊界內，根據 user 當前位置與行為，建立局部工作集，逐步分解未知問題，沿著證據路徑推進，並在必要時停下來請求澄清的有界探詢系統。**

這才是艾企真正有機會走向未來、而不是再次陷入拼裝式架構的中心。
