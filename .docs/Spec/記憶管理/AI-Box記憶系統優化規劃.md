```
┌─────────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────────┤
│  第4層：團隊共享層（Team Memory Layer）                           │

│  第3層：長期記憶層（Persistent Memory Layer）                      │
│  四種類型 │ MEMORY.md 索引 │ Vector DB │ Graph DB               │
├─────────────────────────────────────────────────────────────────┤
│  第2層：工作記憶層（Working Memory Layer）                         │

├─────────────────────────────────────────────────────────────────┤
│  第1層：會話記憶層（Session Memory Layer）                        │

## 2. 效能瓶頸分析

### 2.1 現有架構的潛在瓶頸

根據外部討論與技術審閱，現有架構存在以下優化空間：

#### 2.1.1 同步寫入阻塞

**現況**：
```
用戶消息 → 模型響應 → Stop Hooks → extractMemories()
                                              │
                                              ▼
                                    直接寫入 Markdown 文件
                                              │
                                              ▼
                                    更新 MEMORY.md 索引
                                              │
                                              ▼
                                    寫入 Vector DB
                                              │
                                              ▼
                                    寫入 Graph DB
```

**問題**：
- 所有寫入操作在主模型回應流程中同步執行
- 記憶提取延遲用戶回應時間
- 多個存儲後端串列訪問，增加總延遲

#### 2.1.2 被動式記憶提取

**現況**：
- Stop Hooks 觸發後才執行 `extractMemories()`
- 依賴主模型的判斷決定是否提取記憶
- 缺乏主動的「標籤、篩選、歸納」機制

**問題**：
- 可能遺漏重要記憶片段
- 主模型專注當前任務，可能忽略長期有用的資訊
- 無法根據記憶類型分發到不同的存儲後端

#### 2.1.3 離線整理的腳本式限制

**現況**：
- 四階段整理流程（Orient → Gather → Consolidate → Prune）是腳本式執行
- 缺乏「理解」與「推理」能力
- 無法自動識別需要深度整理的主題

#### 2.1.4 召回機制依賴通用模型

**現況**：
- `selectRelevantMemories()` 使用輕量模型（如 Sonnet）選擇相關記憶
- 無領域特定的意圖識別能力
- 可能無法精確區分「金融查詢」與「一般問答」

## 3. 優化方向建議

### 3.1 優化方向總覽

| 方向 | 描述 | 效益 | 風險 | 優先級 |
|------|------|------|------|--------|
| **委派代理** | 記憶提取異步委派給獨立 Agent | 高 | 低 | **P0** |
| **記憶分發器** | 根據類型分發到不同存儲後端 | 高 | 低 | **P0** |
| **Graph DB 動態更新** | 記憶寫入時同步更新圖譜 | 中 | 中 | P1 |
| **Agent式整理** | 離線整理從腳本升級為 Agent | 高 | 中 | P2 |
| **意圖小模型 (Eb-MM)** | LoRA 微調做召回預導航 | 高 | 高 | P3 |

### 3.2 P0：委派代理（Memory Agent Delegate）

#### 3.2.1 概念

將記憶提取從同步阻塞改為異步委派，讓主模型專注即時回應。

#### 3.2.2 架構對比

```
現況：                        委派後：

主模型回應流程                主模型回應流程
      │                            │
      ▼                            ▼
extractMemories() ──────▶  extractMemories()
      │                            │
      ▼                            ▼
直接處理 (blocking)          發送到 Message Queue
                                  │
                                  ▼
                            Memory Agent (獨立進程)
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
              INDEX.md      Vector DB       Graph DB
```

#### 3.2.3 預期效益

| 指標 | 現況 | 委派後 |
|------|------|--------|
| 主模型回應延遲 | +100-500ms | +0ms |
| 記憶處理並行度 | 0 (串列) | N (並行) |
| 系統彈性 | 低 | 高 (可獨立擴展) |

---

### 3.3 P0：記憶分發器（Memory Dispatcher）

#### 3.3.1 概念

在委派代理基礎上，根據記憶類型自動分發到最適合的存儲後端。

#### 3.3.2 分發邏輯

```
記憶片段
    │
    ▼
┌─────────────────┐
│  類型判斷       │
│  (user/feedback │
│   /project/     │
│   reference)   │
└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────────────────────┐
│                                                     │
│  user      → user/ 目錄 (Markdown)                  │
│  feedback  → feedback/ 目錄 (Markdown)              │
│  project   → project/ + Graph DB (建立關聯)          │
│  reference → reference/ + Graph DB (建立關聯)        │
│                                                     │
│  + 所有類型同步寫入 Vector DB (支援語意召回)        │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### 3.3.3 預期效益

- **自動分類**：減少人工維護成本
- **優化存儲**：不同類型使用最適合的存儲方式
- **Graph DB 增值**：自動建立 project/reference 的關聯圖

---

### 3.4 P1：Graph DB 動態更新

#### 3.4.1 概念

在記憶寫入時，同步更新 Knowledge Graph，建立「人-事-時-地-物」的關聯邊。

#### 3.4.2 觸發時機

| 記憶類型 | Graph DB 更新內容 |
|----------|-----------------|
| user | 創建用戶節點，建立與反饋記憶的關聯 |
| feedback | 創建反饋節點，建立與相關項目的關聯 |
| project | 創建項目節點，建立與時間、人物的關聯 |
| reference | 創建引用節點，建立與引用來源的關聯 |

#### 3.4.3 預期效益

- 支援圖遍歷召回（如「查詢用戶的所有相關反饋」）
- 增強 HybridRAG 的 Graph Search 能力
- 為未來的 LoRA 微調提供結構化樣本

---

### 3.5 P2：Agent式離線整理

#### 3.5.1 概念

將第5層從「腳本式整理」升級為「Agent式整理」，具備理解與推理能力。

#### 3.5.2 現有四階段 vs Agent式

| 現有階段 | 腳本式行為 | Agent式行為 |
|----------|-----------|------------|
| Orient | 掃描重複主題 | 理解主題關聯性 |
| Gather | 查看日誌矛盾 | 主動驗證事實正確性 |
| Consolidate | 合併文件 | 重構知識表示 |
| Prune | 確保索引限制 | 智能判斷保留價值 |

#### 3.5.3 預期效益

- 更好的知識整合
- 自動識別需要深度整理的區域
- 為 LoRA 提供更高質量的訓練樣本

---

### 3.6 P3：意圖小模型 (Eb-MM)

#### 3.6.1 概念

使用 LoRA 微調訓練一個專門用於「記憶意圖識別」的小模型，部署在本地設備。

#### 3.6.2 應用場景

```
用戶輸入
    │
    ▼
┌─────────────────┐
│  Eb-MM (LoRA)   │  ← 取代 Sonnet 做意圖識別
│  - 金融數據查詢 │
│  - 代碼相關     │
│  - 一般問答     │
└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────┐
│                                     │
│  金融查詢 → 直接路由到 Graph DB     │
│  代碼相關 → 路由到 project/ 記憶    │
│  一般問答 → 混合召回策略            │
│                                     │
└─────────────────────────────────────┘
```

#### 3.6.3 前置條件

| 條件 | 說明 |
|------|------|
| 樣本數量 | 至少 10,000 個高質量「意圖-動作」對 |
| 樣本質量 | 需要自動標註，品質分數 > 0.8 |
| 硬體需求 | 可運行 7B 模型 (8GB VRAM) |

#### 3.6.4 預期效益

- **本地部署**：不依賴外部 API
- **低延遲**：比 Sonnet 更快的召回速度
- **領域專精**：比通用模型更準確的意圖識別

## 5. 關鍵技術決策

### 5.1 Message Queue 選擇

| 選項 | 優點 | 缺點 | 建議 |
|------|------|------|------|
| **Redis** | 現有架構已有，簡單 | 不如 RabbitMQ 可靠 | ✅ 推薦 |
| RabbitMQ | 功能完整，可靠性高 | 需要額外部署 | 過渡期後考慮 |
| Kafka | 高吞吐 | 過度複雜 | 不需要 |

### 5.2 樣本標註策略

| 階段 | 標註方式 | 品質門檻 |
|------|----------|----------|
| Phase 2 | 腳本輔助 + 人工抽檢 | 分數 > 0.7 |
| Phase 3 | Agent 自動標註 + 抽檢 | 分數 > 0.8 |
| Phase 4 | 全自動標註 | 分數 > 0.85 |

### 5.3 LoRA 微調時機評估

| 評估維度 | 評估標準 | 達標與否 |
|----------|----------|----------|
| 樣本數量 | ≥ 10,000 個高質量樣本 | 需累積 |
| 樣本品質 | 平均品質分數 > 0.8 | 需驗證 |
| 硬體資源 | 8GB VRAM (如 MBP AMD GPU) | ✅ 已滿足 |
| 需求驗證 | Agent式整理穩定運行 > 1 月 | 需等待 |

## 6. 風險分析

### 6.1 技術風險

| 風險 | 影響 | 緩解措施 |
|------|------|----------|
| Queue 消息丟失 | 記憶未保存 | 持久化 + 重試機制 |
| 記憶分類錯誤 | 存到錯誤的後端 | 人工審核 + 反饋機制 |
| Graph DB 更新衝突 | 圖結構不一致 | 樂觀鎖 + 版本控制 |
| LoRA 樣本質量不足 | 微調效果差 | 先累積樣本再微調 |

### 6.2 架構風險

| 風險 | 影響 | 緩解措施 |
|------|------|----------|
| 委派代理過於複雜 | 維護成本高 | 保持簡單，逐步擴展 |
| 過早引入 LoRA | 浪費資源 | 嚴格評估樣本質量的達標 |

## 7. 總結

### 7.1 核心建議

1. **立即開始**：委派代理 + 分發器是最低風險、最高效益的切入點
2. **積累數據**：在 Phase 1-2 專注積累高質量的 KAIROS 日誌和樣本
3. **按需進化**：等樣本充足後再考慮 LoRA 微調

### 7.2 與現有 HybridRAG 優化的關係

| 優化項目 | 記憶系統的受益 |
|----------|----------------|
| Payload 縮小 | 減少網路傳輸，Vector DB 查詢更快 |
| PyO3 加速 | 記憶處理 (sanitize/parse) 更快 |
| async/await | 記憶委派寫入不阻塞 |

### 7.3 最終願景

```
┌─────────────────────────────────────────────────────────────────┐
│                        AI-Box 記憶系統                            │
│                                                                 │
│   即時回應層 (Session/Working Memory)                           │
│           │                                                     │
│           ▼                                                     │
│   智能委派層 (Memory Agent Delegate)                            │
│           │                                                     │
│           ▼                                                     │
│   自動分發層 (Memory Dispatcher)                                 │
│           │                                                     │
│           ▼                                                     │
│   結構化存儲層 (Markdown + Vector DB + Graph DB)                │
│           │                                                     │
│           ▼                                                     │
│   演化整理層 (Agent式整理 + LoRA 微調)                          │
│                                                                 │
