請介紹 Claude Code 的六維記憶體系分別包含哪些層級？

**Claude Code 的六維記憶體系包含以下六個層級，從最基礎的靜態規則到最高級的離線重塑，構成了一套非常完整的記憶架構**：

* **指令記憶（規則級記憶）** **：對應系統中的 **`cloud.md` 文件，這是一套 **多層級、優先級遞增的靜態指令加載系統** **。它可以理解為用戶提前寫好的行為準則或規矩，用來告訴 AI 該怎麼做事**。
* **短期記憶** **：這是** **當前會話裡的完整對話歷史** **，每一條消息都會未經壓縮地保存在內存（記憶體）裡**。
* **工作記憶** **：主要與** **當前正在執行的任務相關** **，包含任務的進度、偏移量以及機器的響應狀態等資訊**。
* **長期記憶** **：這是記憶體系中** **最核心的部分** **。它是一個** **基於磁盤 Markdown 文件構建的分層知識庫引擎** **，系統會在用戶目錄下創建專門的記憶文件夾，並嚴格按照四種類型來組織知識：用戶畫像 (user)、行為反饋 (feedback)、項目上下文 (project) 以及外部引用 (reference)**。
* **摘要記憶（壓縮級記憶）** **：當對話過長導致 token 快要達到上限時，系統會觸發壓縮。Claude Code 透過獨特的 ** **Session Memory 機制** **，在後台子代理中持續維護一份會話筆記，壓縮時會** **直接用這份漸進式維護的筆記替代臨時生成的摘要** **，從而保留更高的摘要品質**。
* **休眠重塑記憶（離線級記憶）** **：又稱為 ** **Auto Dream（自動做夢）機制** **。當滿足特定條件（例如距離上次整合過去24小時且產生了5個不同會話的新記憶）後，系統會自動啟動整合流程，****像人類覆盤整理筆記一樣，把碎片化的記憶進行清理、合併、去除矛盾，最後更新全局索引**。

Auto Dream 機制是如何像人類做夢一樣自動整理記憶的？

**Claude Code 的 Auto Dream（自動做夢）機制，又稱為休眠重塑記憶，是其記憶體系中最具想像力的離線級記憶設計**,**。它就像人類在休息時大腦會自動整理記憶碎片一樣，透過定期的「覆盤整理」，將碎片化的記憶進行清理、合併、去除矛盾，並更新全局索引**,**。**

**這個機制的具體運作方式包含以下幾個核心環節：**

**1. 嚴格的觸發條件（雙重門控）**整合記憶是一個重量級操作，需要掃描所有記憶文件、讀取日誌、分析矛盾與合併重複，如果每次對話都觸發，會帶來不可接受的成本和延遲**。因此，系統設定了雙重門控預值：必須距離上次整合至少過去 ** **24 小時** **，並且在此期間至少有 ****5 個不同的會話**產生了新記憶，兩個條件同時滿足時才會啟動**。**

**2. 模擬人類思維的四階段整理流程**Auto Dream 啟動後會經歷四個階段，完全模擬了人類「先看全局、再收集新資訊、然後合併整理、最後精簡索引」的筆記整理思維**：**

* **Orient（定向探索）** **：子代理會先瀏覽記憶目錄，檢視現有的文件和記憶索引狀態，並尋找是否有重複或近似的主題**,**。**
* **Gather（資訊收集）** **：查看最近的日誌，檢查舊記憶是否與代碼庫的當前狀態產生矛盾**。必要時，系統還會使用精確的搜尋詞來檢索轉錄文件，但不會進行寬泛掃描**。**
* **Consolidate（整合）** **：將新的資訊合併到已有的主題文件裡，避免創建近似的副本**。這裡有一項關鍵規則：相對日期必須轉成絕對日期；而一旦發現被推翻的舊事實，系統會 **直接刪除** **，而不是僅標註為過時**。
* **Prune and Index（修剪和更新索引）** **：清理並壓縮索引文件（**`memory.md`），刪除陳舊的指標、壓縮冗長的條目並解決矛盾**。系統會確保索引文件保持在 200 行以內，且每行索引不超過 150 個字元**,**。**

**3. 防止衝突的精巧「鎖機制」**為了防止多個 Claude Code 實例在同一時間觸發 Auto Dream，系統使用了一個精巧的鎖文件機制**。該文件的修改時間代表上次整合的時間，文件內容則是持有該鎖的進程 ID（PID）**。在獲取鎖時，系統會進行 CAS（Compare-And-Swap）競爭檢測，如果發現有其他進程正在嘗試獲取鎖，就會自動退讓**。如果整合過程發生錯誤，鎖機制還具備回退功能，將文件的修改時間恢復至之前的值，確保下次能正常觸發**。

**2. 選擇性與按需注入的擴展機制**與許多 AI 助手「一股腦加載所有指令」不同，Claude Code 的指令記憶是**選擇性、按需、分層注入上下文**的，這對執行效率至關重要**。它支援三種進階擴展：**

* **遞歸包含 (Include)** **：允許模塊化組織規則，避免把所有規則堆在一個大文件裡（最多遞歸 5 層，並有循環檢測防護）**。

* **嵌套記憶附件** **：當工具訪問特定目錄時，系統會自動加載該目錄的額外規則**。

* **通道 A（指令記憶）** **：負責注入 **`cloud.md` 這種由用戶編寫、內容多變需頻繁更新的規則。它被包裝成 `system reminder`，作為 **對話列表的第一條用戶消息注入** **，而不是放在系統提示陣列中**。
* **通道 B（行為規範）** **：負責注入系統內建的記憶操作指南（告訴模型怎麼保存和召回記憶）。這部分相對穩定，才真正放入系統提示陣列中**。**這種分離設計不僅讓穩定的系統規範可以被** **全會話緩存** **（不受用戶修改規則影響，互不干擾），也讓 Token 預算分配更加靈活**。

**4. 寧可犧牲實時性也要保證「確定性」**在緩存管理的細節上，來源指出系統對 `cloud.md`**刻意不支援熱重載（Hot Reload）**。如果用戶在對話中途手動修改了磁盤上的指令文件，在緩存被清除前，模型是看不到這些改動的**。這種設計取捨是為了避免複雜的一致性問題——防止模型在響應過程中規則突然改變，從而****確保 AI 行為的高度可預測性與確定性**。

**優先級的加載邏輯與設計巧思：**來源指出，這套四層優先級體系最值得注意的地方在於它的**加載順序**。系統運作時，會先從當前工作目錄（CWD）向根目錄遍歷收集所有規則文件，然後「反轉順序」，改成由根目錄向當前工作目錄的方向來進行處理**。**

**在 Claude Code 的「指令記憶」架構下，系統不僅支援多層級的靜態規則（如 **`cloud.md`）加載，更採用了**雙軌注入（Dual-track injection）**的關鍵設計，將「用戶指令」與「系統行為規範」的注入通道完全分離**。**

**來源指出，許多人會想當然地以為所有的記憶內容都是透過 system prompt 注入模型的，但實際上，這是一個** **深思熟慮的工程決策** **，系統具體將注入分成了兩條獨立的通道**：

* **通道 A（指令記憶通道）：** 專門負責注入用戶編寫的 `cloud.md` 指令內容**。由於這些是用戶自定義的規則，****內容多變且需要頻繁更新**，系統 **不會將其放入 system prompt 數組中** **，而是將它作為對話列表的** **第一條 user message 注入** **，並使用 **`system reminder` 標籤進行包裹**。**
* **通道 B（行為規範通道）：** 專門負責注入系統內建的行為規範，也就是告訴模型目前有哪些記憶類型、該如何保存與召回等操作指引**。因為這些內容** **相對穩定** **，它們才是****真正被放入 system prompt 數組中**的內容，並透過 `system prompt section` 函數進行注入**。**

**來源認為，這種將指令與規範徹底分離的設計，帶來了幾個顯著的工程優勢：**

* **極致的緩存效率：** 兩條通道互不干擾。通道 B 的系統行為規範在**整個會話中只會計算一次並緩存下來**。因此，即使你在專案中頻繁修改 `cloud.md` 文件，也不會觸發系統重新計算龐大的行為規範，大幅節省了運算資源**。**
* **獨立的策略與 Token 控制：** 將靜態的系統準則與動態的用戶規則分開後，系統可以在 **緩存策略上進行獨立管理** **，並且在 ****Token 預算分配上也擁有更高的靈活性**。

**一、 系統特性：嚴格邊界與高穩定性工程架構**

**1. 嚴格的資訊邊界（知道「不該記什麼」）**系統對長期記憶設定了極其嚴格的邊界，明確規範只有四種資訊（用戶畫像、行為反饋、項目上下文、外部引用）值得被記住**。系統** **明文禁止儲存代碼模式、架構分析、文件路徑或 Git 歷史等資訊** **，因為這些都可以直接從代碼庫中推導出來**。這種將代碼視為「最權威來源」的設計理念，避免了記憶系統退化成充斥過時資訊和矛盾的垃圾場，確保了記憶的高訊噪比**。**

**2. 雙軌注入與緩存一致性（保障行為可預測性）**為了兼顧效能與穩定性，系統在將記憶注入給模型時採用了**「雙軌注入」**設計：用戶編寫的動態指令（如 ** **cloud.md** **）透過對話消息通道注入，而系統內建的穩定行為規範則放入 System Prompt 中** **。** **更特別的是，系統**刻意不支援 `cloud.md` 的熱重載（Hot Reload）**。如果在對話中途修改了磁碟上的規則文件，模型在緩存清除前是不會看見改動的**。這種寧可犧牲部分即時性也要保證「確定性」的取捨，是為了避免在模型生成響應的過程中規則突然改變，導致 AI 行為變得不可預測**。

**3. 非阻塞的非同步協作機制**無論是每輪對話前的記憶預取（Prefetch）、對話後的記憶提取（Extract Memories），還是會話記憶（Session Memory）的維護，**全都交由後台子代理（Sub-agent）非同步執行**。這些後台任務會在不阻塞主流程、用戶無感遲延的情況下運作，並透過精確的游標推進與鎖機制，避免主代理與子代理同時寫入造成的衝突**。**

**4. 堅守 API 協議的不變量（API Invariants）**在進行 Session Memory 的對話壓縮時，系統不僅僅是簡單的截斷加摘要，而是引入了嚴密的演算法，自動檢測並調整保留的邊界**。這確保了** **不會把工具調用的請求與結果（Tool Use/Result）切斷，也不會破壞流式響應中的思考區塊（Thinking Block）關聯性** **，嚴格遵守底層 API 的協議要求**。

**二、 安全防護機制：防逃逸、防洩漏與嚴格隔離**

**作為一款有權限讀寫本地文件甚至與團隊共享資料的工具，Claude Code 在安全設計上設置了多道防線：**

**1. 子代理的「權限沙盒」**在後台負責提取記憶的子代理擁有極為受限的權限：它被**禁止執行寫入性質的 Shell 命令、不能調用 MCP 工具，也不能觸發其他代理**。它的寫入操作被嚴格限制在專屬的記憶目錄路徑內，防止子代理在背景執行時對系統造成破壞**。**

**2. 團隊記憶的「防逃逸」與「敏感審查」**當涉及跨終端與團隊成員同步記憶時，安全性標準會被拉到最高檔次**：**

* **路徑安全防護（防 Symlink 逃逸）** **：為防止惡意代碼庫利用符號連結（Symlink）指向敏感目錄（如 **`~/.ssh`）來竊取或覆蓋資料，系統在寫入前會進行字串級別與真實文件系統級別的雙重路徑解析，並直接拒絕懸空的符號連結，甚至防禦了 URL 編碼與 Unicode 全角字元攻擊**。**
* **敏感數據攔截** **：在將記憶寫入團隊共享目錄或推送到伺服器前，系統會運行正規表示式與關鍵詞過濾器，一旦偵測到 GitHub PATs 或 AWS Access Token 等敏感密鑰，就會直接攔截，防止機密外洩到團隊共用空間**。
* **刪除不傳播** **：如果某位用戶刪除了本地的團隊記憶文件，這個刪除動作不會同步給其他人，避免單一用戶的誤刪操作毀掉整個團隊的共享認知**。

**3. 代理持久化記憶的「作用域隔離」**系統支援自定義特化的 Agent（如代碼審查 Agent 或測試 Agent），而**每個 Agent 類型都有自己獨立的記憶作用域**。這意味著不同職能的 Agent 累積的經驗是完全物理隔離的，互不干擾，從而在架構上避免了不同工作流之間的資料污染**。**

**在 Claude Code 的「長期記憶（MD 系統）」這個核心分層知識庫引擎的脈絡下，系統嚴格奉行了一套**「封閉類型」的儲存哲學****。來源認為，這是整個長期記憶設計中最具巧思的部分，因為它明確界定了 **只有以下四種特定類型的資訊才值得被寫入記憶** **，藉此維持極高的信噪比**：

* **User（用戶畫像）類型** **：主要記錄用戶的個人特徵，例如角色定位、核心目標、技能水準以及特定的工作習慣**。其核心目的是**幫助 AI 建立精準的用戶畫像，從而提供高度個人化的協作體驗**。
* **Feedback（行為反饋）類型** **：記錄用戶對 AI 執行結果的糾正與確認**。來源特別指出這裡有一項非常反直覺的精妙設計：系統**不僅會記錄 AI「做錯了」的負面糾正，還會主動記錄 AI「做對了」的成功反饋**。這是因為如果只單向記錄錯誤，模型在未來的操作中會變得過度保守；記錄成功的反饋能明確向 AI 傳達「這種做法是正確的，以後請繼續保持」，這對於塑造 AI 的長期行為模式至關重要**。**
* **Project（項目上下文）類型** **：專門儲存****無法直接從代碼本體中推導出來的專案背景資訊**。例如專案的業務截止日期、高階設計目標、或是團隊內部的協作約定等**。針對這類記憶，系統強制規定了一項重要原則：** **所有的「相對日期」都必須被強制轉換為「絕對日期」** **（例如不能寫「下週五」，必須明確存為「2026年4月10日」），以避免隨著時間推移導致記憶失去參考意義**。
* **Reference（外部引用）類型** **：作為指向外部系統的靜態指標**。例如特定 Issue 的追蹤連結、Grafana 的監控面板網址或是相關的 Slack 頻道等**。**

**核心洞察：「不存什麼」比「存什麼」更關鍵**來源強調，要真正理解這四種儲存類型的價值，必須同時看見系統 **明文禁止存儲的內容** **。系統嚴格禁止將代碼模式、架構分析、文件路徑、Git 歷史或除錯方案寫入長期記憶中**。

**這背後的設計理念非常高明：****這些資訊全都可以從代碼庫本身實時推導出來，因為「代碼本身就是最權威的單一真相來源」**。如果在長期記憶中額外儲存這些資訊的副本，不但容易因為代碼頻繁變更而迅速過時，還極易導致記憶與現實產生矛盾**。透過嚴格堅守這四種分類的資訊邊界，Claude Code 成功** **避免了讓記憶系統退化成什麼都往裡塞的「萬能垃圾桶」** **，確保長期記憶始終保持高純度與高效用**。

在更大的「4. 長期記憶 (Long-term/MD System)」背景脈絡下，討論這些來源對「動態相關性召回」的看法。

**在 Claude Code 的「長期記憶」架構下，長期記憶是一個基於磁碟 Markdown 文件構建的分層知識庫引擎，它在物理儲存上分為兩層：始終加載到上下文中的純索引文件（**`memory.md`），以及可能多達數十上百個的具體記憶文件**。**

**由於不可能將所有詳細的記憶文件都塞進上下文中，系統必須決定在特定時刻「該加載哪些具體記憶」，這便是**「動態相關性召回」**機制發揮作用的地方**。來源對此機制的運作與設計理念有以下深度的解析：

**1. 採用「獨立的 AI 決策」取代傳統檢索**來源指出，這個設計最核心的思路在於，**它把「選擇相關記憶」當作一個獨立的 AI 決策任務來處理，而不是依賴傳統的關鍵詞匹配或向量檢索**。**在每輪對話開始時，系統會異步啟動一個名為 prefetch 的預取流程（與主模型的響應並行，不會阻塞主流程）**。該流程會掃描記憶目錄下的 Markdown 文件，讀取 front matter 提取描述，然後**使用輕量級模型 Claude Sonnet 進行一次「旁查詢」（side query）**。Sonnet 會根據當前的對話上下文，智能判斷並篩選出最相關的記憶，這種做法既保證了篩選的品質，又有效控制了 Token 成本**。**

**2. 嚴格的召回約束與抗污染機制**為了確保召回的記憶精準且不干擾當前任務，Sonnet 的召回過程受到多重約束：

* **數量限制** **：最多只返回 5 篇，不確定的就不選**。
* **去重過濾** **：已經在之前對話輪次中展示過的記憶會被自動過濾掉**。
* **防止污染** **：系統會刻意壓低最近使用過的「工具相關文檔」的優先級，避免這些操作型文檔污染了真正有價值的記憶召回**。

**3. 專為模型設計的「記憶新鮮度」標註**召回機制不僅關注「相關性」，還高度關注「時效性」。每一個被召回的記憶都會被標註其「年齡」**。系統****刻意不使用 ISO 絕對時間，而是轉換成「今天」、「昨天」、「47天前」這種自然語言描述**。來源解釋，這是因為大型語言模型不擅長複雜的日期算術，自然語言的描述更能有效觸發模型的常識性推理**。**

**4. 預防幻覺的「時間快照」警告**如果召回的記憶時間超過一天，系統會強制附帶一個警告：**指出該記憶僅是「時間快照與歷史狀態」，要求 AI 在引用前必須先進行驗證**。來源高度評價這套召回防護體系，認為它從根本上解決了 AI 記憶系統的一個核心痛點：**「記憶說某個東西存在，不等於它現在還存在」**。

在更大的「6. 休眠重塑記憶 (Auto Dream)」背景脈絡下，討論這些來源對「四階段流程」的看法。

**在 Claude Code 最具想像力的第六維度「休眠重塑記憶（Auto Dream）」機制中，這套「四階段流程」被來源高度評價為****完全模擬了人類整理筆記的思維模式**。

**Auto Dream 的核心定位是跨會話的定期「覆盤整理」，為了避免過度消耗資源，它設定了嚴格的觸發門檻（距離上次整合超過24小時且產生5個新會話的記憶）**。一旦觸發，系統便會啟動這套高度擬人化的四階段清理流程：

* **Orient（定向探索）** **：這就像是人類在整理筆記前會「先看全局」**。子代理會先瀏覽整個記憶目錄，檢視現有文件及 `memory.md` 索引的狀態，並主動尋找是否有重複或近似的主題**。**
* **Gather（資訊收集）** **：接著進入「收集新資訊」階段**。系統會查看最近的日誌，並檢查舊記憶是否與代碼庫的當前狀態產生矛盾**。在此階段，若需要檢索對話轉錄文件，系統只會使用精確的搜尋詞來找尋特定資訊，嚴格禁止進行寬泛的掃描**。
* **Consolidate（整合）** **：這一步負責「合併整理」**。系統會將新的資訊與信號整併到已有的主題文件裡，避免產生冗餘的近似副本**。來源特別指出這裡有兩個關鍵的工程規則：一是必須將相對日期轉換為絕對日期；二是對於被推翻的舊事實，系統會** **直接將其刪除** **，而不是僅僅標註為「已過時」**。
* **Prune and Index（修剪和更新索引）** **：最後一步是「精簡索引」**。系統會嚴格控管 `memory.md` 索引文件的規模，確保其保持在 200 行以內，且每行索引不超過 150 個字元**。同時會刪除陳舊的指標、壓縮冗長的條目，並解決其中存在的矛盾**。

**來源認為，這套四階段流程是 Claude Code 記憶體系中極為出彩的設計**。它跳脫了傳統 AI 系統只會單純把對話堆疊存下來的作法，而是透過「先看全局，再收集新資訊，然後合併整理，最後精簡索引」的擬人化思維，確保記憶系統能維持極高的信噪比，避免在長期運作下退化成一個塞滿無效資訊的垃圾場**。**

在更大的「系統特性與安全」背景脈絡下，討論這些來源對「團隊同步」的看法。

**在 Claude Code 的「系統特性與安全」背景脈絡下，來源指出「團隊同步」記憶本質上是一個基於遠端 API 的跨終端同步資料庫，允許同一個代碼倉庫的所有協作者共享一份團隊記憶**。為了在提供這項系統協作特性的同時確保極致的安全性，系統確立了一個核心工程原則：**團隊共享特性的安全性必須比個人特性高出一個等級**。

**關於團隊同步的具體系統特性與安全防護機制，來源探討了以下幾個關鍵層面：**

**1. 服務端優先與「刪除不傳播」的同步特性：**在數據同步的邏輯上，團隊記憶遵循「服務端優先」的策略（Pull 時伺服器內容覆蓋本地，Push 時只上傳哈希值變化的條目）**。特別值得注意的是，系統設計了「刪除不傳播」的保護機制，也就是說，如果某個開發者刪除了本地的團隊記憶文件，這個操作不會同步給其他人，且下次 Pull 時文件又會恢復**。這能有效避免單一團隊成員的誤刪操作癱瘓或影響整個團隊的共享認知**。**

**2. 第一道安全防線：路徑安全防護與防逃逸攻擊：**由於團隊共用代碼庫，系統必須防止惡意的倉庫內容進行「Simlink（符號鏈接）逃逸攻擊」**。例如，防範惡意用戶在團隊記憶目錄裡放置一個指向本地敏感目錄（如 **`.ssh`）的符號鏈接**。為此，系統在寫入操作前會進行多層防護：先做字串級別的路徑規範化檢查，再用真實路徑解析文件系統**。它會直接拒絕指向不存在目標的符號鏈接，並且連 URL 編碼的路徑遍歷攻擊和 Unicode 的全角字元攻擊都防範在內**。**

**3. 第二道安全防線：敏感數據自動審查：**因為團隊記憶會無差別地共享給所有該倉庫的協作者，如果不小心將個人密鑰存入其中，將會導致嚴重的資安後果**。因此，在寫入團隊記憶以及向上同步推送之前，系統會強制運行一套基於正則表達式和關鍵詞的過濾器**。這套過濾器專門用來檢測 GitHub PAT、AWS Access Token 等敏感資訊，一旦檢測到就會直接攔截寫入操作**。**
