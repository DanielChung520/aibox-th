# 04 — 進貨小幫手

> **Agent Key**: `receiving_assistant`
> **Endpoint**: `POST /receiving-assistant/chat`（建議）
> **Ragic 關聯**: ERP_15（收貨單）、ERP_48/ERP_16（進貨/退貨異常）
> **前端對應**: RagicLogisticProcess「收貨單」→「退貨/進貨異常」節點
> **狀態**: ⬜ 未實作

---

## 1. 概述

協助倉管/品管/採購透過 LINE 查詢收貨進度、退貨處理狀態。包含兩種操作類型：收貨查詢（讀取）和異常回報（需確認的寫入）。

### 負責業務邊界

```
倉管/品管在 LINE 上的進貨管理需求
  ├── XX 收貨了沒 → 查詢收貨/進貨單狀態（讀取）
  └── 這批貨有問題 → 回報收貨異常（寫入，需確認）
```

### 不負責

- ❌ 建立採購單（由採購小幫手負責）
- ❌ 更新庫存數量
- ❌ IQC 檢驗作業

## 4. LINE 對話範例

### 4.1 收貨進度查詢（讀取）

```
User > PO-202605003 收貨了嗎？

Agent > 採購單 PO-202605003
       ─────────────────────────
       供應商：XX食品
       品項：A001 原料 x 1,000 KG
       ─────────────────────────
       收貨狀態：
       ✅ 已收貨：600 KG（收貨單 GR-202605001）
       ⏳ 未收貨：400 KG（預計 05/10 到貨）
       
       IQC 狀態：⏳ 檢驗中（取樣 3 件）
       ─────────────────────────
```

### 4.2 異常回報（寫入 + 確認）

```
User > 今天來的 A001 有問題

Agent > 請描述異常情況：
       1. 哪個採購單/收貨單？
       2. 哪個品項有問題？
       3. 異常數量？
       4. 異常原因？（例如：規格不符/品質異常/數量短少/破損）

User > PO-202605003，A001 原料規格不符，200KG

Agent > 好的，以下是異常回報內容：
       ─────────────────────────
       相關單號：PO-202605003
       品項：A001 原料
       異常數量：200 KG（總量 1,000 KG）
       異常原因：規格不符
       ─────────────────────────
       請問以上內容是否正確？
       (請回覆「確認」以送出異常回報)

User > 確認

Agent > ✅ 異常回報已送出！
       異常單號：ER-20260507-0001
       狀態：已通報，等待採購/品管確認
       我們將盡快為您處理。
```

### 4.3 退貨查詢

```
User > ER-001 處理得如何？

       ─────────────────────────
       相關採購單：PO-202605003
```

## 5. 意圖分類

| 意圖 | 觸發關鍵字 | 類型 | 處理方式 |
|------|-----------|------|---------|
| `gr_query` | 收貨, 進貨, 到貨, 收貨單, GR-, 收了嗎 | 讀取 | Data Agent 查 ERP_15 |
| `gr_return` | 退貨, 異常, 不合格, 有問題, 不良, ER- | 讀取 | 查異常記錄集合 |
| `gr_report` | 回報, 異常回報, 通報, 這批有問題 | **寫入** | 摘要→確認→寫入異常記錄 |
| `general_chat` | 其他 | 閒聊 | LLM 一般對話 |

## 6. 資料模型

### gr_exception_reports（異常回報記錄）

```json
{
  "_key": "ER-20260507-0001",
  "report_id": "ER-20260507-0001",
  "related_po": "PO-202605003",
  "related_gr": "GR-202605001",
  "item_name": "A001 原料",
  "quantity": 200.0,
  "unit": "KG",
  "reason": "規格不符",
  "reporter_id": "line:U1234567890",
  "reporter_name": "王小明",
  "source": "line",
  "status": "REPORTED",
  "notes": "",
  "created_at": "2026-05-07T10:00:00Z",
  "updated_at": "2026-05-07T10:00:00Z"
}
```

### 異常狀態列舉

| 值 | 說明 |
|----|------|
| `REPORTED` | 已回報（LINE 建立後預設） |
| `PROCESSING` | 處理中（採購/品管確認中） |
| `RESOLVED` | 已解決 |
| `CONVERTED` | 轉退貨（啟動正式退貨單） |
| `CLOSED` | 已結案 |

## 8. 確認機制

| 階段 | 條件 | Agent 行為 |
|------|------|-----------|
| **異常摘要** | LLM 解析異常資訊後 | 以結構化格式呈現，要求確認 |
| **確認** | 使用者確認 | 寫入 `gr_exception_reports`，回傳異常單號 |
| **修改** | 使用者修改內容 | 重新解析 → 更新摘要 → 再次要求確認 |
| **拒絕** | 使用者說「不用」 | 放棄，回到 IDLE |
| **逾時** | 30 分鐘無回應 | 放棄暫存資料 |
