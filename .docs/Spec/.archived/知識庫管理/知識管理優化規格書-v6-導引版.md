## 1. 文件定位

本文件不是最終實作規格，也不是架構宣言。

本文件的作用是：

> **把《知識管理優化規格書 v6》中的方向性原則，轉化為後續可拆解、可接續、可分工的規格導引。**

它的主要讀者包括：

- 後續撰寫細部規格的人
- 後續實作 HybridRAG / knowledge management 的 coder agent
- 負責審查資料模型、API 契約、前後端改動的人

## 3. 為何需要導引版

《知識管理優化規格書 v6》已明確定義知識管理的新中心：

- 知識邊界治理
- 有界證據組裝
- Governed Memory
- Provenance / Auditability

但它仍屬於**上位規格**，主要回答的是：

- 為什麼要這樣做
- 核心重心在哪裡
- 哪些舊假設必須放棄

它尚未完整回答：

- 應先細化哪一層
- 哪些內容現在可以定義
- 哪些內容必須延後到 HybridRAG / UI / API 細規
- 如何避免 coder agent 把宣言誤當開發說明

因此需要本導引版作為過渡層。

---

## 4. 現階段已確定的事

以下內容在目前討論中，已可視為穩定前提：

### 4.1 知識管理不再以 upload pipeline 為中心

上傳、切塊、向量化、圖譜抽取仍然存在，但它們只是支援層。

### 4.2 知識管理的核心輸出是 Evidence Pack

後續任何細規，都必須以 Evidence Pack 為最終可交付知識單位，而不是停留在：

- file
- chunk
- vector point
- graph node

### 4.3 HybridRAG 的未來角色已確定

HybridRAG 不再只是：

> vector search + graph search + fusion

而是：

> **bounded evidence assembly system**

### 4.4 知識邊界是產品安全契約的一部分

是否允許使用某段知識，不可由 LLM 自主判斷。

### 4.5 記憶不是累積，而是組裝

後續若討論記憶、memory service、memory agent，都不得偏離此原則。

## 5. 現階段故意不定死的事

為了避免過早鎖死錯誤方案，以下內容暫不在本文件中定稿：

### 5.1 HybridRAG 內部融合數學

例如：

- vector score normalization
- BM25 與 graph score 的融合方式
- RRF 的最終參數
- path expansion 的權重模型

這些應在後續 HybridRAG 細規中定義。

### 5.2 Canonical ID 的最終命名策略

雖然 v6 已明確要求 canonical link 必須存在，但：

- entity_id 的命名形式
- vector point payload 命名規則
- evidence_id 的生成規則

應在資料模型細規中定義。

### 5.3 最終 API response 欄位細節

本導引版只確立「哪些型別資訊必須存在」，不定義具體 JSON 最終格式。

### 5.4 UI 最終交互細節

例如 provenance 呈現形式、node detail panel、evidence explainability panel 的細節，應延後到 UI/前端規格。

## 6. 後續拆規格的正確順序

後續文件應依以下順序產出，順序不可顛倒：

### Phase 1：HybridRAG 優化與證據組裝規格

目的：把「bounded evidence assembly」細化為真正可開發的核心規格。

必須回答：

- vector / graph / raw chunk / ontology 如何被組裝
- fusion / provenance / usable scope 如何輸出
- 哪些資料可以進 evidence pack
- query + root_id + role + ontology 如何形成 evidence boundary

### Phase 2：資料模型與 API 契約規格

目的：把 v6 原則與 HybridRAG 細規轉成具體資料結構與接口。

必須回答：

- ArangoDB collections / fields / indexes
- Qdrant payload schema
- evidence pack schema
- lifecycle state machine
- search / provenance / reindex / revoke API

### Phase 3：UI / Review / Audit 規格

目的：讓 provenance、boundary、lifecycle 真正能被人類看見、審查、撤回。

必須回答：

- KB detail 頁要顯示哪些證據資訊
- node / edge 如何回查原文
- 哪些 UI 動作可以觸發 re-run / revoke / activate
- 審核者如何知道一段知識是否可被 AI 使用

### Phase 4：操作感知與意圖收斂規格

目的：讓知識管理與 actionTrail / intent system 結合。

必須回答：

- actionTrail 如何作為 evidence assembly 的上下文輸入
- 哪些 evidence pack 可支援 intent convergence
- rule 與 intent llm 的交替使用如何落地

## 7. 每份後續規格至少要回答的問題

為避免再次產生宣言式規格，從這份導引版開始，後續每份文件至少要回答以下五類問題：

### 7.1 資料問題

- 新增哪些 collection / fields / payload
- 哪些欄位是 required
- 哪些欄位是 derived

### 7.2 流程問題

- 誰觸發
- 何時執行
- 同步或異步
- 失敗時怎麼降級或回滾

### 7.3 邊界問題

- 這層能處理到哪裡
- 不能處理什麼
- 何時交給下一層

### 7.4 驗證問題

- 什麼算成功
- 什麼算失敗
- 用哪些測試或指標驗收

### 7.5 遷移問題

- 舊資料如何兼容
- 是否需要 backfill
- 是否允許灰度期雙軌並存

## 8. 對 coder agent 的使用方式

本文件不可被直接視為開發任務書。

對 coder agent 的正確使用方式是：

### 8.1 可以做的事

- 依本文件判斷接下來該先補哪份細規
- 檢查某份新規格是否越界或跳步
- 用本文件評估某實作方案是否偏離 v6 中心

### 8.2 不應直接做的事

- 直接依本文件修改資料模型
- 直接依本文件開 API
- 直接依本文件重構 HybridRAG

因為本文件故意沒有落到 تلك個層級。

---

## 9. 對後續 HybridRAG 細規的明確要求

當後續開始撰寫 HybridRAG 細規時，必須至少承接以下內容：

1. 不得退回「檢索命中率導向」敘事
2. 必須以 Evidence Pack 作為輸出中心
3. 必須明確區分 vector / graph / fusion / raw 的責任
4. 必須把 provenance / boundary / usable scope 寫進資料與 API 契約
5. 必須說明與 ontology、root_id、role auth、lifecycle status 的關聯

---

## 10. 對後續知識管理開發的分工建議

若未來由多個 coder / architect / agent 並行工作，建議按以下責任面切分：

| 面向 | 建議負責範圍 |
|------|--------------|
| 架構/規格 | HybridRAG 細規、Evidence Pack、boundary contract |
| 後端數據 | Arango/Qdrant schema、canonical link、lifecycle |
| 後端服務 | search API、provenance API、reindex/revoke flows |
| 前端 | KB detail、graph provenance、審核介面 |
| 運維/治理 | backfill、遷移、監控、稽核報表 |

---

## 11. 本文件的結論

v6 上位規格已經回答了「知識管理應該成為什麼」。

本導引版回答的是：

> **接下來應該如何把這個方向，拆成不互相打架、可以逐步收斂的細規與開發工作。**

因此，本文件的作用不是增加新理念，而是保證後續工作都遵守以下紀律：

1. 先細化 HybridRAG / Evidence Assembly
2. 再落資料模型與 API 契約
3. 再落 UI / provenance / audit
4. 最後才接上操作感知與意圖收斂

這個順序，是為了讓知識管理先成為可靠底座，而不是再一次變成功能拼裝區。
