# 技能 04 — 資料智能體（Data-Agent）

## 核心理念：為何企業 AI 查詢總是幻覺？

### 企業資料的規模困境

一般企業的 ERP Schema（資料綱要）有多大？

- 一套完整的 Ragic ERP，262 張資料表
- 每張表 10～50 個欄位，加上關聯描述
- 總計可能超過 **6MB 的結構描述**

而目前最強大的 LLM，context window 也只有 128K～200K tokens（約 0.1～0.2MB）。把整個企業 schema 塞進去？不可能。

**結果**：一般企業 AI 只能盲猜。它看不見企業的資料結構，只能根據訓練時的片段資訊臆測，幻覺率居高不下。

### 我們的答案：智能體（AI + Human Co-Intelligence）

艾企的資料智能體不是「AI 替代人查資料」。它的定位是：

> **AI 與人共同組成的智能體——AI 看得見 Schema，人看得懂業務。兩者協作，缺一不可。**

設計原則：

| 原則 | 說明 |
|------|------|
| **Schema 不進 LLM** | 完整的 262 表存在 ArangoDB，LLM 只收到「意圖匹配後的精確子集」 |
| **Progressive Narrowing** | 使用者逐步縮小範圍，AI 隨之愈來愈精確 |
| **Behavioral Detection** | AI 偵測使用者的表達錯誤，透過前端互動即時修正 |
| **資料不上雲端** | 企業 ERP 資料僅用於查詢比對，不會被保存到 LLM 服務端 |
| **預判而非臆測** | AI 預判使用者下一步可能問的問題，主動提供捷徑 |

## 1. 資料綱要管理（Schema 管理頁面）

### 路由
`/app/data-agent/schema`

### 前置條件
- 已登入系統
- Data Agent 服務正常運作（port 8003）

### 核心理念：讓人類看得懂 Schema，讓 AI 學得會業務

262 張資料表代表 262 個業務概念。使用者不需要知道資料庫的物理結構，只需要知道：

- **我想查什麼業務資料？**
- **這個資料存在哪張表？**
- **這張表有哪些欄位？**

Schema 頁面就是這個探索過程的介面。AI 在後台學習使用者的瀏覽行為，使用者在前台逐步縮小範圍——這是雙向的共同學習。

### 頁面結構

```
┌─────────────────────────────────────────────────────────────┐
│  Data Agent Schema 管理              有效 247 / 無效 15     │
├─────────────────────────────────────────────────────────────┤
│  [全部] [基礎資料] [進銷存] [生產製造] [品質/ISO] [CRM/SCM] │
│  [管理]                                                    │
│  [🔍 搜尋表名或 Table ID]                                  │
│                                                             │
│  [全部] [資料庫] [基本資料維護檔] [ERP表單清單] [庫存] ...  │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Table Name      │ Module │ Tab    │ Status │ 操作    │   │
│  ├──────────────────────────────────────────────────────┤   │
│  │ PURCHASE_1     │ 採購   │ stock  │ 有效   │ 欄位/資料/編輯/刪除 │
│  │ INVENTORY_5    │ 庫存   │ erp    │ 有效   │ ...        │   │
│  │ BOM_COMPONENT  │ 生產   │ mes2   │ 無效   │ ...        │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 操作步驟

**Step 1. 選擇業務分類**
從頂部分類標籤（基礎資料 / 進銷存 / 生產製造 / 品質/ISO / CRM/SCM / 管理）中選擇感興趣的範圍。

→ AI 學習：使用者關注哪個業務範圍

**Step 2. 切換模組 Tab**
同一分類下有多個模組 tab，點選切換。

→ AI 學習：使用者的業務角色

**Step 3. 搜尋特定資料表**
在搜尋框輸入表名或 Table ID，過濾結果。

→ 使用者主導：直接表達意圖，AI 輔助驗證

**Step 4. 查看欄位結構**
點選某列的「**查看欄位**」按鈕，彈出 Modal 顯示該表的完整欄位：

| 欄位名 | 類型 | 可寫入 | 備註 |
|--------|------|--------|------|
| supplier_id | VARCHAR | ✅ | 供應商編號 |
| order_date | DATE | ✅ | 採購日期 |
| total_amount | DECIMAL | ✅ | 總金額 |

→ **關鍵**：使用者看到的不只是欄位名稱，而是業務語義（備註欄位的說明）

**Step 5. 預覽實際資料**
雙擊任意列，或點選「**查看資料**」，彈出 Modal 顯示真實資料預覽（分頁或全部）。

→ 驗證：這張表的資料是否符合我的業務預期？

**Step 6. 管理與維護**
- **編輯**：修改表的名稱、模組、頁籤等元資料
- **刪除**：移除不再需要的資料表
- **匯入**：上傳新的 Ragic 資料表

### 介面元素

| 元素 | 說明 |
|------|------|
| 統計標籤 | 即時顯示有效/無效資料表數量 |

## 2. 架構解密：智慧從何而來

### 2.1 核心設計原則：「從不傳送完整 Schema 給 LLM」

程式碼開頭明示（`data_agent/query/nl2sql/schema_retriever.py`）：

```python
"""
NL→SQL Pipeline - Schema Retriever

Retrieves pruned schema context from ArangoDB for the tables
identified by intent classification. Never sends full schema to LLM.
"""
```

這不是比喻，而是嚴格的技術約束。

### 2.2 資料流向

```
使用者瀏覽 Schema 頁
    ↓ 行為（點了哪些分類、哪些表、停留多久）
    ↓
ArangoDB（262 表 schema + 欄位 + 關聯）
    ↓ 即時查詢（按意圖只取需要的子集）
    ↓
AI 看不到全貌，只看到：
  - 使用者明確感興趣的 1～3 張表
  - 每張表的欄位結構與業務說明
  - 歷史查詢中使用者表達過的意圖模式
    ↓
當使用者輸入自然語言查詢時：
NL → 意圖分類（Qdrant 向量匹配）→ 只取出相關 1～3 表的 schema
→ LLM 只翻譯這精確的上下文 → SQL → Ragic API → 結果
```

### 2.3 為何不用 Template？

並非所有查詢都能靠 Template 應對。系統採用三層生成策略：

| 策略 | 適用場景 | LLM 需求 |
|------|---------|---------|
| **Template** | 簡單、模式固定的查詢 | 無（直接替換參數） |
| **Small LLM** (qwen2.5-coder:7b) | 中等複雜度，單表為主 | 聚焦 Schema + 簡單推理 |
| **Large LLM** (qwen3:32b) | 複雜多表 JOIN、聚合 | 完整推理 |

**關鍵**：無論哪種策略，傳給 LLM 的 schema scope 都**極小**（1～3 表），遠小於 6MB 的總 schema。

### 2.4 意圖 RAG（Intent RAG）

每一個常見的業務查詢，都會被轉化為一個「意圖」存入 Qdrant 向量資料庫：

```json
{
  "intent_id": "QUERY_SUPPLIER_UNDER_BUDGET",
  "description": "查詢採購金額超過指定門檻的供應商",
  "tables": ["PURCHASE_1", "SUPPLIER_MASTER"],
  "core_fields": ["supplier_name", "total_amount", "order_date"],
  "tool_schema": {
    "filterable_fields": ["total_amount", "order_date"],
    "aggregatable": ["total_amount"]
  },
  "nl_examples": [
    "哪些供應商本月採購超過100萬",
    "查詢供應商採購金額"
  ]
}
```

當使用者輸入自然語言，系統：
1. 生成查詢的 embedding（bge-m3 模型，1024 維）
2. 在 Qdrant 中做向量相似度搜索
3. 取出分數最高的 Intent（threshold 過濾）
4. 取出該 Intent 指定的 tables 和 fields
5. **只把這 1～3 表的 schema 傳給 LLM**

### 2.5 解決 6MB Schema 的具體技術

| 技術 | 說明 |
|------|------|
| **意圖裁剪（Intent Pruning）** | 從 262 表中，只取出 intent 命中的 1～3 表 |
| **Tool Schema** | 每個 intent 攜帶結構化的 tool_schema（JSON Schema），只包含 filterable/aggregatable 欄位標記 |
| **Schema Brief** | 格式化時只傳給 LLM pruned schema brief（含 S3 parquet 路徑），而非原始 6MB 結構 |
| **三層生成** | Template → Small LLM → Large LLM，按需升級 |
| **S3 路徑直送** | SQL 生成 prompt 直接使用 `read_parquet('s3://bucket/module/table')` 路徑，LLM 不需內嵌資料 |

### 2.6 快取架構

| 層次 | 位置 | 說明 |
|------|------|------|
| 配置快取 | `config_reader.py` | 系統參數（模型名、threshold 等），300s TTL 程序記憶 |
| Ragic 連線快取 | `ragic/config_loader.py` | Ragic 連線配置，TTL |
| 向量儲存 | Qdrant | Intent 向量持久化儲存，Upsert 同步 |
| Server DuckDB | Rust API Gateway | 查詢結果的 Server-side DuckDB 快取，減少 S3 IO |

## 3. 使用者與 AI 的共同演化

### 當使用者在 Schema 頁探索時：

1. **AI 學習業務範圍**：從使用者點擊的分類和 tab，推斷其業務角色
2. **AI 驗證表達意圖**：使用者的搜尋關鍵字，成為下一輪意圖匹配的訓練信號
3. **AI 預判查詢需求**：當使用者屢次瀏覽某張表，AI 預判其可能想查這張表的資料

### 當使用者在 NL→SQL 查詢時：

1. **AI 翻譯自然語言**：將模糊的業務描述轉為精確的 SQL
2. **AI 偵測表達模糊**：當意圖分數低於 threshold，主動要求澄清
3. **AI 提供捷徑**：基於歷史查詢，推測使用者可能想問的 follow-up

### 資料安全的設計

| 資料 | 去哪裡？ |
|------|---------|
| 使用者的 NL 查詢文字 | 只送到本地 Ollama（embedding）→ Qdrant（向量比對） |
| 選中的 1～3 表 schema | 送到本地 Ollama（NL→SQL 翻譯） |
| 查詢結果（Ragic 資料） | 直接返回前端，不經過任何第三方 |
| **企業資料本身** | **從未離開 Ragic 伺服器** |

## 常見問題

**Q: 為什麼有 262 張資料表？**
> 這些是 Ragic ERP 中的業務資料表，涵蓋採購、庫存、生產、銷售、財務等模組。艾企透過意圖匹配，使用者只需要用自然語言描述需求，系統自動找出對應的 1～3 表來回答。

**Q: 如何確保 AI 不會幻覺？**
> 三層保障：(1) Schema 從不全量送入 LLM，只取出意圖匹配後的精確子集；(2) 使用者可以在 Schema 頁預覽實際資料，先確認這張表是不是自己想要的；(3) NL→SQL 提供四個偵錯 Tab（result/intent/params/debug），可追蹤整翻譯鏈路。

**Q: 為何需要先探索 Schema，不能直接問問題？**
> 可以直接問。但探索 Schema 的過程中，AI 也在學習使用者的業務範圍和查詢習慣。多次互動後，意圖匹配的精準度會持續提升——這是共同演化的過程。

**Q: NL→SQL 翻譯錯了怎麼辦？**
> 系統提供四個偵錯 Tab：result（結果）、intent（意圖匹配分數）、params（翻譯後的 SQL 參數）、debug（原始錯誤）。使用者可以回頭到 Schema 頁驗證這張表是否正確。

**Q: 資料會被保存到 LLM 服務端嗎？**
> 不會。Embedding 計算在本地 Ollama 完成，向量存放在本地 Qdrant，LLM 推理也在本地。企業 ERP 資料只通過 Ragic API 查詢，不會離開你的伺服器。
